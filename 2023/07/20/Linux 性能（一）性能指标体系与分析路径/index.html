Linux 性能（一）性能指标体系与分析路径

发表于 2023-07-20 分类于 性能优化
本文字数： 5.5k 阅读时长 ≈ 5 分钟

引言

接口超时、P99 飘高，落到压测报告里就是一句「慢」。这个字没法直接查，得先换成数。工具倒是不缺，top、vmstat、iostat、sar 装一整套，敲下去就是一屏。难的是 CPU 没跑满、响应时间翻了几十倍，先看哪个，看到什么算查到头。从应用一直到硬件，哪一层都可能把请求拖住，几层一起出问题也有。报告里常常只写「CPU 没跑满，资源还有余量」，P99 那一段怎么涨的，没说。

这十四篇就照这条路走。例子只用一套：4 核 8G、一块 SSD、千兆网卡，跑个 Java HTTP 服务。压测从 300 QPS 加到 3000，P99 从 40 毫秒涨到 800 毫秒，load 4.2，CPU 才 30%。机器和配置都没换，量级一上去就慢。慢在哪一层，从采到的数里找。

篇目按四层资源排：CPU、内存、磁盘 I/O、网络，最后两篇落到监控和整体排查。每篇配一个能重跑的实验，命令和输出原样贴出来。数怎么读、这么改要付什么代价、什么时候不必这么查，都写在里头。工具手册和内核实现不展开，用到再翻。十四篇目录：

性能指标的口径

「慢」是感受，得换成数才能查。压测报告里能落到纸面的就三类：单位时间完成多少请求、耗时怎么分布、失败占多少。少一类，后面的判断就会偏。只报 QPS 不说时延，高吞吐可能只是请求堆在队列里；换成平均耗时，长尾被抹平，超时但成功返回的慢请求在错误率里也一个都不算。

时延要给分位值。100 个请求里 99 个 20 毫秒、1 个 2 秒，平均值 39.8 毫秒，比 40 毫秒的目标还好看一点，实际有人等了 2 秒。验收只能拿 P99、P999 对目标，平均值看看趋势就够了。分位值要在客户端统计：服务端埋点只记处理时间，排队和网络往返都漏掉，压测里的长尾多数出在这两段。

资源侧按 USE 法看三项：使用率是资源忙了多久，饱和度是排队排了多久，错误数是明确失败的次数。

性能问题的本质，就是系统资源已经达到瓶颈，但请求的处理却还不够快，无法支撑更多的请求。

应用侧的数和资源侧的数，中间隔着传导关系：

graph LR
  A["应用负载<br/>吞吐 / 时延 / 错误率"] --> B["资源使用<br/>使用率 / 饱和度 / 错误数"]
  B --> C["某层先到瓶颈"]
  C --> D["请求开始排队"]
  D --> E["P99 抬升"]
  E --> A

使用率低也可能已经卡在瓶颈上。CPU 30% 而运行队列常驻 4，是低使用率高饱和；磁盘 util 60%，await 从 1 毫秒涨到 20 毫秒，同样的情况。压测报告里常有人看到「没跑满」就收工，排队的那部分数没进报告。

容易混的一组 实际含义 搞混之后
并发数 / QPS 同时在途的请求数 / 单位时间完成的请求数 并发翻倍就以为吞吐翻倍，实际耗时也翻倍
平均响应时间 / P99 全体均值 / 99% 请求的耗时上限 均值达标但长尾用户超时
使用率 / 饱和度 忙时占比 / 排队程度 看到 30% 就停止排查
CPU 使用率 / 平均负载 CPU 忙闲 / 运行队列与不可中断进程 把 load 4.2 直接读成 CPU 用了 4 核
吞吐 / 错误率 完成量 / 失败占比 只统计 5xx，漏掉客户端超时

压测基线

基线要在压测之前记，事后补不出来。机器规格、并发数、压测时长固定，低压高压各跑一轮，应用侧和系统侧在同一个时间窗里采，两轮数字才算对得上。压测时长别中途改，采样窗口一错，分位值没法比。

指标 300 QPS 3000 QPS 读出来的信息
QPS 300 3000 目标压测值，两轮都跑满
P50 18ms 46ms 中位耗时涨 2.5 倍
P99 40ms 800ms 涨 20 倍，远快于 P50
P999 92ms 1.6s 尾部已经越过 1 秒
错误率 0.02% 0.4% 客户端超时开始出现
CPU us + sy 12% 30% 算力没跑满
iowait 1% 18% 有等待，但不足以独自解释 800ms
load average 0.8 4.2 4 核机器上队列接近满载
可用内存 5.1G 3.4G 差额主要是页缓存，不是泄漏证据
磁盘 await / util 1.2ms / 8% 24ms / 61% 有压力，没打满
网卡重传 0 少量 需要单独确认是否相关

P50 涨 2.5 倍，P99 涨 20 倍，变慢的只是一部分请求，这部分在等什么得往下追。CPU 30% 和 load 4.2 能同时成立：一个记忙闲，一个记队列长度，队列里排着的可能全是等 I/O 或等锁的进程。

「等什么」可以拆成几条能用数字否掉的假设：

假设 若成立，哪个指标会变 先用的工具
上下文切换与调度延迟 每秒切换数、非自愿切换上升 vmstat、pidstat -w
日志写放大、块设备等待 await、iowait 继续抬升 iostat、strace
软中断或网络重传 softirqs、重传计数上升 /proc/softirqs、sar -n
应用锁或依赖服务变慢 线程 D 状态增多、应用耗时分段偏移 应用指标、strace
页缓存回收与缺页 major fault、内存 PSI 上升 vmstat、/proc/pressure/memory

平均值的误读

  1. 用平均响应时间验收。上面那组数里 P99 已经 800 毫秒，平均值可能只有 70 毫秒，报告写「平均 70ms，达标」，等了将近 1 秒的那批用户就不见了。SLO 得绑分位值，平均值留着看趋势。
  2. CPU 没跑满就判机器没问题。等待也可能发生在块设备、网络、应用锁或者内存回收上。30% 只排除了算力耗尽这一条。
  3. 只看单机资源，不看应用侧分段。数据库慢查询、下游限流都能压低吞吐，本机指标这时候全正常。应用侧耗时分段要在基线那一轮就采上。
  4. 指标没到拐点就调内核参数。连接跟踪表、缓冲区、超时值改一行就生效，可没有可比基线，改完压测数字动没动说不清，参数倒是一直留在机器上。
  5. 把工具输出当结论。top 里排第一的进程未必是瓶颈，中间还差一步：哪个指标异常、据此假设什么、拿哪条命令验。
什么情况不必这么做 原因 替代做法
单机日请求几千、P99 长期稳定在 50ms 内 离拐点很远，采集与看板成本大于收益 只留错误率和基础资源告警
离线批处理、定时报表 关心总耗时与产出正确性，分位值没有意义 记作业起止时间与失败率
压测环境与生产规格不一致 CPU 核数、磁盘类型一变，基线不可迁移 先在同规格环境重跑两轮
瓶颈明确在依赖服务 单机指标再细也改不动下游 先看调用链耗时占比
没有 SLO 的内部工具 「变慢」没有目标值就无法判定 先定一个可接受的 P99 上限

时延、吞吐与利用率

指标 口径 采集入口 常见误读
QPS / TPS 单位时间完成的请求数 客户端压测工具、应用埋点 与并发数混为一谈
P50 / P99 / P999 耗时分位值，不是平均 压测工具 --latency、应用直方图 用平均值代表体验
错误率 失败请求 / 总请求 客户端统计、应用埋点 只算 5xx，漏掉超时
CPU 使用率 忙时 / 总时间，分 us、sy、iowait /proc/stat、mpstat 忽略 iowait 与 steal
饱和度 排队程度 /proc/pressure、vmstat 运行队列 与使用率当成同一个数
平均负载 运行队列 + 不可中断进程 /proc/loadavg、uptime 直接读成 CPU 核数占用
磁盘 await / util 单次 I/O 等待 / 设备忙时占比 /proc/diskstats、iostat util 没到 100% 就排除磁盘
网络丢包 / 重传 各协议层错误数 /proc/net/dev、sar -n 只看带宽不看重传

课程把性能工作拆成六步：选择指标、设定目标、基准测试、定位瓶颈、优化、监控告警。第二步常被跳过。目标得在压测之前定，看到 800 毫秒再回头说「P99 放宽到 1 秒吧」，这组数就没法用了。「能扛多少 QPS」也得先挂一个 P99 上限，不然同一套系统能报出相差十倍的两个数。

监控和告警排在六步末尾，采集不能等到最后才开。线上劣化发生在压测之外，判断有没有变差得翻历史曲线，前面那两轮基线只够覆盖压测这段时间。

小结与参考

800 毫秒的 P99 配上 30% 的 CPU 使用率，算力还有余量，排队已经发生。往下追「在等什么」，写成几条能用数字否掉的假设，再按资源层一条条验。动配置之前，压测那两轮基线和客户端的分位值得先留着，不然改完无从比对。
