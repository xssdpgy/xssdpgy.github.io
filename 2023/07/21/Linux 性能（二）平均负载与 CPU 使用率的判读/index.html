Linux 性能（二）平均负载与 CPU 使用率的判读

发表于 2023-07-21 分类于 性能优化
本文字数： 4.1k 阅读时长 ≈ 4 分钟

引言

压测报告上 load average 写 4.2，CPU 使用率写 30%，机器到底忙不忙？两个数各记一件事：负载数的是排队的进程，使用率算的是算力花掉多少。分开看谁也说不清，合起来才知道 4 核机器上队列接近满载、算力却没耗完，等待发生在别处。这篇拆开两个指标的口径，再用一组压测数据说明怎么一起读。

平均负载

uptime 最后三个数是过去 1、5、15 分钟的平均负载。它数的是单位时间内处于可运行 R 和不可中断 D 两种状态的进程数，跟 CPU 忙了多久是两套账。

平均负载是指单位时间内，系统处于可运行状态和不可中断状态的平均进程数，也就是平均活跃进程数，它和 CPU 使用率并没有直接关系。

R 状态是正在用 CPU 或正等着被调度的进程，ps 里标 R。D 状态卡在内核关键流程里，不能被打断，最常见的是等磁盘或网络 I/O 返回。进程发出读写后要等数据落盘，这中间被打断，磁盘上的数据和进程里的数据就对不上，所以 D 状态也算一层保护。负载把这两种都算进去，等 I/O 的进程即使一点 CPU 不吃，也会把负载顶上去。

进程状态 ps 标记 计不计入负载 通常在等什么
可运行 R 计入 正在跑，或在就绪队列等 CPU
不可中断 D 计入 磁盘、网络等硬件 I/O 返回
可中断睡眠 S 不计入 等事件、等定时器、等 socket
僵尸 Z 不计入 已退出，等父进程回收

三个数字是不同时间窗的指数衰减平均，当平均值理解就行，不必纠缠算法。判断负载高不高，先拿核数做尺子：

最理想是负载贴着核数走，每个核刚好跑一个进程。4 核机器上负载 4.2，意思是队列里的活跃进程比核数略多，多出来的那部分得排队。经验上超过核数的 70% 就值得盯一眼，但这个阈值不是硬线——单看一个数字判断不了，得看它相对自己历史曲线的变化。

负载 4.2 的判读

负载 4.2 只说了「有 4.2 个活跃进程」，没说它们在等什么。同样这个数，成因不同，下一步查的东西完全不一样。

四种常见成因里，最直观的是算力被打满：4 个进程各占一个核，负载和 CPU 使用率一起涨，这种最好查。麻烦的是另外几种。等 I/O 的进程停在 D 状态，负载照涨，CPU 使用率却上不去；再有就是一堆进程抢 4 个核，每个都只分到一点，负载高、使用率也高，但单个进程看起来都不忙。还有一类藏得更深：进程短命，top 刷新一次它就退出了，系统 CPU 明明很高，进程列表里却翻不到。

本篇的锚点数据属于哪种？load 4.2、CPU 30%，算力显然没打满。把三个时间窗摊开看：

1 分钟 4.20 高于 15 分钟的 2.11，负载还在往上走，不是一次瞬时抖动。这时候的 4.2 更像「排队在累积」，得往下追是哪一层在堵。

uptime 与 mpstat 命令

CPU 使用率来自 /proc/stat 里的节拍计数。这些数是开机以来的累计值，拿单次读数算出来的是开机至今的平均值，参考价值有限。工具的做法是隔几秒取两次快照做差，得到这段时间的使用率。

性能分析工具给出的都是间隔一段时间的平均 CPU 使用率，所以要注意间隔时间的设置，特别是用多个工具对比分析时，你一定要保证它们用的是相同的间隔时间。

一轮采样把应用侧和系统侧放在同一个时间窗里，工具之间对齐间隔：

mpstat 的每核输出比 all 那一行有用得多：all 显示 iowait 18%、idle 50%，看着还算宽松；拆到每核，0 号核 us 84% 接近打满，1 号核 iowait 71% 卡在等 I/O。两台机器同样的 all 数字，问题可以完全相反。pidstat 的 %wait 补上另一维——进程有多少时间耗在就绪队列等 CPU，这一列高，说明排队已经落到进程头上。

负载的误读

  1. **把 4.2 读成 CPU 用了 420%**。负载数的是进程个数，百分比是另一套算法，4 核机器上 4.2 只说明队列略超核数。
  2. 只盯 1 分钟值下判断。1 分钟 4.20、15 分钟 2.11 是在涨，1 分钟 2.11、15 分钟 4.20 是在退；同一个数含义相反。
  3. 系统 CPU 高就挨个查进程。有进程短命，top 两次刷新之间它已经退出，进程列表翻遍也对不上 80% 的 us。课程案例里系统 us 80%，所有进程加起来才 21%，元凶是 php-fpm 反复 fork 的 stress。
  4. 拿不同间隔的工具输出直接比。top 默认按几秒刷新，ps 报的是进程整个生命周期，两个工具的 %CPU 对不上很正常，先对齐采样窗口再谈差异。
  5. 看 all 那一行就收工。每核分布被平均值抹平，一个核跑满、一个核在等 I/O，all 行可能看起来波澜不惊。

短时进程这类问题，先用 pstree 看父子关系，确认是谁在反复拉起子进程；再上 execsnoop 盯 exec 调用，它按事件抓，不会像 top 那样漏掉活了几毫秒的进程。perf record 采样能做最后确认——图里 stress 占了 77% 的 CPU 时钟，热点落在随机数生成上，和 top 里「找不到进程」是同一件事的两面。

什么情况不必这么做 原因 替代做法
负载长期低于核数一半、P99 稳定 队列没形成，拆指标的成本收不回 只保留负载趋势告警
单核嵌入式或单容器限流到 1 核 核数尺子失效，负载 1.0 就是满载 直接看该核使用率与运行队列
离线批处理，关心总耗时 进程排队是常态，分位和使用率不对应体验 记作业时长与失败率
瓶颈已确认在下游数据库 本机指标再细也改不动外部依赖 看调用链耗时占比
采样间隔短于进程存活时间 短时进程必漏，统计不可信 换 execsnoop 这类事件型工具

负载与使用率四格

把两个指标摆成四格，先定位再动手：

负载 CPU 使用率 读数 下一步
高 高 算力吃紧或一堆进程抢核 mpstat 看每核，pidstat 看 %wait
高 低 进程多半卡在 D 状态等 I/O 看 iowait、块设备 await
低 高 少数核被打满，平均值被摊薄 mpstat -P ALL 逐核看
低 低 本机没压力，问题可能在别处 查应用分段耗时与下游

本篇那组数据落在第二格：负载 4.2、使用率 30%、每核显示 1 号核 iowait 71%。方向随即从「CPU 不够」转成「等什么」。这个转向不需要动任何配置，只靠把两个指标的口径分开、再逐核拆一层。

小结与参考

平均负载数 R 和 D 状态的进程数，CPU 使用率算算力花掉的比例，两者从来不是同一个数。4 核机器上负载 4.2 配 30% 使用率，说明队列在涨而算力有余量，等待发生在别处；逐核拆开 mpstat、看 pidstat 的 %wait，把「等什么」收窄到几条假设上。遇到系统 CPU 高却找不到进程，别在进程列表里死磕，pstree 和 execsnoop 顺着父子关系追，perf 采样再做确认。
