Linux 性能（三）上下文切换与进程状态

发表于 2023-07-30 分类于 性能优化
本文字数： 6.1k 阅读时长 ≈ 6 分钟

引言

压测加到 3000 QPS，P99 从 40 毫秒涨到 800 毫秒，CPU 使用率却只有 30%。上一节把 load 4.2 读成「有进程在排队」，这节往下追一层：排队的进程在等什么。答案通常落在两处，一是上下文切换把 CPU 时间耗在保存和恢复现场上，二是进程卡在 D 状态等 I/O 返回，或者退出后没人回收变成僵尸。这两类问题的排查入口完全不同，混着看容易把方向带偏。

CPU 上下文切换

先把计量单位说清楚。CPU 要运行一个任务，得知道它从哪里加载、从哪里开始执行，这些信息放在一组寄存器和程序计数器（PC）里，合起来叫 CPU 上下文。

切换的过程是：把当前任务的寄存器和 PC 存进内核，再把下一个任务存的那份装回来，最后跳到新的 PC 继续跑。存和装都要内核在 CPU 上执行指令，这段时间是真实花掉的，任务本身没往前推进。一次切换几十纳秒到几微秒，看着不起眼，每秒几万次就成了一笔可观的开销。

任务不止进程这一种，切换也分三种。进程切换要换虚拟内存、栈、全局变量，连内核栈和寄存器一起换，代价最大；同进程的线程切换共享虚拟内存，只换栈和寄存器，便宜一些；中断切换只动内核态那点现场，连用户态都不碰，最轻。中断处理优先级比进程高，同一个 CPU 上不会和进程切换同时发生。

系统调用容易和进程切换搞混。调用 read 时，用户态的指令位置先存起来，寄存器换成内核态的入口，返回时再换回来，一次调用走两遍这个过程。但自始至终是同一个进程，虚拟内存没换，所以严格说这叫特权模式切换。它确实改了寄存器，只是不算进程上下文切换。

进程为什么能在两种状态间来回切，靠的是特权等级：内核跑在 Ring 0 能访问所有资源，应用跑在 Ring 3，想碰硬件就得通过系统调用陷进内核。

进程什么时候会被换下 CPU：时间片用完、等资源（比如内存不够）、主动 sleep、来了更高优先级的进程、硬件中断打断。这五种场景里，只有第一种和第四种属于被强制调度，其余是进程自己让出或者外部事件插入。记住这个区分，下面看自愿和非自愿两列时才有依据。

vmstat 命令分析上下文切换

系统整体每秒切多少次，看 vmstat 的 cs 列；每秒中断多少次，看 in 列；r 是就绪队列长度，b 是不可中断状态的进程数。这四个数放在一行里，能先圈定大问题在哪。

单看 cs 的总数不够，得知道切换是自愿的还是被强制的。pidstat 加 -w 给出每个进程的两列：cswch/s 是自愿切换，进程拿不到需要的资源主动让出，常见于 I/O 或内存不足；nvcswch/s 是非自愿切换，时间片到了或者被更高优先级的任务挤掉，本质是进程在抢 CPU。

线程这一层必须单独查。Linux 调度的基本单位是线程，vmstat 记的是全机总量，pidstat 默认只显示进程汇总——进程自己的计数可能很小，子线程却已经切了十几万次。加 -t 之后 TGID 是进程、TID 是线程，真正的热点通常藏在 TID 那几行。

这组数里 sy 84%、r 到 8、cs 从空闲时的 35 冲到 139 万，CPU 大部分时间花在内核态的调度上。pidstat 按进程看只看到 sysbench 占满一个核，切换加起来几百次，和 vmstat 对不上；展开到线程才发现单个 sysbench 子线程的非自愿切换过了十万。拿 4 核机器的锚点数据套这个模式：CPU 只有 30% 而队列还在涨，非自愿切换多半是主要来源，方向上应该去查谁在开这么多线程，而不是看哪个进程的 us 高。

cs 多少算高没有统一线。稳定在几百到一万以内通常没事，超过一万，或者比自己的常态高出一个数量级，才值得往下拆。绝对值受 CPU 性能影响，拿别的机器的阈值套自己的业务没有意义。

D 状态与僵尸进程

iowait 升高时，去 top 或 ps 里看 S 列，通常能翻出一批 D 状态的进程。D 是不可中断睡眠，进程正在和硬件打交道，交互没结束前不能被打断——磁盘数据和进程里的数据得保持一致，所以内核不许别人插手。短时间的 D 状态正常，持续出现就说明硬件响应慢了。

另外几个状态也要认得：R 是正在跑或在就绪队列里等 CPU；S 是可中断睡眠，等某个事件，事件来了就回 R；I 是空闲的内核线程，和 D 长得像但不计入负载；Z 是僵尸，进程已经退出，父进程还没回收它的 PID 和描述符；T 是被信号暂停；X 是已经消亡，列表里看不到。只有 R 和 D 计进平均负载，I 不计。

僵尸的成因很具体：子进程退出时给父进程发 SIGCHLD，父进程该调 wait() 或 waitpid() 回收，或者注册信号处理函数异步回收。父进程没做，或者子进程退得太快父进程没赶上，子进程就一直挂在 Z 状态。少量僵尸很快会被回收，数量一直涨就会耗尽 PID，新进程创建不出来。

切换升高的误判

  1. 只看 pidstat 的进程汇总就下结论。默认不带 -t，线程级切换全被吃掉，vmstat 报 139 万、pidstat 加起来几百，两边对不上就怀疑工具。先加 -t 再比。
  2. 把 %wait 和 iowait 当成一回事。pidstat 的 %wait 是进程等 CPU 的时间占比，top 的 wa 是 CPU 等 I/O 的时间占比。等 CPU 的进程在就绪队列里是 R 状态，等 I/O 的是 D 状态，两个指标各算各的。
  3. 看到 D 状态就判定磁盘瓶颈。D 只说明在等硬件响应，可能是磁盘、网络存储，也可能硬件本身没问题只是请求太多。先用 dstat 看 read/write 和 wai 是否同步，再谈瓶颈。
  4. 只盯 top 里那几个 D 状态 PID 查 I/O。D 状态随时在换人，案例里 top 显示的 4344、4345 一个字节都没读，真正读盘的是后来的 6080、6081。放开到全部进程再看一轮。
  5. cs 过万就减线程。非自愿切换高说明在抢 CPU，减并发可能有用；自愿切换高说明在等资源，瓶颈在 I/O 或内存，减线程解决不了。先分清两列再动手。

不是所有切换升高都要追。离线批处理本来就是一堆短任务在抢核，cs 高是常态；单核机器上不产生 RES 重调度中断，拿多核的中断现象去套只会白查；进程已经退出变成僵尸，再上 strace 也追不到系统调用，先 pstree 找父进程。

本篇锚点那组数落在第一行：CPU 30% 配高队列，cs 和 sy 是首要怀疑对象。先展开线程级切换确认是不是抢 CPU，再决定是减并发还是查 I/O——顺序反过来，改的东西就多半留在机器上没用了。

小结与参考

上下文切换分进程、线程、中断三种，按保存现场的多少排代价。vmstat 的 cs 看总量，pidstat -w 的 cswch 和 nvcswch 分清自愿与非自愿，加 -t 才能看到线程级热点——进程汇总和总量对不上时，缺的往往就是这一层。D 状态进程在等硬件响应，Z 状态进程在等父进程回收，两者都计进 top 的观察项但不都计进负载；iowait 高先用 dstat 对齐读写，再用 pidstat -d 放开到全部进程找元凶，进程已退出的改用 perf 追调用栈，僵尸用 pstree 顺藤摸瓜找父进程。
