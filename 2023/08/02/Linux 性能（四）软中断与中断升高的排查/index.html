Linux 性能（四）软中断与中断升高的排查

发表于 2023-08-02 分类于 性能优化
本文字数： 4.7k 阅读时长 ≈ 4 分钟

引言

压测加到 3000 QPS，CPU 使用率停在 30%，P99 却是 800 毫秒。还有一类更极端的情况：top 里每个 CPU 都不高，si 那一列却很扎眼，进程列表翻遍了也找不到吃 CPU 的应用。这多半和收包有关——数据从网卡进来，协议栈逐层解析这项工作记在软中断名下，看着像系统忙，其实是包来得太碎。这篇用一个 Nginx 收小包的例子，把从 si 升高走到具体来源的路径过一遍。

硬中断与软中断

中断是系统响应硬件请求的方式，硬件有事就打断当前进程，转去执行中断处理程序。它要解决一对矛盾：处理程序要快，因为运行期间会临时关中断，拖太久，后来的中断就丢了；可有些活本身就不轻，比如网络包收进来之后要逐层解析。

Linux 的办法是拆成两段。上半部对应硬中断，在关中断模式下跑，只做最要紧的事：把网卡里的数据读进内存、更新硬件寄存器状态，然后发一个软中断信号就退出，整个过程很短。下半部对应软中断，接着做上半部没做完的解析工作，以内核线程的方式运行，每个 CPU 都对应一个，名字是 ksoftirqd 加 CPU 编号。这样网卡处理事情时，别的中断还能进来。

flowchart LR
    A["网卡收到数据包"] --> B["硬中断 上半部"]
    B --> B1["数据读到内存"]
    B --> B2["更新硬件寄存器"]
    B --> B3["触发软中断"]
    B3 --> C["软中断 下半部 ksoftirqd"]
    C --> C1["按协议栈逐层解析"]
    C1 --> C2["送到应用程序"]

软中断不只是网络收发的下半部，内核调度、定时器、RCU 锁这些自定义事件也算。它的执行有两个时机：硬中断返回前顺带处理一批，遗留的交给 ksoftirqd 线程接着跑。所以软中断占的 CPU 记在系统态的 si 列，落到进程头上是内核线程，不是业务进程——这就是为什么 si 很高时，进程列表里翻不到一个吃 CPU 的应用。

看系统里有哪些软中断，用 /proc/softirqs；想看硬中断，用 /proc/interrupts。软中断线程可以在进程列表里找到，名字带中括号的通常是内核线程，拿不到命令行参数。

NET_RX 升高的排查链

实验用两台虚拟机，一台跑 Nginx 当服务端，另一台发压，彼此隔开避免互相干扰。

客户端用 hping3 以每隔 100 微秒一个包的节奏往 80 端口发 SYN，压测开始。

回到服务端，这时连敲几个回车都要等很久。先看整体资源。

load 全是 0，就绪队列只有一个进程，CPU 使用率最高的也没超过 5%，进程列表里居首的是 ksoftirqd。既然 CPU 时间主要花在 si 上，下一步要弄清是哪一类软中断。/proc/softirqs 给的是开机以来的累计次数，单次读数看不出快慢，得看它涨的速度——用 watch -d 把变化的部分高亮出来。

高亮里 TIMER、NET_RX、SCHED、RCU 都在涨，其中 NET_RX 涨得最快。定时、调度、RCU 这些是内核正常运转的底噪，网络接收这一项冒尖，方向就落到收包上。顺着这条线查网卡收发。

eth0 每秒收 12607 个包，收进来的数据量只有 664 KB，算下来平均每包 54 字节——满屏都是小包。包小之所以费 CPU，是因为每收一个包都要从头走一遍协议栈：校验、查路由、送到 socket，这些固定步骤按包收，不按字节收。同样 664 KB 的数据，装成几百字节的大包可能只要一千多次，拆成 54 字节的小包就得上万次，每次都要占一段软中断时间。包越碎，同样的流量吃掉的 CPU 越多。抓包看这些小包是什么、从哪来。

Flags [S] 是 SYN，源地址集中在一个 IP，配合两万上下的 PPS， SYN FLOOD 就对上了。整条链从 si 高出发，靠变化速率锁定 NET_RX，再用 PPS 和包长判断形态，最后抓包确认来源。

flowchart TD
    A["终端响应变慢"] --> B["top: si 高, 无吃 CPU 的进程"]
    B --> C["watch -d /proc/softirqs"]
    C --> D{"哪类软中断涨最快"}
    D -->|"NET_RX"| E["sar -n DEV 看 PPS 与 BPS"]
    E --> F{"平均包长很小"}
    F -->|"54 字节"| G["tcpdump 抓包"]
    G --> H["Flags S 为 SYN"]
    H --> I["确认 SYN FLOOD, 从源头封 IP"]

softirqs、sar 与 tcpdump

这三个工具各管一段，分开看清楚界限，排查时才不会用错。

/proc/softirqs 回答「哪一类」。第一列是软中断类型，NET_RX 是网络接收、NET_TX 是发送，TIMER、SCHED、RCU 分别对应定时、调度和锁。后面每列是一个 CPU 上的累计次数，同一类型在各 CPU 上应该是一个量级。TASKLET 是例外，它只在调用它的那个 CPU 上运行，分布不均是它的机制使然，不必当成异常。

sar -n DEV 回答「收了多少、包多大」。rxpck/s 和 txpck/s 是每秒收发的网络帧数，也就是 PPS；rxkB/s 和 txkB/s 是每秒收发的字节数，也就是 BPS。两个一除就是平均包长，这个小包判断就是这么来的。网桥转发的 docker0、veth 网卡数据和 eth0 对称，那是包转给容器的路径，不用当独立问题看。

tcpdump 回答「包是什么、谁发的」。-i 指定网卡，-n 不解析主机名，tcp port 80 把范围收窄到目标端口。Flags [S] 是 SYN，Flags [S.] 是 SYN 加 ACK，看到清一色的 SYN 又没有后续握手，就要往连接耗尽的方向想。

软中断升高的误判

软中断高只说明 CPU 时间在内核的异步处理上，具体是什么把软中断顶上去的，还得往下查。几种常见的走偏：

  1. 看到 si 高就去加 CPU。软中断占用的是收包和解析的时间，算力加一倍，包还在照样收，缓解有限。
  2. 拿 /proc/softirqs 的单次读数当结论。那是开机累计值，跑得久的机器上每个类型都很大，不看变化率分不出谁是当下的热点。
  3. 看见 NET_RX 高就直接改网卡参数。队列、缓冲区怎么调，取决于收的是正常小包流量还是攻击流量，来源没确认就动手，改完很难说清有没有用。
  4. 只看一个 CPU 的 si。软中断是按核分的，TASKLET 又只在单核跑，平均下来不高、单核被打满的情况并不少见，要看每个核。
  5. 把 SYN FLOOD 当普通流量调优。拥塞控制和超时调参解决不了伪造源地址的半连接洪泛，这种得在交换机或防火墙上按来源拦截。

也有不适用的时候：si 在整体 CPU 里占比很小、软中断类型里没有哪一项明显冒尖，这时软中断不是主线，回到 CPU 使用率或 I/O 等待那条路重查。反过来，NET_RX 冒尖但包长正常、来源分散，多半是真实流量涨了，该看的是容量而不是攻击。

软中断类型速查表

现象 关键读数 含义 下一步
si 高、进程无热点 top 里 si 占大头 CPU 时间在软中断 查 /proc/softirqs 变化率
NET_RX 涨最快 watch 高亮集中在 NET_RX 网络收包是热点 sar -n DEV 看 PPS 与包长
PPS 高、包长小 每秒上万帧、每包几十字节 小包洪泛 tcpdump 抓包看来源与标志位
Flags [S] 成片 源地址集中、无后续握手 SYN FLOOD 从交换机或防火墙封来源
NET_TX 涨得快 发送方向的 PPS 冒尖 发包是热点 查对端接收与本机发送队列
TASKLET 分布不均 单核 TASKLET 明显偏高 仅在调用它的 CPU 运行 机制使然，先不当异常

本篇开头那组数落在第一行：CPU 30% 配高延迟、进程列表又没有热点，si 值得查。真查下去，是 NET_RX 在涨、包又碎，才一步步走到小包和 SYN FLOOD——顺序反过来，一上来就调内核参数，多半调不到点子上。

小结与参考

中断分上半部和下半部：上半部是硬中断，关中断模式下快速处理硬件请求；下半部是软中断，由 ksoftirqd 内核线程接着做解析这类耗时工作。软中断 CPU 使用率升高，生产里最常见的是网络接收型，排查按「si 高 → /proc/softirqs 看变化率定类型 → sar -n DEV 看 PPS 和包长 → tcpdump 抓包定来源」这条链走。/proc/softirqs 是累计值，得看变化率；软中断按核分配，别只看一个 CPU；定位到 SYN FLOOD 后，处置要从源头拦截，调本机参数解决不了。
