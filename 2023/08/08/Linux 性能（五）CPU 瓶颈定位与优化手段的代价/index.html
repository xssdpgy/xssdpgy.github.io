Linux 性能（五）CPU 瓶颈定位与优化手段的代价

发表于 2023-08-08 分类于 性能优化
本文字数： 3.8k 阅读时长 ≈ 3 分钟

引言

前面几节按资源类型把 CPU 的坑挨个踩过：负载、上下文切换、软中断、找不到进程的短时进程。真到线上，指标和工具摆一屏，先跑哪个、看到什么往哪走，往往就卡在这儿。这篇把前面散落的判断收成一条路径：哪三个命令能覆盖大部分指标、指标之间怎么互相印证、找到瓶颈后又该怎么权衡优化手段。后半段落到 perf 这一层——符号丢了怎么办、Java 栈为什么看不到，以及绑核、优先级这些手段各自的代价。

CPU 指标的分类

先把要看的东西分个类。CPU 性能口径说到底就四组：使用率、上下文切换、平均负载、缓存命中率。使用率再往下拆成用户态、系统态、等待 I/O、软中断和硬中断，虚拟化环境里还有窃取和客户两类。

这些口径不是并列的孤立项，各自指向不同的层。用户 CPU 高，说明应用在用户态忙着算；系统 CPU 高，是内核态的事，比如频繁系统调用；iowait 高，CPU 其实在等硬件返回。把它们分开看，排查范围一下就缩小了——用户 CPU 高就别往内核态翻，iowait 高就别只盯进程列表。平均负载数的那三个值，是过去 1、5、15 分钟的平均活跃进程数，理想情况跟逻辑 CPU 个数相等。缓存命中率衡量的是 CPU 多级缓存的复用情况，L1、L2 在单核，L3 多核共享，命中率越低，CPU 等内存的时间越多。

三工具的指标关联

指标知道怎么看，接下来是拿什么看。工具很多，真正常用的就那么几个，其中 top、vmstat、pidstat 三个覆盖面最广：top 给出各种使用率和僵尸进程、平均负载，vmstat 给出上下文切换次数、中断次数和运行/不可中断进程数，pidstat 补上进程级的用户 CPU、系统 CPU 和两类切换。

这张图更该当成一张路线图来读。虚线是指标之间的关联，也是下一步的方向。top 的用户 CPU 升高，就拿 pidstat 按进程对齐，找出是哪个进程在占；找到进程后再用 perf 看调用链、strace 看系统调用。top 的平均负载升高，对照 vmstat 的运行态和不可中断进程数：不可中断那一列涨了，转去查 I/O，用 dstat、sar；运行态那一列涨了，回到 top 和 pidstat 找进程。top 的软中断高，查 /proc/softirqs 定类型，是网络接收就接 sar 和 tcpdump。

flowchart TD
    A["top: CPU 使用率 / 负载 / 僵尸"] --> B{哪一类异常}
    B -->|"用户 CPU 高"| C["pidstat 按进程对齐"]
    B -->|"系统 CPU 高"| D["strace 看系统调用"]
    B -->|"iowait 高"| E["vmstat 看不可中断进程数"]
    B -->|"软中断高"| F["/proc/softirqs 定类型"]
    C --> G["perf 看调用链"]
    E --> H["dstat / sar 查 I/O"]
    F --> I["sar / tcpdump 查网络"]

思路是先用覆盖面广的工具把范围圈小，再换专门工具往下钻，而不是一上来十几个工具全跑一遍。前者快，后者既慢又容易在数字里漏掉关键的一项。

perf 采样与符号表

范围缩到某个进程后，perf 用来看它的调用链。常规做法是采样加报告两步：先 record 一段时间，再 report 展开。

真正卡人的是符号。perf 界面里只看到一串十六进制地址而不是函数名，界面末行通常会有一句 Failed to open ... continuing without symbols，意思是找不到进程的依赖库。跑在容器里的应用最容易碰上，库和符号都在镜像里，宿主机上按路径找不到。

解决办法有几种，代价差别很大。在容器外照原路径补一套依赖库，能行，但要污染宿主机环境；进容器跑 perf，需要特权模式，生产里的普通容器通常给不了；把容器文件系统挂出来，用 --symfs 指过去，可行但要额外装工具。相对省事的是在宿主采样、把 perf.data 拷进容器，在容器里装 perf 再看报告。

Java 应用另有一层麻烦。脚本跑在 JVM 上，系统调用栈拿到的是 JVM 的函数，看不到 Java 方法。perf 本身支持 JIT，但要有一份 /tmp/perf-PID.map 做符号翻译，通常由 perf-map-agent 生成，还得给 JVM 加 -XX:+PreserveFramePointer 保留帧指针。这一层配起来不轻，比普通进程的问题多出好几步。

还有两个常被误读的地方。perf report 里 swapper 占九成多，看着吓人，它其实是系统的空闲任务，CPU 没别的活跑时才轮到它，可以直接略过；真正要看的是占比很小的应用符号。另外调用栈默认有个 0.5% 的显示阈值，占比 0.34% 的 app 展开就是空的，把阈值调低才有栈。

优化手段的适用条件

找到瓶颈之后，先别急着动手。优化前想清楚三件事：拿什么指标证明优化有效、同时冒出几个问题先动哪个、多种方法里选哪种。评估要跨应用和系统两个维度——应用看吞吐和延迟，系统看 CPU 使用率，只盯一边容易误判。多个问题并存时，先动变化幅度最大、又是因不是果的那个；系统资源已经打满的，优先处理资源本身。

选方法的关键是先算代价。绑核把进程固定在几个 CPU 上，能提高缓存命中、减少跨核调度，前提是有核可绑；CPU 核数本来就少，绑完反而限制了调度余地。优先级用 nice 调整，把非核心应用压低、核心应用抬高，前提是分得清主次。cgroups 限额能挡住某个应用吃光资源，代价是配置和维护跟着增加。DPDK 绕开内核协议栈换吞吐，但要独占一个核加大页内存、始终跑满，核少时得不偿失。

flowchart LR
    A["找出瓶颈"] --> B["量化前后指标"]
    B --> C{"多个问题并存"}
    C -->|"是"| D["先动变化幅度最大且为因的那个"]
    C -->|"否"| E{"多种方法可选"}
    D --> E
    E --> F["按代价与适用条件筛选"]
    F --> G["小步优化后重新评估"]

这些手段有个共同前提：确认了瓶颈再上。没有瓶颈就把优化一股脑堆上去，复杂度先涨上来，可维护性往下降，需求一变，这些优化反而挡路。

CPU 定位与优化速查表

现象 关键读数 下一步工具 优化方向与代价
用户 CPU 高 top user 占大头 pidstat 找进程、perf 看调用链 改算法与循环，代价在改动量
系统 CPU 高 top sy 占大头 strace 看系统调用 减少系统调用与切换，代价在重构
iowait 高 wa 高、不可中断进程多 dstat、sar 查磁盘 缓存 I/O 换直接 I/O，代价在语义变化
软中断高 si 高 /proc/softirqs 定类型 按类型优化，网络类看包长与来源
符号只有地址 perf 报告无函数名 –symfs 或容器内看报告 保留符号表，代价是二进制变大
Java 栈看不到 只有 JVM 函数 perf-map-agent 生成 map 加帧指针选项，代价是额外工具链

本篇锚点那组数——CPU 30%、P99 800ms——落在「使用率不高但延迟高」这一格。按路线图，先看 user 和 sy 谁高、iowait 与 si 有没有冒尖，再决定往进程、I/O 还是网络走；确认瓶颈之后再谈绑核还是调优先级，顺序反了，参数就会一直留在机器上却说不清有没有用。

小结与参考

CPU 指标分使用率、上下文切换、平均负载、缓存命中率四类，彼此靠原理关联。排查用 top、vmstat、pidstat 圈定范围，再换 perf、strace、dstat、tcpdump 往专项里钻，比一上来全跑一遍更快。perf 采样后看不到函数名，多半是符号路径不对，容器应用尤其如此；Java 栈还要额外生成符号表并保留帧指针；报告里占比高的 swapper 是空闲任务，可以先略过。优化按「量化前后指标 → 挑影响最大的问题 → 按代价选方法」三步走，绑核、独占、优先级、DPDK 都有各自的前提，核数少、主次不清时收益会被代价吃掉。
