Linux 性能（十）网络协议栈与性能评估

发表于 2023-08-30 分类于 性能优化
本文字数： 4.7k 阅读时长 ≈ 4 分钟

引言

网络慢经常被直接归到带宽不够，但同一台 4 核 8G 机器、同一块千兆网卡，压测从 300 QPS 提到 3000 QPS 后，P99 从 40 毫秒涨到 800 毫秒，CPU 只有三成。这时带宽灯没亮，延迟照样涨，原因可能在队列、缓冲区、连接模型，也可能在压测工具本身。这篇把收发路径、指标口径和分层基准放到一起，说明 C10K 到 C10M 各卡在哪一层，以及测出来的数该怎么读。

网络栈的四层结构

日常说的二层、三层、四层、七层来自 OSI 七层模型，Linux 实际实现的是更实用的 TCP/IP 四层：应用层放 HTTP、DNS 这类协议，传输层管端到端通信，网络层负责封装、寻址和路由，网络接口层处理 MAC 寻址与网卡收发。谈到七层负载均衡时，指的是 OSI 的应用层；落到协议栈上，它对应 TCP/IP 的应用层。

Linux 网络栈分层结构

应用数据向下走时，每层只在前后加上固定格式的头尾：传输层加 TCP 头，网络层加 IP 头，网络接口层加帧头和帧尾，原始负载本身不改。链路能传的帧有上限，MTU 规定了 IP 包的最大尺寸，以太网默认 1500 字节。超过这个尺寸就要在网络层分片，分片越多，收发两端的重组开销越大。调 MTU 之前先看路径上有没有叠加网络，端到端任何一段不支持，调了也白调。

收发过程中涉及三类缓冲区，位置容易搞混。网卡通过 DMA 交互的环形缓冲区由网卡驱动管理；网卡中断处理程序分配 sk_buff 承载网络帧，各层之间传递时只改指针，不反复复制数据；套接字缓冲区由应用按连接设置大小，发送数据是往里写，接收数据是从里读。这些缓冲区都在内核管理的内存里，sk_buff、连接跟踪等通过 slab 分配器管理，可以在 /proc/slabinfo 看占用。

网络包的处理跨了硬中断和软中断：网卡硬中断只做最核心的读取或发送，协议栈的大部分逻辑留给软中断。每个 CPU 绑一个 ksoftirqd 线程处理软中断，硬中断、kworker 等机制一起配合，看到某个 CPU 的软中断占用高，先查网络收发是否集中在那一核。

网络包接收与发送时的逐层封装

千兆网卡的基准量级

接收方向：网卡把帧 DMA 到收包队列，硬中断触发后分配 sk_buff，再用软中断通知内核；链路层验合法性、认出上层协议并去掉帧头，网络层判断转发还是本机接收，传输层按源 IP、源端口、目的 IP、目的端口四元组找到套接字，把数据放进接收缓存，应用才读得到。发送方向反过来：sendmsg 进入套接字层，写入发送缓冲，逐层加头、查路由、按 MTU 分片，网络接口层找到下一跳 MAC 并加上帧头帧尾放进发包队列，软中断通知驱动，驱动用 DMA 发出去。

把量级摊开看，C10K 指的是单机一万并发连接。按 2GB 内存、千兆网卡的老配置算，每连接只要低于 200KB 内存和 100Kbit 带宽，物理资源就够，卡点在同步阻塞模型：一请求一线程，一万个线程的调度和上下文切换先撑不住。I/O 多路复用让一个线程盯一批套接字，select 和 poll 需要轮询描述符集合，还要在用户态和内核态之间来回拷贝；epoll 在内核里用红黑树管理描述符，只处理有事件的那些，轮询的开销省掉了。

有了多路复用，还要定工作模型。主进程初始化套接字、管理子进程，worker 进程各自处理请求，这是反向代理常见的结构；多个 worker 同时等待同一个事件会惊群，需要锁或独占选项来约束。另一种是多个进程各监听同一端口，由内核分发连接，少了应用侧抢锁这一步。

主进程加多个 worker 的请求处理模型

从 C10K 到十万并发，多数情况加物理资源、沿用多路复用就能过。到一百万并发，账就变了：每个连接 16KB 内存意味着约 15GB；按两成连接活跃、每连接每秒 1KB 算，吞吐量要 1.6Gb/s，千兆网卡接不住。文件描述符数量、连接跟踪、协议栈缓存、多队列网卡、软中断负载均衡、TSO/GRO 这类卸载都要一起考虑。再往上到千万并发，协议栈路径本身成了负担，DPDK 跳过内核协议栈在用户态轮询收包，XDP 在包进协议栈之前处理；更多场景直接把请求分摊到多台机器，改动比单机极限优化小得多。

ip 与 sar 的观测

先看接口配置和收发统计。ip -s 比 ifconfig 给的信息更细，LOWER_UP 表示物理链路连通，mtu 是最大传输单元，RX/TX 下的 errors、dropped、overruns、carrier 只要非零，就说明链路上有丢包或错误，得先定位这一层。

再看套接字和协议栈。监听状态（LISTEN）下 Recv-Q 显示当前半连接队列长度，Send-Q 是它的上限；已连接状态下两者分别对应未被应用取走的字节数和未被对端确认的字节数。队列持续非零，说明包在堆积。netstat -s 里的重传段数、ss -s 的连接汇总，用来判断是握手阶段的问题还是传输阶段的问题。

%ifutil 是接口使用率，全双工下按收发两个方向里较大的那个算。它跟吞吐量各有用途：吞吐量要用 sar 的 rxkB/s、txkB/s 或 ethtool 查到的链路速率换算，PPS 看 rxpck/s、txpck/s。小包转发看 PPS 更准，大文件传输看吞吐更准，Web 服务最终还是要看 QPS 和延迟分布。

基准测试要按层选工具。网络层和接口层看 PPS，可以把 pktgen 模块加载后通过 /proc/net/pktgen 配置发包，构造 64 字节小包测转发上限；传输层用 iperf 跑 TCP 吞吐，一端起服务端、另一端起客户端；应用层用 wrk 或压测脚本带真实请求负载，避免工具先成为瓶颈。

同一台机器，ab 跑静态页面可能只有一千多请求每秒，换成带 Lua 脚本的 wrk 能到九千多。差距来自工具能发出的负载：ab 没带真实请求体，wrk 按脚本构造。测出来的低值如果来自工具，拿它当容量规划基线会得出偏小的结论。

带宽与吞吐的混淆

Speed: 1000Mb/s 是链路标称值，实际吞吐要看协议开销、包大小、最窄一跳和压测工具，拿标称值减去一点余量当上限，基线从一开始就偏了。几种常见的走偏：

  1. 只盯带宽。小包场景 IOPS 思路不适用，该看 PPS；大流场景才看吞吐。两个指标混用，测得的数没法横向比。
  2. 端口数当成连接上限。16 位端口号确实只有 65535 个，这是单个客户端 IP 发起连接时的限制；服务端按五元组区分连接，可接的数量大得多，实际受资源和协议栈性能约束。
  3. 看到队列非零就加缓冲。缓冲区调大能吸收突发，也会拉长排队时间，P99 跟着上去；先把堆积来源查清楚。
  4. 直接进入百万并发优化。连接数离目标还远时，多队列网卡、中断绑定、卸载这些改动带来的复杂度，多半换不来可测的收益。
现象 该查什么 先不必做什么
延迟涨、CPU 闲 接口丢包计数、重传、队列堆积 直接判定带宽不足
吞吐到不了标称值 包大小、对端速率、压测工具上限 按标称值算容量
单个 CPU 软中断高 网卡队列与 CPU 绑定关系 无差别调高缓冲区
连接数上不去 文件描述符限制、半连接队列、端口占用 立刻上 DPDK 或 XDP
压测结果偏低 工具本身能发出的并发与负载 直接改应用代码

层次 核心指标 观测或测试工具 读数要点
接口 收发速率、错误、丢包 ip -s、sar -n DEV 错误与丢弃非零先查链路
网络层 PPS、转发能力 pktgen、hping3 64 字节小包贴近转发上限
传输层 TCP 吞吐、重传 iperf、netstat -s 吞吐对比标称值要留余量

本篇锚点那组 P99 800 毫秒、CPU 三成的结果，落到这张表上依次核对：接口有没有丢包，重传有没有涨，队列有没有堆，压测工具自身能不能发出目标并发。四层读数都正常，再往应用逻辑里查。按这个顺序走，网络这一层能不能排除才有依据。

小结与参考

Linux 网络按 TCP/IP 四层实现，数据在每层加头加尾，超过 MTU 就分片；收发的环形缓冲区、sk_buff 和套接字缓冲区都在内核管理的内存里，硬中断只做核心动作，大部分处理落在软中断。千兆网卡下 C10K 的瓶颈在同步阻塞模型，多路复用和合适的工作模型能解决；到百万并发要连内存、带宽、文件描述符、连接跟踪和中断卸载一起算；到千万级才需要绕过协议栈。评估时按接口、网络层、传输层、应用层逐层取基准，带宽、吞吐、PPS、QPS 各管一段，别拿标称值或压测工具的上限当系统能力。
