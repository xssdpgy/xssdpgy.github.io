Linux 性能（七）内存泄漏、Swap 与回收机制

发表于 2023-08-15 分类于 性能优化
本文字数： 4.2k 阅读时长 ≈ 4 分钟

引言

内存这一层有两种常见的坏法：一是分配了不释放，物理内存被一点点吃光；二是内存紧张时系统开始回收，把匿名页换到 Swap，换出换入都走磁盘，延迟跟着抖。这两种问题的现象都能落到本篇锚点上——CPU 三成、P99 却到 800 毫秒——但成因和查法完全不同。这篇先分清可回收的文件页和只能换出的匿名页，再用 memleak 和 Swap 两个案例走一遍从「内存在涨」到「是谁在涨、换出了谁」的路径，最后交代关 Swap、调 swappiness 这些手段各自的前提。

匿名页与文件页

内存回收要分两类页面。缓存和缓冲区属于文件页（File-backed Page），大部分可以直接清掉，下次需要时从磁盘重读；被改过还没落盘的脏页要先写回磁盘，靠应用调 fsync 或内核线程 pdflush 完成。文件映射页也归这一类，释放后从文件重新读回即可。

应用动态分配的堆内存是匿名页（Anonymous Page），它很可能在下次还被访问，没法直接回收。Swap 就是给这类页面留的后路：把不常访问的匿名页写到磁盘，腾出内存给别人，下次访问时再换入。换出和换入合起来，等于把可用内存临时扩大了。

回收什么时候启动，看剩余内存落在哪个水位。kswapd0 定期扫描，拿剩余内存 pages_free 和三个阈值比：

kswapd 内存回收的三个水位阈值

低于 pages_min，进程可用的内存耗尽，只剩内核能分配；落在 min 和 pages_low 之间，压力偏大，kswapd0 开始回收，直到剩余内存回到 pages_high 以上；落在 low 和 high 之间，有压力但还能满足新请求；高于 high，没有压力。pages_low 和 pages_high 由 min 推导，min 本身通过 /proc/sys/vm/min_free_kbytes 间接设置。

flowchart TD
    A["页分配请求"] --> B{剩余内存与水位比较}
    B -->|"高于 high"| C["无压力 直接分配"]
    B -->|"low 与 high 之间"| D["可分配 轻度压力"]
    B -->|"低于 low"| E["kswapd0 后台回收"]
    B -->|"直接回收也不够"| F["直接回收 + 可能触发 OOM"]
    E --> G["回收文件页 或换出匿名页到 Swap"]

还有一层 NUMA 的影响。多处理器被划到不同 Node，每个 Node 有自己的本地内存和 DMA、NORMAL、MOVABLE 等内存域，水位是按 Node、按 Zone 分别算的。所以会出现整机剩余内存还很多、某个 Node 却开始 Swap 的情况——查水位得按 Node 看，不能只看全局。

NUMA 架构下每 Node 的本地内存与内存域

文件页和匿名页先回收谁，由 /proc/sys/vm/swappiness 决定，取值 0 到 100：数值越大越积极换出匿名页，越小越倾向回收文件页。这个数是权重，不是百分比，设成 0 也不代表绝不 Swap。

从内存增长到泄漏点

内存泄漏的判据是趋势，不是某一刻的占用。用一个每秒算一次斐波那契数的程序做例子：跑起来后盯着 free 那一列，它持续下降，buff/cache 基本不动，说明系统用在别处的内存一直在涨。但这还不能断定是泄漏——程序用一个不断增长的数组缓存结果，也会看到同样的曲线。

要往下走一步，得看分配和释放是否配对。堆内存由应用自己调 free() 回收，共享内存分配后忘了释放，后果和堆泄漏一样；栈内存由系统自动管理，只读段和数据段大小固定，这两类不会泄漏。

memleak 能直接给出未释放内存的调用栈，比拿 top 输出写脚本比对方便。

调用栈指到 fibonacci() 分配的内存没被 child() 释放，回到源码补一个 free() 就修好了。这里有个容器场景的坑：memleak 在容器外跑，看不到容器里的 /app 路径，符号会显示成 [unknown]；把二进制文件从容器里拷到宿主机同路径，栈就能正常解析。

Swap 升高后的证据链

Swap 升高同样要从趋势入手。开启 8 GB 的 Swap 文件后，用一个 dd 读大文件的例子压内存，sar 同时看内存和 Swap 两组指标。

内存使用率从两成多涨到 98%，主要被缓冲区 kbbuffers 占着，Swap 才开始动。缓冲区里是谁，用 cachetop 定位到 dd 进程，命中率五成、未命中四万多页。接下来要回答的是：缓冲区明明是可回收的文件页，为什么系统不去回收它，反而动了匿名页的 Swap？

答案在 /proc/zoneinfo 里。盯着 Normal 域的 pages_free 和三个水位看，会发现 pages_free 在小范围波动：低于 low 就触发回收，回收后跳回 high 以上，dd 继续写又把内存吃回缓存，如此往复。回收时文件页和匿名页都会动，所以缓冲区会缩、Swap 也会涨。用 watch 看这段变化最直观。

最后要找出 Swap 换出的是谁，从每个进程的 /proc/<PID>/status 里读 VmSwap 排序。

Swap 换出的是 dockerd 这类进程的内存，它们再访问时就会慢。整条链从 Swap 升高出发，用 sar 看趋势、cachetop 找缓存来源、zoneinfo 解释回收、VmSwap 定位受影响的进程。

Swap 与泄漏的处理边界

找到来源之后，处置也要讲条件。几种常见的走偏：

  1. 见 Swap 升高就关掉。Swap 升高只是内存紧张的结果，先查是谁在涨、回收为什么不回收文件页；直接关掉，压力会转移到 OOM，核心进程可能被杀。
  2. 把 swappiness 调到 0 当万能解。它是回收倾向的权重，不是开关；剩余内存加文件页低于高水位时，设成 0 照样发生 Swap。
  3. 拿 free 的剩余内存判断能不能分配。可回收缓存也算可用内存，看 available 才接近真实情况。
  4. 用 top 的单次快照断定泄漏。泄漏是趋势，一次快照高低说明不了问题，得用 vmstat 或 sar 看一段时间的曲线。

什么时候不必动 Swap：内存充足、水位长期在 high 以上、swpused 始终为零，这时 Swap 配置本身不影响性能，调它没有收益。反过来，如果延迟敏感的应用跑在开了 Swap 的机器上，又不能关 Swap，可以用 mlock 或 mlockall 锁住它的内存，阻止换出——代价是这部分内存别人也拿不走。

本篇锚点的「CPU 三成、P99 800 毫秒」，在内存这一层对应泄漏或换页两条路径。先 vmstat 看内存是不是持续在涨：涨且 cache 不动查泄漏，Swap 动查回收和受影响进程。确认成因再谈关 Swap、调 swappiness 或锁内存，顺序反了，参数留在机器上却解决不了延迟。

小结与参考

内存回收分文件页和匿名页：文件页可直接回收或写回脏页后回收，匿名页要靠 Swap 换出到磁盘。kswapd0 按 pages_min、low、high 三个水位决定何时回收，水位按 Node 和内存域分别计算，NUMA 下要逐个 Node 看；swappiness 调节回收倾向，是权重不是开关。查泄漏看内存趋势，用 memleak 拿未释放内存的调用栈；查 Swap 用 sar 看趋势、cachetop 找缓存来源、zoneinfo 解释回收、VmSwap 定位受影响进程。关 Swap、调 swappiness、用 mlock 锁内存都有前提，先定位成因再动手。
