Linux 性能（九）I O 瓶颈定位与优化

发表于 2023-08-25 分类于 性能优化
本文字数： 4.2k 阅读时长 ≈ 4 分钟

引言

前面把 I/O 栈和指标口径铺开了，这篇专门走定位与优化。现象还是本篇锚点那组：CPU 三成、P99 从 40 毫秒涨到 800 毫秒，只是这次瓶颈落在磁盘上——应用发出 I/O 后挂起等待，iowait 冒高，算力闲着。I/O 类问题的难处不在工具少，而在几个案例长得很像：都是响应慢、都是 iowait 高，根因却可能是狂打日志、临时文件、慢查询或持久化配置。这篇把「iostat 定瓶颈、pidstat 找进程、strace 和 lsof 定位文件」这条主线走实，再交代 fio 基准与几种优化手段的代价。

await util 与队列深度

判断磁盘有没有瓶颈，先看几个数的含义。%util 是磁盘处理 I/O 的时间占比，超过八成通常就算有瓶颈；r/s + w/s 是 IOPS，rkB/s + wkB/s 是吞吐量，r_await + w_await 是响应时间，aqu-sz 是平均请求队列长度。

这几个数得合起来看。使用率只统计「有没有 I/O」，不管请求多大，所以 %util 到 100% 时磁盘仍可能接受新请求——这个数只描述繁忙时间占比。磁盘何时接不了新请求，要看饱和度；iostat 不直接给饱和度，拿 aqu-sz 或等待时间跟 fio 的基准结果比，才能估出来。

请求大小也关键。数据库、小文件这类随机读写场景，IOPS 更能反映性能；多媒体这类顺序读写场景，吞吐量才更能反映。同样一块盘，4 KB 随机写和 1 MB 顺序写跑出来的 %util 可能都是 99%，但每请求的处理能力和队列深度会差出一大截，脱离读写类型、比例和大小去比较单个指标，很容易得出错的结论。

所以要谈「磁盘够不够快」，先得有个基准值。fio 是最常用的基准测试工具，通过选项组合覆盖各种场景：rw 指定读写模式，read/write 是顺序、randread/randwrite 是随机；bs 设块大小；ioengine 选引擎，libaio 表示异步；direct=1 绕过系统缓存，测的是磁盘本身；filename 指向裸盘或文件，测裸盘会破坏上面的文件系统，事先得备份。

报告里的 IOPS、带宽、延迟分位数，就是这个盘在该场景下的极限。拿它当基线，线上观测到的队列长度和等待时间才有得比——否则「await 7 秒算高吗」这种问题没有答案。同一块盘，换块大小、换随机顺序，测出来的数会差出几倍，基准得贴着应用的真实 I/O 特征来测。

从 iowait 追到写日志线程

看一个狂打日志的例子。应用跑起来后，top 里 CPU0 的 iowait 超过 90%，进程列表里 python 进程 CPU 只有 6%，不算高；内存 8 GB 里缓存占了 6 GB。iowait 高说明 CPU 在等 I/O，方向转到磁盘。

每秒写 64 次、32 MB，写响应 7 秒，队列长度 1100——%util 99% 配合这么长的队列，磁盘已经饱和。下一步用 pidstat -d 找出是谁在写。

python 每秒写 45 MB，是整盘 32 MB 的写出者。有意思的是 jbd2 和 kworker 的 iodelay 更大，但它们是保证文件系统完整性的内核线程，延迟的根源还是那批大量 I/O，顺着 python 往下查就行。用 strace 看它写的是什么。

写的是日志文件，一次写 300 MB。根因是调试日志级别忘了调回去，大量日志把磁盘写满了。另一个相似的案例里，strace 看不到 write——换成 filetop 和 opensnoop 从内核态追踪，才发现应用在读写大量临时文件。工具没有结果时，先怀疑工具用法，别急着下没有 I/O 的结论。

    A["top: iowait 高"] --> B["iostat 定磁盘瓶颈"]
    B --> C["pidstat -d 找 I/O 进程"]

iostat strace 与 lsof

这条链上每个工具管一段，界限清楚才不会用错。

/proc/diskstats 是 iostat 的数据源，按设备给出读写请求数、合并数、读写的字节数和耗时。iostat 把这些原始计数换算成人能读的指标，看整盘够不够用；它回答不了「是谁在读写」，这要 pidstat -d 或 iotop 补——前者给每个进程的读写速率和 iodelay，后者按 I/O 大小排序找大户。

strace 跟踪进程的系统调用，能看到 openat、read、write 作用在哪个文件描述符上；lsof 则把文件描述符还原成路径，两者配合才知道进程在读写哪个文件。多线程进程要加 -f，否则可能一条 write 都看不到。

当进程在容器里、strace 又看不出问题时，filetop 和 opensnoop 从内核态跟踪读写文件和打开文件，能补上这一层。要追到块设备这一级，用 blktrace 及配套的 blkparse，看请求在 I/O 路径各阶段的耗时。

MySQL 和 Redis 的案例就是这么走的：pidstat 锁定 mysqld 或 redis-server，strace 加 lsof 找出操作的文件，再结合数据库引擎或持久化原理推断根因——一个是没走索引的慢查询，一个是 AOF 持久化配置不当加上客户端通信过频。

util 满就换盘的缺口

%util 到 100% 常被直接当成换盘信号，但这一步跳过了太多东西。几种常见的走偏：

  1. 只看使用率就换盘。%util 统计繁忙时间，不反映请求大小和队列深度；先看 aqu-sz 和 await，再结合 IOPS、吞吐和读写类型判断是真瓶颈还是短暂突发。
  2. 拿 top 的单次结果下结论。iowait 高只说明 CPU 在等 I/O，得用 iostat 和 pidstat 确认磁盘真的忙、并找出写出者，否则可能把缓存回收或 Swap 换页当成磁盘问题。
  3. strace 没看到 write 就判定没 I/O。多线程不加 -f、容器内外路径不一致，都会让追踪失真；换 filetop 或 opensnoop 再从内核态核一遍。
  4. 不测基准就设优化目标。IOPS、吞吐要多少才算够，得先用 fio 在相同配置下测出极限值，否则优化完了也说不清是否达标。

也有不必深究的时候：iostat 显示 %util 接近零、await 稳定在低位，这时延迟和 I/O 无关，回到 CPU 或应用逻辑上查。反过来，若 iostat 忙而 pidstat 里大多是内核线程，方向就转到内存——Swap 换页和缓存回收都会制造大量磁盘 I/O，症结在那边。

I O 瓶颈定位速查表

现象 关键读数 下一步工具 处置方向与代价
iowait 高 top wa 占大头 iostat 确认磁盘瓶颈 先确认是真 I/O 还是换页
磁盘饱和 %util 高、aqu-sz 长 pidstat -d 找进程 按读写类型判断，别直接换盘
写出者不明 pidstat 只有内核线程 转查 Swap 与内存回收 调内存，代价在回收压力
进程 I/O 大 pidstat -d 某进程居首 strace -f 加 lsof 定位文件 改日志级别或缓存策略
strace 无结果 看不到 write filetop / opensnoop 内核态追踪，需 bcc 工具
随机读写为主 IOPS 高、请求小 fio 测 4K 随机基准 调调度或合并请求
顺序读写为主 吞吐高、请求大 fio 测大块顺序基准 看预读与带宽上限

本篇锚点的 CPU 三成、P99 800 毫秒，落在「iowait 高、应用在等 I/O」这一格。按主线先 iostat 确认磁盘饱和，再 pidstat 找写出者，然后 strace 加 lsof 定位文件；确认是日志、临时文件还是数据库访问，才谈调级别、改缓存还是建索引。顺序反了，改的参数多半留在机器上却解释不了延迟。

小结与参考

I/O 瓶颈看使用率、IOPS、吞吐、响应时间，配合请求大小和队列深度一起判断；%util 是繁忙时间占比，到 100% 时照样可能接受新请求。定位按 iostat 定瓶颈、pidstat 找进程、strace 加 lsof 定位文件的顺序走，strace 看不到的改用 filetop 和 opensnoop，多线程记得加 -f。日志狂打、临时文件、慢查询、持久化配置不当都会落到同一组现象上，根因要靠工具和原理共同确认；优化前先用 fio 在相同配置下测出基准，再选调日志、缓存、索引还是调度，别拿单个指标直接下换盘的结论。
