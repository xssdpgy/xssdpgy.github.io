Linux 性能（六）内存工作原理与 Buffer Cache

发表于 2023-08-13 分类于 性能优化
本文字数： 4k 阅读时长 ≈ 4 分钟

引言

本篇转到内存。前面锚点那组数里，CPU 只有 30%、延迟却到 800 毫秒，有一种可能是请求卡在内存这一层：页缓存没命中，读请求落到磁盘；或者可用内存看着不少，其实都压在回收慢的缓存上。要判断这些，得先分清楚进程看到的虚拟内存、真正占的常驻内存，以及 free 里那一栏 buff/cache 到底算不算被占用。这篇从虚拟地址空间和页表讲起，把 Buffer 与 Cache 的口径、缓存命中率的测法串起来，最后落回「free 每一列怎么读」。

内存的工作原理

进程能直接碰到的是内核给它的一块连续虚拟地址空间，物理内存要经映射才能访问。空间分内核段和用户段，进程在用户态只能访问用户空间，进了内核态才能访问内核空间；虽然每个进程都带着内核空间，但那里映射的是同一份物理内存。

所有进程的虚拟内存加起来远超物理内存，但真正用到的才分配物理页。虚拟地址到物理地址的对应关系记在页表里，由 MMU 负责转换；查不到时触发缺页异常，内核分配物理页、更新页表，再回到用户态继续跑。页表放在 MMU 里，还有一层更快的缓存 TLB，缓存的就是它——这正是减少上下文切换能提升内存访问速度的原因：切换少了，TLB 刷新就少。

映射的最小单位是页，通常 4 KB。页太小带来页表项暴涨——光 32 位系统映射 4 GB 空间就要一百多万个页表项——于是有了多级页表和 HugePage：前者只保存用得到的区块，后者用 2 MB 或 1 GB 的大页，给 Oracle、DPDK 这类吃大内存的程序用。缺页也不全是坏事，malloc 之后内存要等首次访问才真正分配，靠的就是这个机制；但频繁分配大块内存会让缺页异常堆积，内核花在维护页表上的时间跟着涨，这就是大块内存走 mmap 也让内核负担变重的原因之一。

用户空间从低到高又分五段：只读段放代码和常量，数据段放全局变量，堆从低地址往上长，文件映射段从高地址往下长，栈放局部变量和调用上下文，大小固定。

malloc() 分配小块走 brk 移动堆顶，释放后缓存起来复用，快但容易攒碎片；大块走 mmap 在文件映射段申请，释放即归还，代价是每次都要缺页。内存紧张时，内核依次回收缓存、把不常访问的内存换到 Swap、实在不行用 OOM 杀掉评分最高的进程。

回收缓存时绕不开 free 里的 buff/cache 一列，它是 Buffer 和 Cache 的总和。两者定义查 man free 只看到来源，再查 man proc 才清楚：Buffers 是磁盘块的临时缓存，通常 20 MB 上下；Cache 是从文件读取的页缓存；SReclaimable 是 Slab 中可回收的那部分。

口径容易记反，用 dd 做四个场景就能分清。清掉缓存后写一个 500 MB 的普通文件，观察到的是 Cache 一路上涨、Buffer 几乎不动；改向裸磁盘分区写 2 GB，Buffer 涨得比 Cache 快得多。读也一样：读文件 Cache 涨、Buffer 不动，读裸磁盘分区则 Buffer 涨得快。

flowchart LR
    A["dd 读写"] --> B{目标是文件还是裸磁盘}
    B -->|"普通文件"| C["Cache 增长"]
    B -->|"裸磁盘分区"| D["Buffer 增长"]
    C --> E["Cache 缓存文件数据 读写都算"]
    D --> F["Buffer 缓存磁盘块 读写都算"]

结论是：Buffer 缓存磁盘数据，Cache 缓存文件数据，读和写都会用到。文档里只写 Cache 是文件读的页缓存，实测写文件同样进 Cache。这里的关键是文件与磁盘的区别——磁盘是块设备，分区上建了文件系统、挂到目录，才能读写文件；读写文件经过文件系统，读写裸分区跳过文件系统，两者走的是不同缓存。

free 每一列的含义

把口径落回命令。free 默认以字节为单位，输出分物理内存 Mem 和交换分区 Swap 两块。

六列里，total 是总量，used 是已用，free 是空闲，shared 是共享内存，buff/cache 是两类缓存之和，available 是新进程真正能拿到的内存。available 比 free 大，是因为它把可回收的缓存也算进去了；但缓存里正在用的那部分收不回来，所以两者不能划等号。判断内存够不够，看 available 比盯 free 准。

进程这一层用 top 或 ps，重点看 VIRT、RES、SHR。

VIRT 是申请过的虚拟内存，没分配物理页也算；RES 是实际占用的物理内存，不含 Swap 和共享；SHR 是共享部分，包含动态链接库和代码段。多个进程的 SHR 直接相加会重复计算，统计总占用时得走 /proc/<PID>/smaps 按 PSS 累加。

缓存命中率的测法

要判断缓存有没有被用好，看命中率。系统级用 cachestat，进程级用 cachetop，两者都来自 bcc、基于 eBPF。

TOTAL 是总 I/O 次数，MISSES 未命中，HITS 命中，DIRTIES 是新增脏页，后两列是 Buffer 与 Cache 的大小。cachetop 按命中次数排序，给出每个进程的读写命中率。

结合一个具体例子看。一个 512 MB 的文件，清缓存后第一次 dd 读取只有 33 MB/s，cachetop 显示命中率约 50%；再读一次，速度跳到 4.5 GB/s，命中率 100%，pcstat 也确认文件已全进缓存。同样的文件，差的就是缓存命中。这也说明拿 dd 测文件系统性能时不清缓存，结果会严重失真。

另一个例子里，应用每读 32 MB 要 0.9 秒，cachetop 却显示 100% 命中。看着矛盾，把命中次数换算成数据量就通了：1024 次命中乘以 4 KB，五秒才 4 MB，和应用的 32 MB/s 差得远。strace 一看，openat 带了 O_DIRECT，读的是裸分区、绕开了缓存，命中率统计里根本不含这部分。去掉这个标志再跑，单次降到 0.03 秒。命中率这个数得结合应用实际的 I/O 大小看，单看百分比会得出相反的结论。

内存读数的常见误判

把上面的口径串起来，有几处读数容易被直接用错。

  1. 拿 buff/cache 当被占用。缓存可回收，这一列高只说明磁盘和文件数据进了内存，除非 available 也跟着见底，否则无从谈内存不足。
  2. 把 SHR 按进程相加。共享库、代码段在多个进程里重复统计，加出来的总量会虚高；要算真实占用得走 smaps 的 PSS。
  3. 命中率 100% 就当缓存用好了。直接 I/O 不计入命中统计，那个读 32 MB 花 0.9 秒的例子就是反例——得把命中次数换算成字节，跟应用声称的吞吐对上。
  4. 不清缓存测 I/O 性能。同一文件第一次 33 MB/s、第二次 4.5 GB/s，差的不是磁盘，是数据有没有进页缓存。

什么时候不必往深查，也列一下：

情况 判断 该做的
buff/cache 高、available 充足 正常缓存 不清理
进程内存稳定、无回收压力 无内存瓶颈 转查 CPU 或 I/O
命中率低但 I/O 本就少 缓存无关瓶颈 查应用逻辑
需要真实测磁盘性能 缓存会干扰结果 测前清缓存

内存指标速查表

现象 关键读数 含义 下一步
buff/cache 很高 free 里 buff/cache 占大头 磁盘或文件数据被缓存 看 available 判断可用量
available 很小 free 里 free 尚有余量 缓存多不可回收或内存吃紧 查回收与 Swap
读文件慢、命中率低 cachetop READ_HIT 低 数据没进页缓存 预热缓存或查 I/O 路径
命中率 100% 仍慢 HITS 换算字节远小于吞吐 直接 I/O 不计入命中 strace 查 O_DIRECT
VIRT 远大于 RES top 两列差距大 虚拟内存未真正分配 属正常，看 RES 判占用
多进程 RES 相加偏大 共享段重复计算 SHR 被多次计入 走 smaps 按 PSS 累加

本篇锚点的「CPU 不高却慢」，在内存这一层对应的就是缓存未命中那条路径：读请求落到磁盘，进程等 I/O，CPU 使用率自然上不去。查法是先看 free 的 available 判断有没有真缺内存，再用 cachetop 看命中率，命中率低就查为什么没缓存住，命中率高还慢就查有没有走直接 I/O。

小结与参考

进程看到的是虚拟内存，经页表和 MMU 映射到物理页，TLB 缓存页表项；分配按页进行，小块走 brk、大块走 mmap，内存紧张时依次回收缓存、换出到 Swap、触发 OOM。Buffer 缓存磁盘数据、Cache 缓存文件数据，读写都算，free 的 buff/cache 是两者之和；判断可用内存要看 available，进程占用要看 RES，统计总量得按 PSS 避免共享段重复。缓存用得好不好看命中率，cachestat 管系统、cachetop 管进程，命中率要结合 I/O 大小解读——直接 I/O 不计入统计，百分比漂亮照样可能慢。
