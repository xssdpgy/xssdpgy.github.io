高并发（五）NoSQL 与缓存读写策略

发表于 2023-05-25 分类于 架构设计 ， 高并发
本文字数： 5.4k 阅读时长 ≈ 5 分钟

引言

NoSQL 不是关系库的替代品，它只补关系库扛不住的那类查询；选谁按查询形态定，不按数据量拍。先看常见的商品详情页：单 SKU、库存 5000 件、30 万人预约，整点开抢后峰值 2 万 QPS，一次打开要取标题、规格、价格和库存，按 3 倍读放大就是每秒 6 万次。关系库接不住，详情要么整块搬去 NoSQL，要么前面加一层缓存；迁移那几天新旧两份都在写，读到的值算谁的，得先定下来。

概念界定

按查询形态分工，比按数据量决定存储更靠得住。关系库的价值是关联查询、事务和二级索引，这块不该往外搬；NoSQL 补的是它扛不动的部分。写入快的一类多用 LSM 树，把随机写攒成内存里的有序结构再顺序落盘，代价是读要翻多层文件，读性能是让出去的。以下对应关系可以直接拿来选型：

查询形态 典型诉求 落点
按主键点查、热点读 极低延迟、高 QPS 缓存 / KV 存储
字段多变的商品详情 免改表、整文档读写 文档库
名称模糊搜索 分词、倒排 搜索引擎
离线统计、海量写入 顺序写、横向扩 列式存储
关联查询、事务 强一致、可追溯 关系库

Cache Aside 是缓存加关系库这套组合里最常用的读写策略，数据以库为准，缓存按需加载。读路径四步：读缓存、命中就返回、未命中查库、回种缓存再返回。写路径两步：先更新库，再删缓存。删而不是改，是因为两个写请求并发改同一个缓存值会乱序覆盖，读改写还会丢失更新；删掉让下一次读自己回种，是成本最低的写法。

先删缓存再更新库，并发读会在库还没改完时把旧值回种，缓存里长期是脏的。先更新库再删缓存也有一个理论窗口：读请求未命中、已从库里拿到旧值，此时写请求更新了库并删了缓存，读请求随后才把旧值写回缓存。这个窗口出现的概率不高，因为写缓存通常比写库快一个数量级，很难反过来赶上；真出现了，靠短过期时间兜底，过期后下一次读会重新加载。要求强一致的读不能靠这套策略，这是它的边界，不是缺陷。

sequenceDiagram
    participant A as 读请求
    participant B as 写请求
    participant C as 缓存
    participant D as 关系库
    A->>C: get sku:1001 未命中
    A->>D: select 得到旧值 20
    B->>D: update 改成 21
    B->>C: del sku:1001
    A->>C: set sku:1001 = 20 回种旧值
    Note over C,D: 短过期时间内缓存与库不一致

案例推演

把大促秒杀的设定摆一遍：单 SKU、库存 5000 件、预约 30 万人、整点开抢，日常下单 200 QPS、P99 60ms，峰值 2 万 QPS，验收目标是 2 万 QPS 下 P99 < 200ms、P999 < 1s、错误率 < 0.1%，链路为下单 → 锁库存 → 支付 → 发货。分层结论是网关 6 台、应用 20 台、缓存 3 分片、数据库同步写入不成立。

商品详情的读放大按 3 倍算，2 万 QPS 落到缓存就是每秒 6 万次，3 分片每片约 2 万次，落在单分片能力之内；关系库直接接这 6 万次不成立。详情字段多、读多写少、允许秒级延迟，适合整份放到文档库或缓存，读路径一律走 Cache Aside。库存是另一回事：它是强一致计数，扣减要在缓存里做原子操作或留在关系库用事务，不能因为「详情搬走了」就把它也塞进最终一致的文档库。名称模糊搜索也不该留在关系库，前置通配的 like 用不上索引，会退化成全表扫描，交给倒排索引才对。

难点在迁移期。秒杀商品数据从关系库迁往缓存与文档库，存量同步加增量双写跑起来后，同一份数据在新旧两处都存在。这时 Cache Aside 的删缓存顺序会被放大：一次更新既要写旧库、写新库，又要删掉对应的缓存键，任何一步漏删或顺序错位，读请求就可能在两个库之间拿到不同版本。所以迁移期不追求「切换瞬间一致」，而是用步骤把不一致关在可控窗口里，并且让旧库一直保持可写。

flowchart LR
    S0["旧库单写"] --> S1["① 双写：存量同步 + 增量写新旧两库，旧库为准"]
    S1 --> S2["② 灰度读：10% → 50% 读流量切新库"]
    S2 --> S3["③ 校验：抽样比对新旧一致，工具提前备好"]
    S3 --> S4["④ 切读：100% 读切新库，双写保留"]
    S4 --> S5["观察数日后停写旧库"]
    S1 -.-> RB["回滚：读开关拨回旧库，旧库全程在写"]
    S2 -.-> RB
    S3 -.-> RB
    S4 -.-> RB

四步的判定点要写死：双写阶段新库写失败要记日志补写，不能默默丢；灰度读每次只放一小段流量，观察 P99 与错误率；校验用抽样比对，工具在动手迁移前就得在测试环境跑通；切读后双写再保留几天，确认没问题才停写旧库。回滚路径不是事后再想——双写期间旧库始终有全量写入，把读开关拨回去就是回滚，代价只是之前那点灰度流量读到了新库。周期长、业务代码要改造，是这套方案的账。

代码与目录

这段实现有明确边界：删缓存失败没有重试，靠的是短过期时间兜底，真要收紧就得给删除加重试或异步补偿；空值哨兵的存活时间比业务键短一个量级，避免撑爆内存；写路径刻意不碰缓存值，把并发覆盖的风险挡在外面。库存扣减、资格判定这类要求读到的就是最新值的操作，不能走这段，得换成单键原子操作或数据库事务。

反模式与适用边界

  1. 把 NoSQL 当关系库整体替换。 关联查询、跨表事务、二级索引一起丢掉，搜索和账务都要另起炉灶，最后常常再切回来。补位可以，替代不成立。
  2. 先删缓存再更新库。 并发读会在库改完之前把旧值回种，脏数据会一直留到下次更新，删缓存的顺序不能反。
  3. 写路径里顺手把新值写回缓存。 两个写请求乱序会互相覆盖，读改写还会丢失更新，删缓存是这里成本最低的做法。
  4. 存量同步完就把数据源一步切到新库。 增量已经写进新库、旧库没有，发现问题也回不去，等于没有回滚路径。
  5. 没写校验工具就切读。 抽样比对要提前在测试环境跑通，靠切换后肉眼核对，等于把校验这一步省掉了。

下面这些情况，这套读写策略与迁移步骤可以不做或只做一半：

情形 为什么不必套 建议做法
内部后台、报表，峰值不到单机拐点十分之一 关系库直接扛得住，缓存层是净成本 单库加索引，不加缓存
字段固定、关联密集的账务与结算 缺跨表事务，一致性优先级更高 留在关系库用事务
数据量小且没有扩展预期 分片与文档库都是为扩展准备的 单库单表，定期归档
一次性活动页，内容全静态 请求在静态层就被挡完 静态化加就近分发
强一致的库存扣减与资格判定 读写策略允许短时不一致 原子扣减或数据库事务

要点速查

决策点 结论 代价
关系库与 NoSQL 按查询形态分工，互补不替代 两套存储，运维与一致性成本
商品详情 文档库或缓存，允许秒级延迟 迁移期要双写
库存扣减 留在关系库或单键原子操作 用不上文档库的扩展便利
Cache Aside 写顺序 先更新库，再删缓存 残留一个低概率脏数据窗口
残留不一致 短过期时间兜底 强一致场景不适用
迁移四步 双写 → 灰度读 → 校验 → 切读 周期长，业务代码要改造
回滚 双写期间读开关随时拨回旧库 旧库需一直保留写入能力

小结与参考

按查询形态选存储，比按数据量拍脑袋省事。热点点查交给缓存就够了；商品详情字段多变，放文档库比不断改表省事；模糊搜索得靠倒排索引，关系库做不了分词。事务和关联查询仍归关系库，这块不该往外搬。Cache Aside 的删缓存顺序是并发下读不读得到旧值的分界，不是习惯问题，残留窗口能接受多久要在方案里写明。迁移把双写和回滚留在手边，切读才敢做，代价是周期和代码改造。
