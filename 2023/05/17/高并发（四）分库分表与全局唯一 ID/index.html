高并发（四）分库分表与全局唯一 ID

发表于 2023-05-17 分类于 架构设计 ， 高并发
本文字数： 6.1k 阅读时长 ≈ 6 分钟

引言

分片键按查询的主维度选，选错就得跨片聚合；先垂直拆分再水平，别一上来就铺开分库分表；拆完之后 ID 必须全局唯一且趋势有序，Snowflake、号段、库内自增各有各的代价。比如订单表按 user_id 还是 order_id 分，看着只是选个字段，实际决定了查个人订单和按单号查哪个会变成扫全片；秒杀又只有一个 SKU，5000 件库存的扣减热点全压在一处，分片规则稍不留神就把这点写压力挤到单个分片上。

概念界定

分库分表是把原本一张表的数据按规则摊到多个库、多张表里。和主从复制不同，这里每个节点只存一部分数据，不是全量拷贝，所以既降了单表容量，也把写请求分散到多个节点。拆分分两步：垂直拆分按业务把表分到不同的库，专库专用，故障也跟着隔离；水平拆分再按某个字段把单表的数据切到多个库和表。顺序别反，业务边界没理清就先水平切，后面每加一个查询维度都要重迁一次数据，代价远高于先划清库。

水平切的规则常见两种。对字段取哈希再取余，数据打得散，适合实体表；按时间或 ID 区间切，查询能先定位落在哪张表，但最近的数据天然是热点，表还得提前建好，跨了区间没人建表就写不进去。区间切用在按时间浏览的列表类数据上顺手，用在实体表上容易把新数据全堆到最后一片。

    APP["下单应用"] --> ROUTE{"按 user_id 哈希定位分片"}
    ROUTE --> O0["订单库 0 / 表 0-15"]

    ROUTE --> O2["订单库 2 / 表 0-15"]
    ROUTE --> O3["订单库 3 / 表 0-15"]
    ID["发号器：全局唯一 + 趋势有序"] -.->|生成 order_id| APP
    V["垂直拆分：订单库 / 用户库 / 商品库 分离"] -.-> ROUTE

代价集中在分片键上。拆完之后，查询必须带上分片键才能定位库表，否则就要向所有分片各发一次；16 库 64 表就是上千次查询，性能直接垮掉。跨库的 join、count、排序、分页都变麻烦，得在业务代码里拼，或者把计数单独冗余出来。按非分片键查询的办法是建一张映射表，先查出分片键再回表，多一份存储、多一次查询，但比再切一套便宜得多。

另一个躲不掉的问题是主键。单库时自增字段最省事，分库分表后每个库各自自增，ID 必然撞。UUID 不依赖第三方、生成快，但无序、没有业务含义、占空间，作为主键会让 B+ 树索引不断做随机插入和页分裂，写性能吃亏。所以分库分表后的 ID 要满足两件事：全局唯一，且趋势有序。有序既能当时间排序用、省掉一列创建时间和对应索引，又让新记录顺序追加到索引右侧，写入局部性好。

三种做法各有代价。Snowflake 把 64 位拆成时间戳、机器标识、序列号，本地生成、不依赖数据库，趋势有序、还能反解出生成时间和机器，但要处理时钟回拨——机器时间往回跳就可能发重复号，通常的做法是回拨期间拒绝发号。号段方式从数据库一次取一段 ID 缓存在本地，逐个发放，段用尽再取，数据库压力小、ID 严格递增，代价是要维护发号记录，且发号器重启会跳段。库内自增靠设置不同步长和起始值让多库不撞，最简单，但扩容加库要重新规划步长，扩展性差。

案例推演

订单表按什么分，先看查询怎么来。大促秒杀的设定是单 SKU、库存 5000 件、预约 30 万人、整点开抢，峰值 2 万 QPS 是日常下单 200 QPS 的 100 倍，验收目标「2 万 QPS 下 P99 < 200ms、P999 < 1s、错误率 < 0.1%」，链路下单 → 锁库存 → 支付 → 发货。前端最高频的两类查询是查个人订单列表和按订单号查详情。

若按 order_id 哈希分片，按单号查能一次命中，但查个人订单要带 user_id、不带分片键，就得扫所有分片再聚合，几千次查询拼一个列表，P99 直接崩。若按 user_id 分片，用户维度的列表查询落单片，单号查询则要靠一张 order_id 到 user_id 的映射表先定位，多一次查询但可控。选 user_id 作分片键是这笔账算下来的结果：主维度是用户，就把分片键定在用户上，另一个维度用映射表补，而不是反过来让最频繁的查询去扫全片。

分片键 命中好的查询 变差的查询 补救 适用
user_id 个人订单列表、用户维度统计 按 order_id 查详情 order_id 到 user_id 映射表 C 端订单主维度是用户
order_id 按单号查详情、履约对账 个人订单列表 用户维度另建冗余表 / 全片聚合 后台、履约侧
创建时间区间 按时间段归档、对账 跨时间段的用户查询 时间加用户二级索引 归档、冷数据
SKU / 商品 ID 单商品维度查询 秒杀单 SKU 全压一片 库存热点移交缓存与排队 不适合做订单分片键

这里有个反直觉的点：分片键选得再对，秒杀单 SKU 也会造热点。30 万人抢 5000 件，扣减请求几乎都指向同一个 SKU 的库存行，不管订单怎么分片，那一行始终是单点。分片解决的是订单写入量，不是库存热点；后者要靠缓存预扣、排队和入口限流，把它挡在数据库之外。把两件事混在一起，以为分了片就万事大吉，热点照样把承载库存的那一片打挂。

ID 的选择跟着分片键走。order_id 若用库内自增，各库各自从 1 开始，全局必撞；用 UUID，索引写入变成随机插入，订单表每天几千万行时，B+ 树页分裂的开销肉眼可见。趋势有序的 ID 还能顺带当排序列：订单列表按 ID 倒序就是按下单时间倒序，省一列创建时间。号段或 Snowflake 生成的 order_id 单调递增，新订单集中写在索引右侧，局部性好；但秒杀时刻发号 QPS 高，若用 Snowflake 且每毫秒只发几个号，末位序列号长期偏小，拿 ID 直接取余分片会分得不均，要么时间戳退到秒级多发几个号，要么给序列号起点加随机。

反模式与适用边界

  1. 没到容量瓶颈就分库分表。 跨片聚合、join、count 的复杂度先到账，单表数据量远未到千万时收益基本为零。
  2. 分片键按看着顺眼选。 不带主查询维度，列表页变成扫全片再聚合，几千次查询拼一个结果。
  3. 先水平后垂直。 业务边界没定就切数据，每加一个查询维度都要重迁一次，迁移期双写校验的成本反复付。
  4. 用 UUID 做主键，或各库自增期望不撞。 前者毁索引局部性、写入随机插入，后者分库后必然重复，都不可接受。
  5. 拿 ID 直接取余分片。 忽略发号 QPS 低时序列号长期偏小造成的数据倾斜，分片看着有 16 个，数据只落在少数几个。

判断点 结论 代价 / 坑
拆分顺序 先垂直（按业务），再水平（按字段） 反了就反复迁数据
分片键 取查询主维度 选错就跨片聚合、扫全片

小结与参考

分库分表不是把一张表拆开那么简单，它把「查询必须带分片键」和「ID 必须全局唯一」两条约束一起带进来。分片键定在查询主维度上，其余维度用映射表补；垂直拆分先划清业务边界，水平拆分才不会反复返工；主键换成趋势有序的全局 ID，索引局部性才保得住。秒杀那种单 SKU 热点更说明一件事：分片解决的是写入量，热点要另找缓存预扣和排队，别指望换分片键能顺手解决。方案没有免费的，Snowflake 怕时钟回拨，号段会跳号，自增步长难扩容，挑一个能把代价说清楚的用，比追一个新方案稳当。
