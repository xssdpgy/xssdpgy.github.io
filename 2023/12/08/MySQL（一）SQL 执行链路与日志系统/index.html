MySQL（一）SQL 执行链路与日志系统

发表于 2023-12-08 分类于 数据库
本文字数： 5.3k 阅读时长 ≈ 5 分钟

引言

写了几年业务，SQL 大多能写对，但一条语句发进去之后在 MySQL 内部走过哪些地方，很多人说不太清。平时这层盲区没什么影响，语句返回结果正确就够了。等到碰上慢查询、锁等待，或者一次异常重启后发现数据对不上，缺了这层认识就容易靠猜——加个索引试试，重启一下看看。

这篇从两条最简单的语句入手。一条查询，看它从连接器到执行器经过哪些模块；一条更新，看它比查询多出来的两份日志，以及这两份日志怎么配合，才能让重启后的数据还对得上。链路走通之后，后面讲索引、锁、事务时提到的很多判断才有落点。

整个系列八篇，按下面的顺序展开：

  • MySQL（一）SQL 执行链路与日志系统
  • MySQL（二）事务隔离与 MVCC
  • MySQL（三）索引——结构与设计取舍

不必从头顺着读，哪篇的问题眼下更急，就从哪篇开始。

查询链路的五个模块

MySQL 大体分两层。上面是 Server 层，连接器、查询缓存、分析器、优化器、执行器都在这里，日期、数学、加密这些内置函数，以及存储过程、触发器、视图，也都归它管。下面是存储引擎层，管数据的存和取，做成插件式，InnoDB、MyISAM、Memory 都能挂上来。建表时不指定引擎，默认就是 InnoDB。两层之间通过一组接口交互，改了存储引擎，上面那半截不用动。

连接器先接待客户端。TCP 握手之后校验用户名密码，通过后去权限表把权限读出来，这个连接后续的权限判断都以这份为准。这里有个容易踩的点：管理员改了某个用户的权限，已经建立的连接不受影响，得等新连接才用上新权限。连接完成后一直没有动作就是空闲状态，show processlist 里 Command 列显示 Sleep 的就是。空闲太久会被断开，由 wait_timeout 控制，默认 8 小时。

建连接的成本不低，所以用量上偏向长连接。代价是执行期间临时用的内存挂在连接对象上，只有断开才释放，长连接攒多了内存涨得快，严重的会被系统杀掉，从外面看就是 MySQL 异常重启。两个常见的处理办法：用一段时间后主动断开重连；或者在跑完一个大查询后执行 mysql_reset_connection 把连接资源复位，这一步免去了重连和重新认证。

查询缓存这一段值得单独说，因为它常被误会。语句和结果以键值对缓存在内存里，命中就直接返回，看起来很划算。问题是失效太频繁：只要对表有一次更新，这张表上所有缓存全部清空。更新稍微频繁一点，命中率就低得可怜，存进去还没用就被清掉了。它只适合那种长期不动的配置表。较新的版本干脆把查询缓存整块功能拿掉了，日常用法里可以按需关闭，只在确定要用的语句上显式打开。

分析器负责弄明白语句要做什么。先做词法分析，把字符串识别出来——select 是查询关键字，T 是表名，ID 是列名；再做语法分析，按语法规则检查这条语句合不合法。语法出错会报 You have an error in your SQL syntax，提示里紧贴 use near 的就是出错位置。列不存在这类错误也在这个阶段报，比如表 T 没有 k 列却写了 where k=1，报 Unknown column，分析器在优化器之前就把它拦下了。

优化器决定怎么做。表里有多个索引时选哪个，多表 join 时按什么顺序连，都是它的活。同一条语句的两种执行路径逻辑结果一样，效率可能差很多，优化器就是在这中间挑。

执行器真正动手。开始先校验对这张表有没有权限，没有就返回 ERROR 1142。通过后打开表，按引擎定义调用对应的接口。如果 ID 列没索引，执行器就调引擎接口取第一行，判断 ID 值，不符合跳过，符合放进结果集，再取下一行，直到表尾。慢查询日志里的 rows_examined 记录扫描行数，就是执行器每次调引擎取数时累加出来的。要注意引擎内部一次调用可能扫了多行，所以这个值跟引擎实际扫描的行数未必相等。

redo log 与 WAL

更新语句前面那段链路和查询完全一样，连接器、分析器、优化器、执行器一个不落。区别在后面：更新还多出两份日志。

先看第一份。如果每次更新都要直接写进磁盘，磁盘得先找到那条记录再改，找记录和改数据的成本都高。这个困境有个通俗的对照：柜台掌柜记赊账，账本密密麻麻几十页，每来一笔就翻出来找人、拨算盘、写回去，忙起来根本来不及。实用的做法是先在粉板上记一笔，打烊了再统一誊到账本。

MySQL 用的就是这套思路，叫 WAL（Write-Ahead Logging）——先写日志，再写磁盘。具体到 InnoDB：一条记录要更新时，引擎先把改动写进 redo log（粉板），同时更新内存，这时更新就算完成了；随后在系统相对空闲的时候，再把操作落到磁盘（账本）。

redo log 的大小是固定的，比如配成一组文件、写到末尾回到开头循环写。这里有两个位置概念：write pos 是当前写到的地方，一边写一边后移；checkpoint 是要擦除的地方，擦之前先把对应记录更新到数据文件。两者之间空着的部分还能接受新操作。write pos 追上 checkpoint 就意味着粉板写满了，此时得停下来推进 checkpoint、腾出空间，更新才能继续。

正因为有 redo log，InnoDB 能保证异常重启前提交的记录不丢，这个能力叫 crash-safe。只要改动记在了粉板上或者账本上，哪怕中途停业，恢复之后也能凭这两处把账目对回来。

binlog 与两阶段提交

第二份日志在 Server 层，叫 binlog（归档日志）。它和 redo log 并存有历史原因：早期 MySQL 自带的引擎是 MyISAM，没有 crash-safe 能力，binlog 只用来归档。InnoDB 是后来以插件形式加进来的，光靠 binlog 保证不了崩溃恢复，于是自己又做了一套 redo log。

两份日志的三点区别，是后面很多问题的根：

维度 redo log binlog
归属 InnoDB 引擎特有 Server 层实现，所有引擎可用
内容 物理日志，某数据页上做了什么改动 逻辑日志，语句的原始逻辑
写入 固定大小，循环写、会覆盖 追加写，写满切下一个文件，不覆盖

拿 update T set c=c+1 where ID=2 看完整流程。执行器先找引擎取 ID=2 这一行：ID 是主键，引擎直接树搜索定位，数据页在内存就返回，不在就先从磁盘读进来。执行器把值加一得到新行，调引擎接口写入。引擎把新行更新到内存，同时把改动记进 redo log，并把这份日志标成 prepare，然后告诉执行器可以提交了。执行器生成这条操作的 binlog 写入磁盘，最后调引擎的提交接口，引擎把 redo log 改成 commit 状态，更新完成。

中间把 redo log 的写入拆成 prepare 和 commit 两步，就是两阶段提交。它要解决的问题是两份日志之间的逻辑一致。用反证法看得最清楚。假设当前 c=0，在写完第一份日志、第二份还没写完时崩了：

  • 先写 redo log 后写 binlog。redo log 写完崩溃重启，靠它能把数据恢复成 c=1；但 binlog 里没有这条语句。之后拿这份 binlog 去恢复临时库，这一行就是 c=0，和原库对不上。
  • 先写 binlog 后写 redo log。binlog 写完崩溃，redo log 还没写，这个事务在崩溃恢复时无效，原库是 c=0；可 binlog 里已经记了「c 从 0 改成 1」，拿它恢复出来的临时库又成了 c=1，还是对不上。

两种顺序都会让数据库本身的状态和用日志恢复出来的状态不一致。两阶段提交让 redo log 和 binlog 对事务提交状态达成一致，避开这个裂缝。它的用处不止误删后的恢复——加备库扩容时常见的做法是全量备份加应用 binlog，这里的不一致会直接变成线上主从数据不同。

刷盘参数与崩溃恢复

前面说「redo log 和 binlog 持久化到磁盘就能恢复」，还有个前提没交代：这两份日志自己怎么才算真正写进磁盘。

先看 binlog。事务执行中先写进 binlog cache，提交时再把整个事务一次性写进 binlog 文件——一个事务的 binlog 不能拆开。cache 每个线程一份，大小由 binlog_cache_size 控制，超过就暂存到磁盘；所有线程共用同一个 binlog 文件。写盘分两步：write 只把日志写进文件系统的 page cache，速度快；fsync 完成真正的持久化，磁盘 IOPS 主要花在这里。时机由 sync_binlog 控制：

取值 行为 代价
0 每次提交只 write 主机异常重启丢全部未 fsync 的 binlog
1 每次提交都 fsync 每次提交多一次刷盘
N>1 累积 N 个事务再 fsync 异常重启丢最近 N 个事务的 binlog

有 IO 瓶颈时把 sync_binlog 调大能提升性能，常见取值在 100 到 1000 之间，一般不设 0。

redo log 有类似的三种状态：在 redo log buffer 里（进程内存）、write 到 page cache 但没 fsync、真正持久化到磁盘。写进 buffer 很快，write 也快，持久化慢得多。innodb_flush_log_at_trx_commit 控制提交时的策略：设 0 只留在 buffer，设 1 直接持久化，设 2 只写到 page cache。另外有个后台线程每秒把 buffer 里的内容 write 再 fsync 一遍，所以未提交事务的 redo log 也可能已经落盘；buffer 用到一半、或者别的事务提交搭便车时，也会带出去。

通常说的「双 1」，指 sync_binlog 和 innodb_flush_log_at_trx_commit 都设成 1，一个事务完整提交要等两次刷盘。既然如此，看到 TPS 两万、磁盘能力也才两万，为什么没成为瓶颈？靠的是组提交。LSN（日志逻辑序列号）单调递增，对应 redo log 的一个个写入点。并发的多个事务在准备阶段各自写完 buffer，第一个到达的被选为 leader，等它真正写盘时，组里已经攒了几个事务，leader 带着最大的 LSN 一次性落盘，LSN 更小的成员直接跟着返回。组成员越多，摊到每个事务的 IOPS 越少。为了让组里多攒几个，MySQL 还会把 redo log 的 fsync 时机往后拖到 binlog 写完——用一点响应时间换更少的刷盘次数，这部分由 binlog_group_commit_sync_delay 和 binlog_group_commit_sync_no_delay_count 控制。

回头看 WAL 为什么能减少磁盘写：一是 redo log 和 binlog 都顺序写，比随机写快；二是组提交把多次 fsync 合并了。如果 IO 已经成了瓶颈，可选的手段和代价是：调那两个 binlog 组提交参数（增加响应时间，不丢数据）；sync_binlog 调到大于 1（掉电丢 binlog）；innodb_flush_log_at_trx_commit 设成 2（掉电丢数据）。最后这个不建议设 0——设 0 时日志只在内存，MySQL 自己重启就丢，而设 2 只是进 page cache、速度相差不大，异常重启却不会丢。

执行链路速查

现象或需求 先看哪里 处理方向
改了权限没生效 现有连接权限是建连时读的 新建连接才用新权限
长连接后内存飞涨 临时内存挂在连接对象上 定期断开或用连接复位
查询缓存命中率低 表上有更新就全量失效 关闭，仅静态表按需开启
列不存在报 Unknown column 分析器阶段 检查 SQL 里的列名
崩溃后数据对不上 redo log 与 binlog 是否一致 确认两阶段提交、双 1 配置
IO 到瓶颈 write 与 fsync 的次数 组提交参数，权衡掉电丢数据风险

小结与参考

把链路和日志放在一篇里讲，是因为它们连着同一条主线：一条语句从客户端进去、落到磁盘，中间经过的每个模块都在为「正确」和「快」做取舍。查询缓存为快而生，却因失效太猛被弃用；两份日志为正确而生，靠两阶段提交和刷盘参数兜底，又要靠组提交把性能找回来。后面几篇展开的索引、锁、事务，都是在这条链路上继续往细里看。
