MySQL（二）事务隔离与 MVCC

发表于 2023-12-15 分类于 数据库
本文字数： 6.1k 阅读时长 ≈ 6 分钟

引言

四种隔离级别的名字背下来不难，关键在于它和查询返回的数据怎么对上。同一个事务里两次查同一行，结果可能一样也可能不一样；普通 select 和加了 for update 的 select，读到的版本也可能不同。这些差别背后是同一套东西——版本链和一致性视图。这篇先把四种级别的现象摆出来，再顺着版本链和视图的构造走一遍，最后看幻读为什么需要间隙锁。

隔离级别与现象

事务要保证一组操作要么全部成功、要么全部失败。ACID 里的隔离性管的是并发事务之间的可见程度。多个事务同时跑，常见三种现象：读到别的事务尚未提交的改动，是脏读；同一事务两次读同一行，中间被别的事务改掉，结果不一样，是不可重复读；同一事务两次按条件查，后一次多出别的事务新插入的行，是幻读。

隔离级别按能容忍的现象分成四档。读未提交允许读到未提交的改动；读提交只认提交后的改动；可重复读让事务执行期间看到的数据和启动时一致；串行化对同一行加读写锁，冲突时后来的事务等着。隔离越强，并发越弱，选哪一档要看业务能接受哪种现象。

用一个只有一列的表看差别。表里先放一行 c=1，事务 A 依次读三次，事务 B 在中间把 1 改成 2：

sequenceDiagram
    participant A as 事务 A
    participant B as 事务 B
    A->>A: begin
    B->>B: begin
    B->>B: update T set c=2 （尚未提交）
    A->>A: V1 = select c from T
    B->>B: commit
    A->>A: V2 = select c from T
    A->>A: commit
    A->>A: V3 = select c from T （新事务）

V1、V2、V3 三个读数，在不同级别下是：

隔离级别 V1 V2 V3
读未提交 2 2 2
读提交 1 2 2
可重复读 1 1 2
串行化 1 1 2

读未提交直接返回记录上的最新值，B 还没提交 A 就看到了 2。读提交等 B 提交后才让 A 看见，所以 V1 还是 1，V2 变成 2。可重复读把 A 看到的值钉在事务启动的那一刻，V2 仍是 1，直到 V3 属于提交后的新事务才读到 2。串行化下 A 的读加读锁，B 的更新被挡住，要等 A 提交后才能继续，A 这边的读数保持前两次是 1。

四种级别在 InnoDB 里的实现分两条路。读未提交没有视图，直接读最新值；串行化靠加锁让读写排开；读提交和可重复读都靠一致性视图，区别在于视图什么时候建——读提交每条语句执行前重新算一个，可重复读在事务启动时建一次，之后整个事务共用。隔离级别由启动参数 transaction_isolation 指定，用 show variables like 'transaction_isolation' 能看当前值。从 Oracle 迁过来的应用通常设成读提交，保持和原来一致；对账这类需要整段计算看同一份数据的场景，用可重复读省事。

一致性视图与版本链

可重复读下事务像是与世无争，别人改了它还是看老数据。这个快照不用真的拷贝整库，靠的是每行数据的多个版本。

InnoDB 给每个事务分配一个严格递增的 transaction id。每次更新一行，就生成这行的一个新版本，把更新它的事务 id 记成这个版本的 row trx_id，旧版本保留。同一行连着被改几次，就串出一条版本链。

flowchart LR
    V4["V4 · k=22<br/>row trx_id=25 · 当前版本"] -->|U3| V3["V3 · k=20<br/>row trx_id=20"]
    V3 -->|U2| V2["V2 · k=15<br/>row trx_id=15"]
    V2 -->|U1| V1["V1 · k=10<br/>row trx_id=10"]

链上的 U1、U2、U3 就是 undo log。V1、V2、V3 并没有物理存着，需要哪个版本，就从当前版本 V4 沿着 undo log 一路算回去。要 V2，就执行 U3、U2。

快照靠一个数组实现。事务启动时，InnoDB 把此刻还在活跃（启动了没提交）的事务 id 记进数组，数组里的最小值叫低水位，系统已经创建过的最大事务 id 加一叫高水位。数组加高水位合起来就是一致性视图。判断某个数据版本对当前事务可见与否，拿它的 row trx_id 和这个视图比：

flowchart LR
    subgraph view["一致性视图：视图数组 + 高水位"]
    direction LR
    A1["trx_id 低于低水位<br/>启动前已提交 · 可见"]
    A2["trx_id 介于低水位与高水位<br/>在数组中不可见 · 不在数组中可见"]
    A3["trx_id 不低于高水位<br/>启动后生成 · 不可见"]
    end

换成按时间说更好记：版本在视图创建前提交的，可见；创建后提交的，不可见；创建时还没提交的，不可见；事务自己改的，总是可见。读一行时从当前版本往回找，碰到第一个可见的版本就返回。

版本链留着不删，是为了给老视图留退路。系统里没有比某段 undo log 更早的视图时，这段日志才能回收。长事务会一直攥着一个很老的视图，它提交之前，期间产生的回滚记录都得留着，占存储空间，还占着锁。查超过 60 秒的事务可以看：

事务怎么启动也有讲究。begin 或 start transaction 之后，要等到第一条操作 InnoDB 表的语句，事务才算真正起来；想立刻拿到一致的快照，用 start transaction with consistent snapshot。另一种写法 set autocommit=0 会把当前线程的自动提交关掉，之后随便一个 select 都落在事务里，长连接下容易攒出意外的长事务。建议保持 autocommit=1，需要事务时显式 begin；担心多一次交互，可以用 commit work and chain，提交当前事务并顺手开启下一个，省掉再次 begin。

快照读与当前读

回到开头那个让人犯晕的结果：事务 B 查到 k=3，事务 A 查到 k=1。表 t 里初始两行 (1,1)、(2,2)，三个事务按下面的顺序走：

sequenceDiagram
    participant A as 事务 A (trx 100)
    participant B as 事务 B (trx 101)
    participant C as 事务 C (trx 102)
    Note over A,C: A 启动时活跃事务 99，初始行 row trx_id=90
    C->>C: update t set k=k+1 where id=1 得到 (1,2)
    C->>C: commit
    B->>B: update t set k=k+1 where id=1 得到 (1,3)
    B->>B: select k where id=1 得到 3
    A->>A: select k where id=1 得到 1

A 的视图数组是 [99,100]，B 是 [99,100,101]，C 是 [99,100,101,102]。C 先把 (1,1) 改成 (1,2) 并提交，B 又在 (1,2) 的基础上改成 (1,3)，此刻最新版本是 (1,3)，row trx_id=101。

A 查询时从最新版本往回走，判断过程是这样：

flowchart TD
    S["当前版本 (1,3)<br/>row trx_id=101"] --> Q1{"对 A 的视图可见?"}
    Q1 -->|不可见，在数组中| N1["回退到 (1,2)<br/>row trx_id=102"]
    N1 --> Q2{"对 A 的视图可见?"}
    Q2 -->|不可见，高于高水位| N2["回退到 (1,1)<br/>row trx_id=90"]
    N2 --> Q3{"对 A 的视图可见?"}
    Q3 -->|可见，低于低水位| R["返回 k=1"]

B 查到 3，道理在更新那一步。更新永远是先读后写，这个读走的是当前读——读已经提交的最新值，不走自己的视图。B 执行 k=k+1 时拿到的当前值是 C 提交的 (1,2)，加一得到 (1,3)。随后 B 再查询，看到最新版本 row trx_id=101 正是自己，直接返回 3。

普通 select 走快照读，按视图挑版本；update、delete，以及 select … for update 或 lock in share mode 走当前读，锁定读最新版本，碰上别人的行锁就等。两条路分得清，很多看不见的疑惑就解开了。

flowchart TD
    Q["一条读语句"] --> L{"带锁?"}
    L -->|"普通 select"| S["快照读：按视图挑可见版本"]
    L -->|"for update / lock in share mode"| C["当前读：读最新版本，遇锁等待"]
    S --> R1["可重复读：复用事务视图"]
    S --> R2["读提交：语句前新建视图"]

可重复读和读提交的差别，落在视图创建的时机上。可重复读整个事务共用一个视图，读提交每条语句前重算一个。同样三个事务的时序，读提交下 A 查询的视图在语句执行时才建，(1,3) 还没提交不可见，(1,2) 已提交可见，A 读到 k=2；B 仍然读到 3。表结构没有 row trx_id，只能走当前读那条路，这也是表结构没法做可重复读的原因。

幻读与间隙锁

快照读和当前读的分工，在当前读下会碰到一个麻烦。表 t 有主键 id 和索引 c，初始 6 行，id 分别是 0、5、10、15、20、25。session A 在同一个事务里连查三次：

三次查询之间，session B 把 id=0 这行的 d 改成 5，session C 插入一行 (1,1,5)。三次结果依次多了 id=0 和 id=1 两行。后一次查询看到了前一次没看到的新插入行，这就是幻读。B 把已有行的 d 改成 5 让 A 多看到一行，这种不算幻读；幻读专指新插入的行。快照读看不到别的事务插入的数据，所以幻读只在当前读下出现。

sequenceDiagram
    participant A as session A
    participant B as session B
    participant C as session C
    A->>A: Q1: d=5 当前读 得到 {5}
    B->>B: update t set d=5 where id=0
    A->>A: Q2: d=5 当前读 得到 {0,5}
    C->>C: insert into t values(1,1,5)
    A->>A: Q3: d=5 当前读 得到 {0,1,5} 幻读

按事务可见性规则看，这三次当前读都读到了已提交的最新值，本身没违反规则。麻烦在两处。一是语义：A 声明要锁住所有 d=5 的行，B 和 C 却还能改、还能插。二是一致性：A 随后执行 update t set d=100 where d=5，数据库里最终只有 id=5 这行被改成 100，可 binlog 按提交顺序重放到备库，id=0 和 id=1 也会变成 100，主备数据就对不上了。

把扫描到的所有行都加上行锁，能挡住 B 改 id=0，仍挡不住 C 插入 id=1——插入时那行还不存在，行锁无处可加。InnoDB 于是加了一把间隙锁，锁的是记录之间的空隙。行锁和间隙锁合起来叫 next-key lock，区间前开后闭。表 t 锁全表时形成 7 段：

flowchart LR
    G["(-∞,0]"] --- R0["(0,5]"] --- R5["(5,10]"] --- R10["(10,15]"] --- R15["(15,20]"] --- R20["(20,25]"] --- RS["(25,+supremum]"]

间隙锁彼此不冲突，冲突的是往同一间隙插入记录。两个事务都查 id=9（不存在），都会加 (5,10) 的间隙锁；谁先插入 (9,9,9)，就会被对方的间隙锁挡住，两个事务互相等待形成死锁，由死锁检测挑一个报错返回。

不想要间隙锁，可以把隔离级别设成读提交——这个级别下间隙锁不生效，锁的范围小。代价是得把 binlog 格式设成 row，才能保证前面说的数据和日志一致。这个组合能用，但选它的理由应该是业务用不到可重复读，而大家都这么配算不上理由：mysqldump 逻辑备份时用的还是可重复读，同一个库里并存两种隔离级别，先把各自的现象弄清楚再说没问题。

事务隔离速查

现象或需求 背后的机制 处理方向
读到未提交的改动 读未提交没有视图 改读提交或可重复读
同一事务两次读数不同 读提交每条语句重建视图 需要对账一致性就用可重复读
更新覆盖了别人的改动 快照读在历史版本上更新会丢 更新走当前读，靠行锁串行
当前读多出新插入的行 幻读，行锁锁不住不存在的行 next-key lock 锁住间隙
两个会话插入同一不存在 id 卡住 间隙锁互相挡住插入 死锁检测报错，或改用读提交加 row binlog
回滚段一直涨 长事务攥着老视图 查 innodb_trx，缩短事务范围

小结与参考

隔离级别是现象上的约定，一致性视图和版本链是它的实现。读提交每条语句重建视图，可重复读整个事务共用一个，两者都靠 row trx_id 判断版本可见性；更新走当前读，快照读走视图。幻读出在当前读上，行锁管不到还不存在的记录，所以要靠间隙锁补上。选隔离级别时，把能容忍的现象、锁的范围和 binlog 格式放在一起看，比单看性能得失更靠得住。
