Linux 性能（十一）网络问题定位——DNS、抓包、延迟与 DDoS

发表于 2023-09-11 分类于 性能优化
本文字数： 4k 阅读时长 ≈ 4 分钟

引言

网络异常常以几种相似的外壳出现：域名解析忽快忽慢、ping 的 RTT 很低但命令跑了十秒、服务突然连不上、单次请求很快而并发一上来延迟翻倍。它们用到的命令看着差不多，根因分别落在 DNS 配置、名称反查、半开连接和 TCP 小包交互上。这篇按现象把证据链接起来：先确定慢在哪一段，再决定抓哪个端口的包，最后才谈改哪个参数。

四类现象的分界

域名解析是把名字换成 IP。客户端按 /etc/resolv.conf 里配置的地址询问 DNS 服务器，缓存没命中时，服务器从根域开始逐级查 NS 记录，直到权威服务器给出 A 记录。公网延迟、丢包、缓存过期、DNS 服务器负载高，都会让这一步变慢；配置缺失时，查询会直接超时。

工具自身变慢是另一类。ping 输出里每个包的 RTT 都在 30 毫秒左右，汇总却显示总耗时 11 秒，多出来的时间花在把 IP 反查成域名（PTR 请求）上。不少网络工具默认做名字解析，抓包时能看到两次 PTR 请求各自等到五秒超时，第二个包才发得出去。

小包冲击看 PPS 和包长。接收每秒两万多包、每包五十多字节时，带宽占用极低，半开连接表却可能被占满，正常客户端连不上。这类现象的根子在连接状态，链路利用率读数给不出线索。

请求延迟要分开看单次和并发。hping3 测 SYN 到 SYN+ACK 的往返时间只有七毫秒，wrk 压同一台机器却把平均延迟拉到四十多毫秒。差额来自一次请求内部多个分组的交互：服务端等 ACK，客户端等超时，两边各等一次，四十毫秒就堆出来了。

从延迟抖动到抓包

解析超时的排查从配置开始。容器里 nslookup 报 no servers could be reached，ping DNS 服务器却是通的；加 -debug 后会看到请求发给环回地址的 53 端口，再查 /etc/resolv.conf 发现是空文件，补上 nameserver 就能解析。解析慢但能通时，用 ping 量到 DNS 服务器的 RTT：两百毫秒以上还伴随丢包，换一台几十毫秒的服务器，单次解析从十秒降到几十毫秒。仍有秒级抖动，可以在本机起 DNS 缓存服务，把解析地址指向本地，第一次查询走上游，后续命中缓存。

ping 慢而 RTT 正常这一类，用 tcpdump 一边抓包一边跑 ping。-nn 关掉抓包工具自身的名称解析，过滤 DNS 端口和目标 IP，输出里 ICMP 请求和响应只隔三十毫秒，中间夹着两条 PTR 请求没有应答，两条各耗五秒。给 ping 加 -n 禁止反查，总耗时回到两秒。

小包冲击的实验用三台机器：一台跑 Web 服务，一台模拟攻击，一台模拟正常客户端。攻击开始后，正常客户端连接超时；sar -n DEV 1 显示接收 PPS 两万多、吞吐每秒一千多 KB，算下来每包约 54 字节。抓包看到成片的 Flags [S]，netstat 里 SYN_RECV 状态堆到一百多条，源地址集中在同一 IP。按源地址拒绝后，正常请求恢复，延迟从两毫秒涨到一秒多，说明攻击包仍在消耗内核资源。源地址随机时按 IP 拒绝失效，改用限制 SYN 速率、调大半连接队列、减少 SYN+ACK 重试、打开 SYN Cookies。这些手段都只是缓解：报文已经进了服务器，内核协议栈的处理开销还在；带宽被打满的情况要在上游做流量清洗。

请求延迟的排查靠单请求与并发的对比。hping3 测两个端口都在七毫秒左右，wrk 并发一百时，一个端口平均九毫秒，另一个四十多毫秒。抓 8080 端口的包放进 Wireshark，跟随 TCP 流看时序：第一次请求响应很快，第二次请求里客户端收到第一个分组后隔了四十毫秒才发 ACK。这个数字对应延迟确认的超时时间；再用 strace 看压测工具只设了 TCP_NODELAY，没设快速确认，服务端配置里 tcp_nodelay 又是关的。服务端开着 Nagle 等 ACK，客户端等着延迟确认超时，两边互相等。打开服务端的 tcp_nodelay 后，两个分组连续发出，平均延迟回到九毫秒。

dig 与 tcpdump 命令

DNS 这一侧，先看本机配置，再看解析结果和递归路径。-debug 给出查询发给谁，+trace 逐层列出 NS 与最终 A 记录，每一跳后面的耗时能定位是哪一级慢。

抓包这一侧，表达式先按协议和端口收窄，再按地址收窄；-nn 关掉反查，-w 存成 pcap 文件交给图形界面分析。host 表达式可以直接写域名，抓包工具会先解析它。

连接与延迟这一侧，sar 看 PPS 和包长，netstat 按状态统计半开连接，strace 看应用给套接字设了哪些选项。三步分别对应链路、连接表和应用程序。

跳过归因就调参数

解析超时先别判定网络不通：配置缺失时，到 DNS 服务器的 ICMP 完全正常。RTT 低也别急着下判断，工具总耗时里可能藏着反查。几条常见的走偏：

  1. 看到超时就改 DNS 服务器地址。先确认本机有没有 nameserver、查询实际发往哪里，再比较候选服务器的 RTT 和丢包。
  2. 把解析慢全归给网络。缓存未命中会触发递归查询，加上本地缓存或预取后，重复请求的耗时能差一个数量级。
  3. PPS 高就以为是带宽打满。每包五十多字节时，带宽读数很低，真正被占满的是半开连接表；看 SYN_RECV 数量比看 %ifutil 有效。
  4. 单源拒绝当成长久之计。攻击源随机化后按 IP 封禁失效，限速、队列容量和 SYN Cookies 要提前配好；流量型攻击仍需上游清洗。
  5. 延迟一高就动 Nagle 或缓冲区。先用抓包流图确认等待发生在哪一跳，再决定关哪个选项；改完要拿同一组并发参数复测。
现象 先确认什么 证据不足时别做什么
域名解析超时 resolv.conf 与实际查询目标 判定链路不通
RTT 低、命令慢 PTR 请求有没有应答 归因为服务端处理慢
高并发下连接超时 PPS、包长、SYN_RECV 数量 只盯着带宽利用率
并发延迟翻倍 单请求 RTT 与 TCP 流时序 直接调大发送缓冲
攻击源随机 限速与半连接容量 逐条按源 IP 封禁

本篇锚点那组 P99 800 毫秒、CPU 三成的结果，放到这张表上要分开测：单次 RTT 用 hping3，并发延迟用 wrk，两边差距大就抓包看流图。解析、反查、半开连接各走各自的证据链，网络这一层的结论才有依据。

小结与参考

网络问题按现象分四路查：解析看配置和递归路径，工具总耗时看名称反查，连接建不上看 PPS 与半开连接表，并发延迟看单请求 RTT 与 TCP 流时序。dig、tcpdump、sar、netstat、strace 各管一段，抓包前先用表达式收窄范围，-n 关掉工具自己的反查。SYN 攻击只能缓解，报文进到服务器后内核开销已经产生；TCP 选项调整要先看到等待发生的那一跳，改完用同一组并发参数复测。
