Linux 性能（十四）监控体系与综合实战

发表于 2023-09-29 分类于 性能优化
本文字数： 3.2k 阅读时长 ≈ 3 分钟

引言

性能问题有两个难处：一是登录上去时现场已经消失，二是现象相似而根因分散在不同层。前者要靠监控留下历史，后者要靠逐层收窄证据。这一篇把两组综合案例走完：一组是时断时续的丢包，查到 netem 规则、iptables 丢弃和过小的 MTU；另一组是吞吐上不去，连着跨过连接跟踪、工作进程、监听队列和端口复用四道坎。最后把 USE 法、应用黄金指标和监控组件串起来，说明哪些指标该常驻看板。

USE 法与黄金指标

系统监控看资源。USE 法把每种资源的指标压成三类：使用率是服务时间或容量占比，饱和度对应等待队列，错误数是出错事件数。CPU 看使用率、运行队列和硬件错误，内存看用量、换页和 OOM，磁盘看设备忙闲、等待队列和 I/O 错误，网络看带宽、重传和丢包；文件描述符、连接数、连接跟踪这些软件资源也能套同一套。

应用监控看请求。资源使用率低并不能说明应用正常，锁等待或下游 RPC 慢都会拖长响应。核心指标是请求数、错误数和响应时间；再往外补三层：进程资源占用用来和系统资源对齐，服务间调用的频率、错误与延迟用来定位调用链问题，核心逻辑的耗时与错误要靠应用自己暴露。跨服务的调用链用链路跟踪工具串起来，日志提供参数与上下文，指标解决「哪里慢」，日志回答「什么样的请求慢」。

监控系统由采集、存储、查询处理、告警和可视化几块组成。采集有拉模式和推模式，目标动态变化时配合服务发现；时序库按时间追加写入，查询语言支撑告警规则与看板；告警要分组、抑制和静默，否则同类问题会把值班通知淹没。日志侧常用 ELK 或更轻量的 EFK，链路侧用 Jaeger 一类工具。

丢包与吞吐两条证据链

丢包案例从 hping3 开始：发十个 SYN 只收回五个，RTT 在三毫秒到三秒之间跳。包可能丢在链路、网卡环形缓冲、QoS、IP 分片、连接跟踪、端口监听、套接字缓冲或应用层，逐层查比凭猜测快。容器内 netstat -i 没有网卡错误，tc -s qdisc 却显示 eth0 上挂了 netem 规则，丢包率 30%。删掉规则后仍然丢包；netstat -s 里是连接失败、SYN 重传和半连接重置；回到主机查 conntrack，当前 182、上限 262144，排除表满；iptables -nvL 暴露出 INPUT 与 OUTPUT 链各有一条随机丢弃 30% 的规则。删掉两条规则，hping3 恢复零丢包。

故事还没完。curl 访问 HTTP 仍然超时，hping3 却显示端口正常。抓包看到三次握手完成后，三秒内没有 GET，只有客户端发出的 FIN；netstat -i 的接收丢弃数涨到 344。两种工具的差别在于 curl 会携带 HTTP 数据，而 eth0 的 MTU 被设成了 100。改回以太网默认值后，请求正常返回。验证工具只覆盖到端口，就不足以宣布问题解决。

吞吐案例里，wrk 压 Nginx 加 PHP，初始每秒 189 个请求，响应全部异常。ss -s 显示大量 TIME_WAIT，dmesg 报 table full，连接跟踪上限与当前值都是 200；调大上限后吞吐到 5382，但四万多个响应仍异常。Nginx 日志里的 499 指向服务端处理太慢，PHP 日志提示 max_children 只有 5；调到 20 后成功请求从八千多涨到一万五。继续查 netstat -s，监听队列溢出次数持续上涨，ss -ltnp 里监听队列只有 10，调大应用 backlog 与系统 somaxconn。

队列修好后响应又全部失败，Nginx 报 EADDRNOTAVAIL，临时端口范围只有 50 个。扩到一万多个端口后异常响应很少，但读错误增多；top 里系统 CPU 接近一半，火焰图热点落在 inet_hash_connect 和 __init_check_established。ss -s 显示三万多个 TIME_WAIT 仍占着端口，tcp_tw_reuse 处于关闭状态；打开后吞吐稳定在五千多，异常响应清零。

ss 与火焰图命令

两组案例用的命令按层次分：网卡与协议栈统计看 netstat，队列与连接状态看 ss，内核配置与日志看 sysctl 和 dmesg，规则看 tc 与 iptables，收发时序靠 tcpdump，CPU 热点用 perf 加火焰图。每改一处都要用同一组参数重测，否则无法判断这一步是否有效。

指标堆叠的报警噪声

监控建起来以后，常见的问题是指标太多、告警太碎。几条走偏：

  1. 只看使用率就下结论。使用率低时应用仍可能卡在锁或下游调用上，配合饱和度和错误数一起看。
  2. 把系统指标套到应用上。应用该盯请求数、错误率和响应时间，资源指标用于关联，不能替代黄金指标。
  3. 告警规则逐项建。同类告警不分组、不抑制，高峰时通知会把真正的问题盖住。
  4. 验证只做到端口通。hping3 能通只覆盖到端口，HTTP 能否响应要另行验证；curl 依旧超时就继续抓包看时序。
  5. 一次优化改多项配置。改动堆在一起，复测结果无法归因到具体参数，回滚也无从下手。
走偏做法 补什么证据 边界
只看使用率 队列长度、错误数 资源指标不替代应用指标
全量指标上报 黄金指标优先 辅助指标进看板不进告警
端口可达即结束 真实请求加抓包 协议层验证要覆盖负载
一次改多项 每次只改一处并复测 保留回滚路径
日志与指标二选一 指标定位、日志补上下文 跨服务再补链路跟踪

监控与排查速查表

层次 关键指标 常用工具 处置方向
CPU 使用率、运行队列、错误 top、pidstat、perf 找热点函数与等待原因
内存 用量、换页、OOM free、vmstat、dmesg 区分回收、Swap 与限额
磁盘 I/O 使用率、await、队列 iostat、pidstat、fio 先定瓶颈再找写出者
网络 丢包、重传、PPS netstat、ss、sar、tcpdump 逐层收窄丢包位置
应用 请求数、错误率、响应时间 链路跟踪、应用监控 用拓扑找异常组件
日志 参数与错误上下文 ELK / EFK 与指标时间线对齐

本篇锚点那组 P99 800 毫秒、CPU 三成的结果，到这里可以走完整条路：先用 USE 法和黄金指标判断资源与应用哪边异常，再按层次取证据、逐项改动并复测；问题消失后把对应指标写进看板和告警，下次发生时才有历史可查。

小结与参考

丢包排查按协议栈逐层收窄，网卡统计、tc 规则、协议汇总、conntrack、iptables、抓包时序和 MTU 各给一段证据；吞吐排查按连接跟踪、工作进程、监听队列、端口范围、端口复用依次推进，每改一处都用同一组压测参数验证。监控侧用 USE 法覆盖系统资源，用请求数、错误率和响应时间覆盖应用，采集、存储、查询、告警与展示连成闭环，再以日志补上下文、链路跟踪串起跨服务调用。
