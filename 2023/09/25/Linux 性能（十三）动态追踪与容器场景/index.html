Linux 性能（十三）动态追踪与容器场景

发表于 2023-09-25 分类于 性能优化
本文字数： 3.6k 阅读时长 ≈ 3 分钟

引言

有些问题靠指标找不到答案：容器里的应用启动一次要二十多秒，日志却显示一切正常；内核线程占着三成 CPU，进程级工具挂不上去。前者要从容器边界和 cgroup 限额看，后者要直接观察内核函数的执行路径。这篇把动态追踪的事件源和工具摆在一起，再用两组实验说明怎么把「慢」拆到某个函数、某段等待，最后交代调试符号、开销和容器场景的边界。

动态追踪的事件源

动态追踪在系统正常运行时通过探针采集行为，不用改代码、不用重启服务。事件源分三类：硬件事件来自性能监控计数器，覆盖缓存、指令周期、分支预测；静态探针事先写进代码，常见的有内核跟踪点和用户态的 USDT；动态探针在运行时挂到函数入口或返回处，内核侧叫 kprobes，用户态叫 uprobes。

USDT 要求应用自己埋点，数据库类软件常内置；kprobes 与 uprobes 可以在运行时挂到任意函数，灵活性更高，代价是要拿到符号。工具建立在探针之上。ftrace 通过 /sys/kernel/debug/tracing 下的文件交互，function_graph 能给出调用关系；perf 采样事件，也能用 perf probe 加自定义探针；eBPF 在内核里跑自定义程序，BCC 把编译和加载包装成 Python 接口；SystemTap 把脚本编译成内核模块再插入；sysdig 面向容器场景。多数性能问题用 perf 加火焰图就够，需要按 I/O 大小这类维度做统计时再写脚本。

常见动态追踪场景与推荐工具

容器冷启动的等待分布

一个容器化应用启动后，客户端先收到连接重置，等待二十多秒才拿到一次响应，随后容器退出。docker logs 里只有启动完成的记录，看不出原因；docker inspect 显示 OOMKilled 为真、退出码 137。内核日志进一步指出，OOM 发生在 cgroup 内存限制处：容器限额 512 MB，进程匿名内存加页内存已经顶到 524 MB。

再看 JVM 的堆设置，最大堆接近 2 GB。容器内部看到的可用内存仍是主机规格，运行时按主机内存推算堆上限，和 cgroup 限额对不上。显式给堆设置与容器限额一致的上限后，应用能稳定响应。这里的判断依据是容器边界：限额写在外层，进程看到的是另一套数字。

启动仍然要二十多秒。top 里 CPU 总体空闲，java 进程只占一成；在启动过程中用 pidstat -t 看线程，部分线程的等待列接近 97%，CPU 使用列却很低。容器的 CPU 份额被设成 0.1 个核，线程大量时间耗在等调度。把份额提到一个核，同样的应用两秒启动完成。去掉限额能让容器跑得更快，代价是任何应用异常都可能拖垮整机，这个交换通常不划算。

冷启动拆开看还有更多段落：事件触发、资源调度、镜像拉取、网络配置、应用启动。用链路跟踪记录每段耗时，找出占大头的那一段；镜像拉取慢就缓存热点镜像，网络配置慢就预分配资源，调度和启动慢就复用预创建的容器。跨段的耗时数字比单点火焰图更适合定位冷启动。

perf 与火焰图命令

内核线程高 CPU 这一类，先看线程属于谁。kthreadd 是内核线程的管理者，ksoftirqd 每核一个，kswapd0 管回收，kworker 跑工作队列，jbd2 管文件系统日志。名称在 ps 输出里带中括号。pstack 挂不上内核线程，/proc/<pid>/stack 只给几层通用栈，这时用 perf 采样。实验用两台机器，一台跑服务，另一台发小包压测：两个 CPU 的软中断占比都超过三成，进程列表最前面是 ksoftirqd。

服务端与压测客户端的实验拓扑

火焰图从下往上看，下面一层是上面一层的父调用；同一层按函数名排序，宽度对应采样占比。展开最宽的那条路径，能看到收包、网桥、Netfilter 到转发的连续调用，其余小火焰里还有 TCP 与连接跟踪的函数。报告里的热点调用链从 net_rx_action、netif_receive_skb 到 br_handle_frame、br_nf_pre_routing，再经 br_pass_frame_up 到 ip_forward。收包、网桥、Netfilter 钩子连在一起，对应容器网络经 veth 到 docker0 网桥的路径；结合压测端发出的 SYN 小包，软中断升高就有了具体来源。

容器、veth、docker0 网桥与 DNAT 规则的位置

需要看某个函数的参数或返回值时，用 perf probe 挂动态探针；perf trace 提供系统调用视图，走的是内核事件，开销比基于 ptrace 的 strace 小。ftrace 的五步操作可以用 trace-cmd 收成两条命令。

追踪工具的适用边界

追踪本身会改变被测对象，符号和数据量也会限制结论。几种常见的走偏：

  1. 高并发进程上长期挂 strace。它基于 ptrace，事件多时内核态与用户态切换频繁，还会用信号挂起目标进程；性能敏感的服务改用 perf trace。
  2. 没有调试符号就下结论。输出里只有十六进制地址，函数名和参数都看不到；内核要装调试符号包，应用要用带符号的二进制或源码加 -g 重新编译。
  3. 把火焰图当作时间顺序图。横轴是采样占比，纵轴是调用栈，图里没有任何时间先后信息；要看时序得回到抓包或链路跟踪。
  4. 生产环境全量长时间追踪。事件量越大开销越明显，先收窄到进程或函数，采完就关。
  5. 启动慢就去掉资源限额。限额能防单容器拖垮整机，调整时要同步核对运行时自己的上限。
场景 合适工具 限制
内核函数调用关系 ftrace、trace-cmd 需要 debugfs 挂载点
热点函数与调用栈 perf、火焰图 缺少符号时只有地址
函数参数与返回值 perf probe、BCC 依赖调试信息
自定义统计维度 eBPF、SystemTap 开发成本与兼容性
容器进程与网络 sysdig 与宿主机命名空间相关

现象 先看什么 再追什么
容器启动慢或退出 inspect 退出码、dmesg 运行时内存上限、CPU 份额

本篇锚点那组 P99 800 毫秒、CPU 三成的结果，如果指标层解释不了，就换一个观测角度：容器里看 cgroup 限额与运行时配置是否一致，内核线程高看 perf 采样出的热点函数。两条路都要先拿到证据，再决定改配置还是改代码。

小结与参考

动态追踪靠探针在系统正常运行时取样，硬件事件、静态探针和动态探针覆盖不同观测点；ftrace 适合看函数调用关系，perf 加火焰图适合找热点，eBPF 与 SystemTap 用于自定义统计，容器场景可用 sysdig。容器问题要先看 cgroup 限额与进程自身配置是否对齐，内核线程问题要用 perf 绕过进程级工具。调试符号、追踪开销和时间维度的缺失，都会影响结论，读结果时一并考虑。
