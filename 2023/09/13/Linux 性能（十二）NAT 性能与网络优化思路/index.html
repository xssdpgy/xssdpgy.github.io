Linux 性能（十二）NAT 性能与网络优化思路

发表于 2023-09-13 分类于 性能优化
本文字数： 3.4k 阅读时长 ≈ 3 分钟

引言

同一台服务，用主机网络跑压测能到每秒六千多请求，换成走端口映射的容器，每秒只剩几十个请求，连接建立时间从一百多毫秒涨到一秒以上。两边的应用代码和机器规格都没变，差别在报文经过网关时要改写地址，还得查一张连接跟踪表。这篇先把 NAT 的开销落在哪个环节说清楚，再用丢包点和调用栈还原一次完整的定位，最后按协议层列出可选的优化手段和各自的代价。

NAT 与连接跟踪

NAT 改写 IP 包的源地址或目的地址，让多台内网机器共享出口 IP。静态 NAT 做一对一固定映射，动态 NAT 从地址池里挑，日常最常见的是带端口的 NAPT：SNAT 在发包时替换源地址和源端口，DNAT 在收包时替换目的地址和目的端口，两者一起用就形成双向的一对一映射。Linux 上这些规则由 Netfilter 框架执行，iptables 是配置入口；NAT 规则写在 nat 表，SNAT 与 MASQUERADE 挂 POSTROUTING 链，DNAT 挂 PREROUTING 链。转发还得打开 IP 转发选项。

改写地址要依赖连接跟踪模块 conntrack。它用一张哈希表记录每条连接的协议、地址和端口，回包才能找到对应的原始连接。这张表是 NAT 的实现基础，也是性能成本所在：每条新连接要查表和分配跟踪对象，表项满了会直接丢包。哈希表大小由 nf_conntrack_buckets 决定，最大记录数由 nf_conntrack_max 决定，两者的比值决定链表长度；调大上限意味着更多内存，调小则容易在并发高峰撞到天花板。MASQUERADE 是最常见的出口规则，多个内网地址转成同一个公网地址时，源端口可能被重新分配。连接按五元组区分，内网地址不同，端口相同也能共存；出口侧可用的端口数、连接跟踪表和带宽都在同一条链上，其中一项见顶就会拖住整体。

连接表打满的证据链

实验用两台机器，一台跑服务，一台用 ab 压测。先用主机网络起服务，并发五千、总请求十万，得到每秒六千五百多请求、平均延迟七百多毫秒的基线。换成做端口映射的容器后，两秒超时的压测只完成五千多个请求；把超时放宽到三十秒，结果变成每秒七十多个请求，平均延迟六十五秒。延迟涨了几十倍，先怀疑内核里有丢包。

用动态追踪脚本挂在 kfree_skb 上统计丢包位置，输出里一万多个包丢在 nf_hook_slow，只有几百个丢在 tcp_v4_rcv。这个名字指向 Netfilter 的钩子函数，范围缩到 NAT 相关路径。接着用 perf record 抓调用栈，在报告里找 nf_hook_slow，三条主要路径浮出来：连接跟踪的 ipv4_conntrack_in、网桥转发的 br_nf_pre_routing、做 DNAT 的 iptable_nat_ipv4_in。三处开销都落在内核态，方向转向连接跟踪配置。

flowchart TD
    A["压测吞吐骤降"] --> B["追踪 kfree_skb 找丢包点"]
    B --> C["nf_hook_slow 占大头"]
    C --> D["perf 展开调用栈"]
    D --> E["conntrack、网桥、DNAT"]
    E --> F["查 nf_conntrack_max 与内核日志"]
    F --> G["调表项上限后复测"]

查 sysctl 发现最大连接跟踪数只有一千，而压测并发是五千；dmesg 里已经出现 nf_conntrack: table full, dropping packet。把上限调到十三万、哈希表保持六万五千多，再用原来两秒超时的参数重跑，吞吐回到每秒六千三百多，接近无 NAT 的基线；建连延迟仍高一倍，这段差额就是连接跟踪的成本。

调大之前要算内存。表项对象和链表项各有固定大小，上限乘以对象大小加上桶数乘以链表项大小，就是大致占用；一千个表项配六万多桶只有一点几 MB，调到十三万就要按同样公式重算。表里的内容可以用 conntrack -L 看，压测时按状态统计，TIME_WAIT 记录堆到九千多条，绝大多数来自同一客户端 IP，默认超时一百二十秒。连接规模长期很大时，缩短超时能腾出表项，代价是对端迟到的报文可能被丢弃或归到新连接上。

conntrack 与 perf 命令

先看配置与内核日志，再抓丢包位置和调用栈，最后核对表内状态分布。四步分别回答「上限多少」「丢在哪里」「谁在耗时」「表里装了什么」。

参数调整的常见顺序

定位到瓶颈之前，调参数容易变成逐项试错。几种常见的走偏：

  1. 吞吐掉了就加套接字缓冲。缓冲区能吸收突发，也会拉长排队时间；连接表打满时，加缓冲只会让等待更久。
  2. 看到 table full 就把上限拉到极大。表项占内存，链表过长会拖慢查找；先估算内存和并发峰值，再定上限与桶数的比例。
  3. 把无状态映射也跑成有状态 NAT。固定 IP 和端口的映射场景，可以用 tc 或基于用户态的方案绕过 conntrack，省掉每次查表的开销。
  4. TCP 选项叠着开。Nagle 配延迟确认会互相等；NAT 服务器上的端口回收类选项容易引发连接失败，改之前先确认场景。
  5. 忽略叠加网络的 MTU。VXLAN 在原始报文外多包一层，包长变大后触发分片，吞吐会掉；链路设备与虚拟网卡的 MTU 要一起调。
现象 先确认什么 不宜直接做什么
压测吞吐骤降 丢包点、连接跟踪上限 无差别调大缓冲区
conntrack 表满 并发峰值、桶数、内存预算 把上限设成极大值
建连延迟偏高 表项状态分布、超时设置 反复重启服务
小包吞吐低 网卡队列、软中断分布 只盯带宽读数
叠加网络延迟高 封装后的 MTU 与分片 只改应用发送缓冲

网络优化层次速查表

优化目标随场景变化：网关看 PPS，缓存和数据库看延迟，Web 服务两头兼顾。目标定下来，再按协议栈从下到上取基准、找瓶颈、改配置。

层次 主要手段 代价或适用条件
应用 epoll、多进程或多线程模型、长连接、压缩负载、缓存与 DNS 缓存 长连接要管空闲回收
套接字 收发缓冲按带宽乘延迟估算；TCP_NODELAY、TCP_CORK 按场景选 缓冲越大排队越久
传输层 TIME_WAIT、SYN、Keepalive 相关参数；UDP 按 MTU 定包长 参数之间可能互相冲突
网络层 打开转发、反向校验、调整 MTU、限制 ICMP 叠加网络要同步改两端
链路层 中断亲和性、RPS/RFS、多队列、TSO/GSO/GRO/RSS、QoS 转发场景慎用合并卸载
极限场景 DPDK 用户态轮询、XDP 协议栈前处理 开发和维护成本高

小结与参考

NAT 的开销来自两处：Netfilter 钩子改地址，conntrack 维护连接状态。压测吞吐骤降时，沿丢包点、调用栈、内核日志、表内状态这条链往下查，比逐项调参数更有效；表项上限要按并发和内存一起算，调完用同一组压测参数复测。再往上的优化按协议层展开：应用改 I/O 与工作模型，套接字按带宽乘延迟定缓冲，传输层和网络层调连接与分片参数，链路层分摊中断并合理卸载。这些方法用尽仍不够，才考虑 DPDK 或 XDP 绕过协议栈。
