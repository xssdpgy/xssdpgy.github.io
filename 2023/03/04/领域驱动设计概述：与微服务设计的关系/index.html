领域驱动设计概述：与微服务设计的关系

本篇从一次按数据表拆服务的改造说起，说明 DDD 在拆分决策里的位置，以及哪些情况下不值得用它。

某电商系统原本是一个单体应用，一张库里躺着 order、order_item、stock、coupon、payment、shipment 等十余张表。团队决定「上微服务」，按数据表拆成八个服务，两周内完成了部署拆分。

上线三个月后出现三个典型症状：

  • 一次下单要串行调用库存、优惠、订单、支付、履约五个服务，链路长、故障点分散；
  • 「优惠券能否与满减叠加」这条业务规则，一半写在 order-service 的应用服务里，一半写在 promotion-service 的 Controller 里，改一次规则需要两个团队联调；
  • 库存扣减逻辑同时存在于 stock-service 与 order-service，超卖时无法判定哪一处是权威。

于是代码往往长成这样——服务拆开了，业务逻辑却仍散落在调用方：

这里真正出问题的不是注册中心、网关或 RPC 框架，而是没人能说清业务的边界在哪里。按表拆、按技术层拆、按团队人数拆，都是用技术或组织维度去替代业务维度。服务数量成了目标，边界反而成了事后补的解释。

微服务架构本身并不提供边界的判定方法。这正是 DDD 被引入微服务设计的原因。

概念界定

领域驱动设计（DDD） 是一套以业务领域为起点的设计方法：通过建模把复杂业务切分为边界清晰的领域，建立团队共用的语言，并让业务模型与代码模型保持一致。它既不是架构规范，也不绑定任何框架；单体应用同样可以使用它。2004 年 Eric Evans 在《Domain-Driven Design》中系统提出这套方法，此后长期只在高复杂度业务中少量实践，直到微服务需要一套边界判定方法，才被大规模引入。

DDD 分为两个部分：

  • 战略设计：从业务视角出发，梳理业务流程与领域对象，聚类出聚合与限界上下文，产出领域模型与边界。
  • 战术设计：从实现视角出发，把领域模型落成聚合根、实体、值对象、领域服务、资源库等代码对象。

其中边界分两层，它决定了建模与拆分的粒度：

flowchart TB
    subgraph CTX["限界上下文：交易（物理边界候选）"]
        subgraph AGG1["聚合：订单（逻辑边界）"]
            ROOT["订单 Order（聚合根）"] --- ITEM["订单项 OrderItem（实体）"]
            ROOT --- ADDR["收货地址 Address（值对象）"]
        end
        subgraph AGG2["聚合：支付单（逻辑边界）"]
            PAY["支付单 Payment（聚合根）"] --- TXN["支付流水（实体）"]
        end
    end

聚合是业务一致性边界：同一聚合内的对象在同一事务中变更，由聚合根统一对外；这是逻辑边界，通常运行在同一进程内。限界上下文是语义与模型的适用边界：同一个词在不同上下文里可以有不同的含义与模型；它通常对应独立的代码库、数据库与部署单元，是物理边界的候选。

至于微服务，它是一种架构风格，关注运行时：进程间通信、容错与故障隔离、去中心化的数据与服务治理，以及独立开发、测试、构建和部署。

两者关系可以压缩成一条链路：

flowchart LR
    A["业务领域"] --> B["事件风暴：发散出命令、事件、实体"]
    B --> C["聚类收敛：形成聚合与限界上下文"]
    C --> D["领域模型：两层边界确定"]
    D --> E["微服务边界：拆分方案"]
    D --> F["代码模型：目录与对象映射"]

一句话：DDD 产出边界，微服务消费边界。前者是设计方法，后者是架构风格；两者都强调从业务出发，并随业务演进持续调整边界与代码，也就是演进式架构。

案例推演

把贯穿案例按上述链路走一遍。

第一步，列出业务事实，而不是先画服务。 订单履约过程中的关键动作与事件是：用户提交订单 → 订单已创建 → 库存已锁定 → 支付已完成 → 发货单已生成 → 订单已完成。同时记录参与者与命令：「用户 / 提交订单」「支付网关 / 回调支付结果」「仓库 / 触发发货」。这个阶段追求发散和穷举，不讨论服务怎么分。

第二步，把紧密相关的对象聚合成一致性单元。 订单与订单项必须同生共死，收货地址依附于订单且无独立标识，因此归入「订单聚合」，订单为聚合根；支付单与支付流水归入「支付单聚合」；SKU 的可用库存归入「库存聚合」。聚合内部的规则由聚合根把守，例如「已支付订单不允许修改收货地址」。

第三步，按语义边界归入限界上下文。 「库存」在交易语境里是「可售数量」，在仓储语境里是「货位与批次」，两者模型不同，应拆开；支付涉及外部渠道与对账，独立成上下文；发货之后的物流轨迹属于履约上下文。由此得到的服务清单是推导结果：

限界上下文 建议服务 核心聚合 数据存储
交易 order-service 订单 独立库
支付 payment-service 支付单 独立库 + 对账表
库存 inventory-service SKU 库存 独立库
履约 fulfillment-service 发货单 独立库

与开篇的按表拆分相比，差别不在服务数量，而在每条业务规则都有唯一归属：叠加规则属于交易上下文内的促销规则，「可售数量」的扣减权威属于库存聚合。跨上下文的协作通过领域事件完成，例如「支付已完成」触发发货单创建，而不是在订单服务里直接调用发货接口。

这里有一个容易被忽略的结论：限界上下文与微服务不必一一对应。一个上下文在业务早期可以由一个服务承载，也可以在演进中拆分；反过来，若两个上下文始终同生命周期、同团队、同发布节奏，合并部署往往更经济。边界先于部署单元，部署单元服务于边界。

反模式与适用边界

  1. 服务越小越好。 把服务数量当 KPI，导致分布式事务、链路追踪和联调成本超过拆分收益。
  2. 用框架替代设计。 引入注册中心、网关、配置中心就宣称完成微服务化，边界仍按数据库表划分。
  3. 先定服务再补模型。 服务已经上线，再回头补领域模型，模型只能用来给既有拆分做解释，失去指导意义。
  4. 只做战略、不做战术。 限界上下文画得很漂亮，代码依旧是事务脚本，模型与实现脱节，半年后文档失效。
  5. 把 DDD 当作所有系统的默认选项。 战术设计对团队能力有要求，落地成本不低。

以下情形建议不采用完整 DDD，或只采用其中的战略设计部分：

情形 建议
以 CRUD、报表、数据搬运为主，业务规则少且稳定 传统分层即可，无需领域建模
一次性交付、后续不再演进的系统 战略设计收益有限
领域专家无法参与，需求只能靠文档传递 先补齐沟通机制，不急于建模
团队尚无战术设计经验、又无演进计划 先做限界上下文划分，暂缓聚合与事件风暴落地
验证性原型、短期活动页 直接实现，保留重构空间

判断标准可以简化为一问：这个系统的复杂度主要来自业务规则，还是来自技术规模？ 前者适合 DDD，后者优先解决工程问题。

要点速查

概念 关注点 主要产出 常见误区
DDD 业务复杂性 领域模型、边界 被当成架构规范或框架
战略设计 业务视角 子域、限界上下文、聚合划分 只画图不落地
战术设计 实现视角 聚合根、实体、值对象、资源库 代码与模型两套语言
限界上下文 语义边界 服务边界候选 与微服务强行一一对应
聚合 一致性边界 事务范围、聚合根 设计成大聚合，锁竞争严重
微服务 运行时与部署 独立进程、独立数据、独立发布 拆得越细越好

一条主线：业务事实 → 领域对象 → 聚合（逻辑边界）→ 限界上下文（物理边界候选）→ 微服务 → 代码目录。

小结与参考

微服务拆分的困难，本质是缺少一套从业务出发判定边界的方法。DDD 的战略设计提供这套方法，战术设计保证边界能传导到代码；微服务则负责边界确定之后的运行与治理。三者不在同一层次，也就不存在「DDD 和微服务二选一」的问题。
