领域事件：微服务解耦与最终一致性

发表于 2023-03-21 分类于 架构设计
本文字数： 6.6k 阅读时长 ≈ 6 分钟

引言

本地事务提交成功、消息却没发出去，是跨服务链路里最隐蔽的一类故障。本篇讲领域事件：进程内事件与跨服务事件的差别，Outbox 怎样把业务提交和事件发布收进同一个事务，以及幂等与乱序的收敛办法。

支付回调服务在灰度发布当晚被重启了一次。重启前那几秒里，有 37 笔订单的本地事务已经提交、状态改成「已支付」，进程却在把「支付已完成」写进消息队列之前被 kill 掉。结果：支付上下文显示收款成功，履约上下文始终没收到发货指令，次日客服按「已付款未发货」逐单手工补发，其中两笔因重复补发又触发了退款。

出问题的代码只有一行位置不对：

消息发在事务内，事务一旦回滚，下游会为未成立的支付发货；发在事务外，提交后崩溃就永久丢消息。业务数据在数据库、消息在中间件，两个资源没有共同的事务边界，这类「双写」不可能靠重试补干净——因为重放时无法区分「没发过」和「发过但没记录」。

根因不是消息队列不可靠，而是把一次业务事实拆成了两次没有原子性的写。

概念界定

领域事件是领域内已经发生、且会触发后续业务动作的事实，用过去时命名：OrderCreated、PaymentCompleted、StockRejected。它携带两类数据：事件元数据（全局唯一事件 ID、发生时间、事件类型、事件源）和事件发生那一刻的业务快照。事件一旦产生即不可变，订阅方拿到的是快照，不回查发布方——这条约束决定了后面所有的可靠性设计。

按作用范围分两类，实现机制完全不同：

  • 进程内事件：发生在同一服务内不同聚合之间，由事件总线在同一进程分发，可同步可异步，通常不引入消息中间件；同一本地事务即可覆盖发布方与订阅方。
  • 跨服务事件：发生在限界上下文之间，必须经过消息中间件，发布方与订阅方各有独立事务，只能最终一致。

进程内事件的价值是解耦同一服务内的聚合；跨服务事件的价值是解耦服务与发布节奏。后者才是微服务里真正需要认真设计事务边界的地方：发布方提交后即返回，不等待订阅方成功，因此必须自己保证「该发的事件一条不丢」。

案例推演

把开头那 37 笔订单的时间线摊开：

  • t0，支付应用服务开启本地事务，写 payment 与 payment_txn，提交。
  • t1，准备发送 PaymentCompleted。
  • t1+，进程被 kill。

消息若在 t0 之前发出，回滚后下游凭空发货；在 t0 之后发出，则永久丢失。两种顺序都不可接受，因为 payment 表与消息队列之间缺少第三个能记录「该发什么」的地方。补上即可：在同一本地事务里，把待发事件作为一行写进业务库。业务提交成功，这行一定在；业务回滚，这行一定不在。再由独立投递任务把它搬到消息队列。这就是本地消息表 / Outbox。

两者常被混用，取舍其实清晰：

方案 一致性保证 投递方式 运维成本 适用
本地消息表 业务 + 事件同本地事务 定时轮询扫表 低，一个任务即可 中小流量、事件量可控
Outbox + CDC 同上 捕获 binlog 高，需维护解析链路 高吞吐、低延迟
共享事件库 需分布式事务 应用直发 高且性能差 不推荐
事务内直发消息队列 无原子性 应用直发 低 禁止

本地消息表是一张通用 event_message 表，存序列化事件体、状态与重试次数，投递任务扫未发送行，成功后改状态；优点是与业务语义无关，缺点是要轮询，且对账时得靠事件 ID 反查。Outbox 与之同源，但强调事件由聚合根在状态变更时以不可变快照写入，并常配合 CDC（捕获数据库日志）而非轮询投递，延迟更低、不给业务库加轮询压力，代价是要引入并维护 binlog 解析链路。共享事件库把事件单独放一个库，业务库与事件库跨库，必须分布式事务才能一致，性能与复杂度都更差。取舍可以压缩成一句：能用本地事务把业务与事件绑在一起，就不要引入任何跨资源的一致性机制。

消息中间件给出的是「至少一次投递」，重复与乱序都要在消费侧兜住。

  • 幂等：以全局事件 ID 建唯一约束的去重表，消费前先插去重行，插入冲突即判重丢弃；去重行与业务写入放同一本地事务，避免「记了重、业务没做」。支付回调重复、投递重试、消费者重启重放，是三类最常见的重复来源。
  • 乱序：PaymentCompleted 完全可能早于 OrderCreated 抵达履约上下文。用状态机校验而非到达顺序：发货单只能从 WAIT_PAY 经 PAID 流转，收到支付事件时若订单快照尚未落地，先落一条待处理记录，等订单事件到来再推进；或由事件携带聚合版本号做 CAS，版本落后的事件直接丢弃。

修复后的时序如下：

sequenceDiagram
    participant P as 支付应用服务
    participant DB as 支付库（业务表 + Outbox）
    participant R as 投递任务
    participant MQ as 消息中间件
    participant F as 履约应用服务
    P->>DB: 本地事务写支付流水 + Outbox 行
    DB-->>P: 提交成功
    R->>DB: 扫描未投递行
    R->>MQ: 发送 PaymentCompleted
    MQ-->>R: ack
    R->>DB: 标记已投递
    MQ->>F: 投递（至少一次）
    F->>F: 去重表插入 eventId
    alt 首次消费
        F->>F: 本地事务生成发货单
    else 重复投递
        F->>F: 唯一键冲突，丢弃
    end

投递任务只做一件事：把 Outbox 里未投递的行搬到消息队列并标记，失败就重试，从不反向修改业务数据。发布方因此可以在事务提交后立即返回，履约侧何时处理完，与支付接口无关。

反模式与适用边界

  1. 事务内直发或提交后裸发。 两个资源没有原子性，回滚与崩溃各留一类脏数据，且无法靠重试区分。
  2. 把事件当同步查询用。 发布方发完就等订阅方回写结果，异步链路被重新拉成同步，超时与级联失败一并回归。
  3. 事件里塞可变对象引用、让订阅方回查发布方。 发布方数据一变或一下线，历史事件无法重放，对账失去依据。
  4. 消费者不幂等。 把「至少一次」当「恰好一次」，重试一次就多发一次货、多扣一次款。
  5. 事件粒度过细或没有业务语义。 把 FieldChanged 这类技术变更当领域事件，订阅方拿到字段差异而非业务事实，无法驱动流程。

以下情形建议不采用基于事件的最终一致：

情形 建议
扣款与入账必须同时成功、不允许中间态 同一聚合的本地事务同步完成，不引入事件
下游需要发布方实时结果才能继续 直接同步调用，别用事件伪装异步
团队尚无去重表、补偿任务与事件对账 先补基础设施，否则「最终一致」只是「最终不一致」
事件量极小、只有一个订阅方、同进程可完成 进程内事件总线或直接方法调用，不必上消息中间件
无法接受秒级延迟的强实时校验（如秒杀库存） 同步校验 + 本地事务，事件只用于事后通知

判断线：领域事件换来的是解耦与削峰，代价是中间态、补偿与运维复杂度；没有对账与补偿能力，最终一致只是一个好听的说法。

要点速查

维度 进程内事件 跨服务事件
范围 同一服务、聚合之间 限界上下文之间
通道 事件总线 消息中间件
事务 可同一本地事务 发布方 / 订阅方各自独立事务
一致性 可强一致 最终一致
是否需要 Outbox 通常不需要 必需
幂等与乱序 压力小 必须显式处理
问题 手段
业务与事件的原子性 本地消息表 / Outbox，同本地事务
重复投递 事件 ID + 去重表唯一键
乱序到达 状态机校验 / 聚合版本号 CAS
投递可靠性 独立投递任务重试 + 状态标记
事后核对 事件持久化 + 按事件 ID 对账

小结与参考

跨服务通信解耦的关键，不是选哪个消息中间件，而是让「业务发生了什么」与「把这件事告诉别人」共享同一个事务边界。本地消息表 / Outbox 用一张同库的表解决了这件事；幂等与状态机则把「至少一次投递」收敛成可预期的业务结果。开篇那 37 笔订单的修复没有改动消息队列的任何配置，只是在本地事务里多写了一条 Outbox 记录——多数分布式一致性问题，本质是本地事务边界没画对。
