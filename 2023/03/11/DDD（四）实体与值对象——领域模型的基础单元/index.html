DDD（四）实体与值对象——领域模型的基础单元

发表于 2023-03-11 分类于 架构设计
本文字数： 5.9k 阅读时长 ≈ 5 分钟

引言

一个地址字段选型错了，发货单、售后单和历史快照会一起跟着变。本篇讲实体与值对象的分界：什么时候该用唯一标识，什么时候用不可变的值，以及值对象在关系库里怎么存。

客服对不上账：用户三天前下的订单，详情页里的收货地址变成了他昨天新改的地址。发货单、售后单、当时的快照全跟着变了。排查下来，地址被建成一张带主键的表，订单只存了一个 address_id，指向那一行可随时 update 的记录。

代码没有 bug，事务也正常。问题在建模：地址在这里没有独立生命周期，它只是”这一单送到哪里”的描述，却被赋予了标识和可变状态。任何一次改动都会沿着 address_id 回溯到全部历史，而历史本不该被改写。

结论先行：判断一个概念靠标识区分、还是靠值区分，决定了它会不会被别处的修改牵连。需要追踪”是不是同一个”、且会独立变化，用实体；只描述”是什么样的”、没有独立生命周期，用值对象。 值对象一旦不可变、只做整体替换，历史就自然被固定在下单那一刻。

概念界定

实体靠唯一标识区分，标识在历经状态变更后保持一致；重的是延续性而非属性，属性可变，业务逻辑内聚在实体（充血模型）中。订单、支付单、发货单都是实体——改了金额、改了状态，它仍是同一单。

值对象靠属性值识别，没有标识，不可变，把若干相关属性收成一个概念整体；相等性由全部属性决定，要改就整体替换，不就地修改，因而对协作对象没有副作用。Money、Address、OrderId、SkuId 都是值对象。

取舍只有一句话：有身份、要留痕、会独立变化 → 实体；无身份、只描述、可整体替换 → 值对象。

classDiagram
    class Order {
        <<实体 聚合根>>
        +OrderId id
        +OrderStatus status
        +changeAddress(Address) void
        +totalAmount() Money
    }
    class OrderItem {
        <<实体>>
        +Long id
        +SkuId skuId
        +subtotal() Money
    }
    class Address {
        <<不可变值对象>>
        +String province
        +String city
        +String detail
    }
    class Money {
        <<不可变值对象>>
        +BigDecimal amount
        +Currency currency
        +plus(Money) Money
    }
    Order "1" *-- "0..*" OrderItem
    Order "1" *-- "1" Address
    OrderItem ..> Money
    Order ..> Money

实体有延续性，Order 里 changeAddress 换掉的是整个 Address，不是修改它的某个字段；值对象没有这条时间线，它只是某一刻的一个取值。

案例推演

把订单履约里的对象过一遍，归属其实很稳定：

领域对象 归属 理由
Order、PaymentInstruction、ShipmentOrder 实体 有唯一标识，状态跨多次变更，需要被追踪
OrderItem 实体 依附订单但需单独标识，行级优惠与退货都按行追溯
Money、Address、OrderId、SkuId、Quantity 值对象 只描述，无独立生命周期，改即整体替换

三条判断比背定义管用：

  1. 是否需要独立标识。 两张一百元没有区别，两张订单有。
  2. 是否会独立变化且变化要留痕。 订单状态从”已创建”到”已支付”，是同一对象的一段历史；收货地址从 A 改成 B，是换了一个值，不该留下”地址被改过”的历史。
  3. 是否被多处引用且共享可变状态。 一旦多个对象指向同一份可变数据，就要警惕：要么把它实体化并管好生命周期，要么让它不可变、各自持有副本。开篇的事故正是踩了这一条。

同一个概念会随场景换边。订单里的收货地址是值对象，随订单快照固化；而”用户地址簿”里的地址要被反复编辑、单独查询、跨订单复用，就该建成实体。是实体还是值对象，取决于它在当前上下文里承担的职责，不取决于它叫什么名字。

值对象落到关系库，有三种存法，取舍要看查询需求而不是建模偏好：

方案 表结构 适用 查询能力 代价 案例落点
嵌入式列 实体表内若干列 属性少且固定、需按属性检索 可索引、可条件过滤 概念在库表上被摊平，列随属性膨胀 amount + currency 两列
JSON 列 实体表内一列存 JSON 属性多、结构会变、不按内部属性查 只能整体读写 无法对内部属性加索引，方言有差异 address_json
独立表 值对象单独建表 + 外键 一对多、需独立检索或跨实体复用 完整 join 增多，易滑向”实体化” 多收货地址的地址簿

默认选嵌入式列；属性多且不检索用 JSON；只有当值对象出现一对多、或要被独立查询时才升格为独立表。但要留个心眼：一旦为它建了主键、允许单独修改，就该重新审视它是不是其实已经是实体——存储层的这步滑移，往往正是模型边界开始模糊的信号。

反模式与适用边界

  1. 给值对象加 ID 和 setter。 把描述性对象实体化，一次修改回溯到全部历史，开篇的事故就是这么来的。
  2. 用 double 存金额、String 存散落属性。 精度、币种、整体校验全部失守，属性零碎到无法表达概念。
  3. 在值对象里塞可变状态与业务逻辑。 它只负责描述，行为应留在实体或领域服务。
  4. 所有对象一律建成实体，或一律建成值对象。 跳过取舍，等于把判断交给 ORM 或表结构。
  5. 为值对象建独立表、加主键，又不承认它是实体。 语义与存储互相打架，改数据时无所适从。

以下情形建议不引入值对象，或保持最简：

情形 建议
以 CRUD、报表为主，对象几乎没有行为 直接用 PO / DTO 平铺，不抽值对象
对象需被多处独立修改且改动要留痕 建成实体，别用值对象
团队不熟悉自定义类型映射、ORM 难落地 先用嵌入式列手工转换，不急上 JSON
需按值对象内部属性高频检索 用嵌入式列或独立表，别用 JSON
一次性交付、无后续演进 保持简单数据模型，不做不可变封装

判断收成一问：一组属性是否总是一起出现、一起校验、一起被替换？ 是，抽成值对象才划算；否则平铺更直观。

要点速查

维度 实体 值对象
区分方式 唯一标识 全部属性值
可变性 可变，属性随时间演进 不可变，整体替换
相等性 标识相同即同一对象 属性全等即相等
生命周期 有，需被资源库追踪 无，依附于实体
典型例子 Order、PaymentInstruction Money、Address、OrderId
持久化 独立表，主键标识 嵌入式列 / JSON / 独立表
常见误区 建成只有 ID 的贫血对象 加主键、加 setter

一条主线：有身份、要留痕 → 实体；只描述、可替换 → 值对象；一起出现、一起校验 → 抽成值对象。

小结与参考

标识决定”是不是同一个”，不可变性决定”改动会不会外溢”。值对象不是简化版的实体，而是另一类没有身份的东西：它用整体替换换取确定性，用不可变换取历史不被改写。把这两者用对，order 表少几列、多几列倒是次要，真正省下的是那些因共享可变状态而产生的对账与客诉。
