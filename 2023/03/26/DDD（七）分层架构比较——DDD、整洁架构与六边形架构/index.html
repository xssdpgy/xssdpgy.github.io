DDD（七）分层架构比较——DDD、整洁架构与六边形架构

发表于 2023-03-26 分类于 架构设计
本文字数： 5.8k 阅读时长 ≈ 5 分钟

引言

DDD 分层、整洁架构与六边形架构常被当成三选一，其实回答的是同一个问题的不同侧面。本篇用一条下单用例对照三者的依赖方向与领域层位置，给出选型判断，也说明什么时候引入端口适配器并不划算。

一次把订单库迁往分库分表中间件的改造，评估会上给出的工作量是「三周，改 47 个类」。翻代码才发现，难点不在 SQL 方言，而在领域对象本身长成了这样：

换库要动 @Table、DAO 与所有 SQL；换服务发现组件要动 StockFeignClient；而「库存不足不允许下单」这条最该稳定的规则，和前两者挤在同一个类里。任何一次基础设施变更，都要回归全部业务规则。这不是迁移成本，是依赖方向反了：本该保护核心逻辑的层，反过来依赖了最容易变化的东西。

三种分层架构模型的分歧，几乎都从这一处开始——谁依赖谁，领域层放在哪，外部资源怎么接进来。

概念界定

三者提出于不同年代，但共享同一个内核：以领域模型为中心，依赖方向一律由外向内，核心业务逻辑与外部应用、基础资源隔离。差别只在表达形式与隔离手段。

  • DDD 分层架构（依赖倒置后的四层）：用户接口层 → 应用层 → 领域层 → 基础层。基础层不再被其它层依赖，而是实现领域层定义的接口；采用严格分层时，每层只与紧邻下层耦合。
  • 整洁架构（洋葱架构）：同心圆由内向外为领域模型、领域服务、应用服务、最外层适配器（UI 与基础设施）。依赖原则只有一条：外层依赖内层，内层对外部一无所知。
  • 六边形架构（端口与适配器）：内六边形是应用与领域模型，外六边形是外部驱动与资源；内外之间只通过端口（接口）与适配器（实现）交互，一个端口可接多个适配器，由适配器完成协议转换。

把三者叠起来看，圈住的都是同一块：领域模型加应用服务构成的核心，外围是易变的 UI、数据库与消息中间件。DDD 用「层」描述它，整洁架构用「同心圆」，六边形用「端口」。

三张子图的箭头一律指向核心，这正是它们共同的骨架；DDD 图里基础层那条虚线，是依赖倒置留下的痕迹——它不去依赖领域层，而是去实现领域层定义的接口。无论采用哪种画法，领域层都封闭在各自的限界上下文内部，不跨上下文共享模型。

案例推演

拿同一条用例「用户提交订单 → 校验可售库存」看三种架构把它放在哪。

  • DDD 分层：OrderController（用户接口）→ PlaceOrderAppService（应用，编排事务、发布领域事件 OrderCreated）→ Order 聚合根与 StockPolicy 领域服务（领域，持有「可售数量 ≥ 数量」规则）→ OrderRepositoryImpl、StockHttpClient（基础，实现接口）。规则在领域层，事务在应用层。
  • 整洁架构：同一条规则落在同心圆最内的实体里，用例编排在应用服务，Web 与数据库在最外层。与 DDD 的差别主要是术语与层次画法，落地代码几乎同构。
  • 六边形架构：PlaceOrderUseCase 在内侧，StockPort 是端口，StockHttpClient 与 StockDbAdapter 是外侧适配器。规则同样在内侧，但内外之间只允许通过端口通信，没有「层与层」的概念，只有「端口与适配器」。

把差异收敛成一张对照表：

维度 DDD 分层架构 整洁架构 六边形架构
结构隐喻 四层堆叠 同心圆 内外六边形 + 端口
依赖方向 上层依赖下层，基础层经依赖倒置反转 外层依赖内层 适配器依赖端口，指向内六边形
领域层位置 第三层，核心 最内圆 内六边形
外部资源接入 基础层实现资源库接口 最外层被动适配器 端口 + 适配器
隔离手段 分层 + 依赖倒置 依赖原则 端口 / 适配器、协议转换
术语重心 层、聚合、资源库 用例、实体、依赖原则 端口、适配器、驱动

选型可以按诉求直接对号入座：

场景 / 诉求 建议模型 理由
团队刚从三层架构迁移，需要清晰的目录与职责 DDD 分层架构 四层与既有工程习惯最接近，落地阻力最小
强调用例边界、要求业务规则完全不依赖框架 整洁架构 依赖原则最直白，便于用架构测试约束
多前端 / 多渠道接入、外部系统多且协议杂 六边形架构 一个端口多适配器，协议转换集中
需要频繁替换存储、消息中间件或第三方渠道 六边形架构 适配器可插拔，核心零改动
以 CRUD 为主、外部依赖单一 传统分层即可 三者收益都有限

三者不是递进关系，也不互相替代。DDD 分层回答「代码放哪一层」，整洁架构回答「依赖该朝哪个方向」，六边形回答「外部系统怎么接进来」。生产里常见的是叠用：用 DDD 的四层组织目录，用依赖倒置落实依赖方向，用端口适配器管理多变的外部渠道。

三个类分属领域层、基础设施层、应用层，编译期依赖是「应用 → 端口 ← 适配器」，运行期由容器注入具体实现。领域层与编排层没有一行框架代码，这正是开头那次迁移本该有的样子：换库存渠道只改 StockHttpClient，换库只改 OrderRepositoryImpl，PlaceOrderAppService 与 Order 不动。构造器注入也顺带消掉了反例里字段注入带来的隐式依赖。

反模式与适用边界

  1. 领域层 import 框架或基础设施。 实体带 @Entity、注入远程客户端，业务规则与框架同生共死，换依赖要回归全部业务。
  2. 把业务规则写进应用层或 Controller。 应用层膨胀成事务脚本，领域模型贫血失焦，规则重复实现且无处归属。
  3. 依赖倒置只做一半：接口和实现都放在基础设施层。 领域层依旧依赖具体包，接口只是一层空转，换库照样改领域代码。
  4. 没有多适配器诉求却机械照搬端口。 一个端口只接一个适配器还到处建端口，目录复杂度翻倍，收益为零。
  5. 松散分层放任跨层调用。 用户接口层直接调领域服务甚至资源库，核心逻辑外泄，服务变更时调用方找不全。

六边形架构的价值与「外部系统的数量和变化频率」成正比，以下情形不值得引入：

情形 判断
外部依赖单一且长期不变（一个库、一个前端） 四层分层足够，端口适配器是纯开销
以 CRUD / 报表 / 数据搬运为主，业务规则少 领域层本就很薄，隔离收益有限
一次性交付、后续不再演进 可插拔能力无处兑现
团队尚不熟悉依赖倒置与接口隔离 先落实四层与「接口放领域层」，别一步到位
外部协议由网关统一屏蔽，业务侧只见一种调用方式 适配器层没有协议转换可做

再补一句总判断：三者都以「领域模型相对稳定、外部需求易变」为前提。若一个系统连领域模型本身都还在探索期，任何分层的投入都会随模型重写而作废，此时直接实现、保留重构空间更经济。

要点速查

架构 一句话 依赖方向 隔离手段 优先诉求
DDD 分层 用四层组织代码与职责 上层 → 下层，基础层依赖倒置 分层 + 资源库接口 目录清晰、易迁移
整洁架构 用同心圆约束依赖方向 外层 → 内层 依赖原则 业务规则不依赖框架
六边形架构 用端口适配器隔离外部 适配器 → 端口 → 内六边形 端口 / 适配器 多渠道、多协议、可插拔
检查项 合格标准
领域层是否纯净 不 import Spring / ORM / HTTP 客户端
端口归属 接口在领域层，实现在基础设施层
应用服务 只依赖接口，不含业务规则
依赖方向 编译期依赖始终指向领域层
换库 / 换渠道成本 只改适配器，不动核心

小结与参考

三种架构不是三种答案，而是同一条原则的三种画法：让最稳定的领域逻辑待在中心，让最易变的外部资源待在外围，依赖永远由外向内。DDD 分层给目录，整洁架构给依赖约束，六边形给外部系统的接法，工程上完全可以叠用。真正决定迁移成本的从来不是选了哪张图，而是领域层里有没有一行不该出现的框架代码。
