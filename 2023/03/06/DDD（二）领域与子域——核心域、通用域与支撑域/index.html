DDD（二）领域与子域——核心域、通用域与支撑域

发表于 2023-03-06 分类于 架构设计
本文字数： 5.4k 阅读时长 ≈ 5 分钟

引言

面对没做过的业务，第一版架构最容易把名词平铺成模块，再把资源平均分掉。本篇讲初始子域划分：先判核心域、支撑域与通用域，按档位决定人力和自研深度，也给出这套分级不成立的条件。

一个团队接手从未做过的电商履约业务，评审会上给出的第一版架构，是把能想到的名词平铺成十四个一级模块：用户、商品、订单、库存、支付、促销、发票、物流、通知、字典、权限、报表、评价、售后。每个模块分一个小组、一个库、一套 CRUD，两周搭完骨架，排期表整齐漂亮。

大促当天出了问题：同一 SKU 被超卖。追查下来，库存扣减散在两处——下单时在订单服务里执行一次 update stock set available = available - n，发货前又在履约服务里扣一次，中间没有锁定态，也没有占用记录。规则没有归属，更没有人把它当成需要认真设计的东西。

坏味道通常长这样，库存被当成与字典、通知同构的通用能力：

没有并发控制，没有”谁占用了这批货”的记录。这不是写得差，而是被放错了投入档位：最强的三个人派去做权限和消息中心，库存交给一个新人按 CRUD 实现。十四个模块被平均对待，等于没有判断。

面对陌生业务，资源永远不够。初始划分要解决的不是”分得全不全”，而是先分出轻重：哪一块值得最强的人自研，哪一块能买，哪一块够用就行。分错档位，比少画一个框代价大得多。

概念界定

领域是要解决的业务问题范围，范围即边界；把范围逐层收窄，得到的更小问题域叫子域。子域只是问题空间的切分结果，还不是服务，也不是代码目录——陌生业务里，这一步最容易被跳过，直接跳到建表和服务名。

按”重要性 + 功能属性”给子域分档，得到三类：

  • 核心域：决定产品与公司的竞争力，承载本企业区别于对手的规则，去掉它业务就不成立。
  • 支撑域：必需，但既非竞争力来源，也不是到处都能复用的通用功能；往往带企业特性，需要定制开发。
  • 通用域：无个性化诉求、被多个子域共用、行业内已有成熟实现可直接采购，例如认证、权限、通知、数据字典。

分档的唯一目的是决定投入，不是给架构图染色。同一块业务在不同公司会落在不同档位：支付通道对自营电商是支撑域，对支付公司就是核心域。子域是问题空间的切分，限界上下文是解空间的边界，二者不必一一对应。

把贯穿案例按这三类摆开：

    D["领域：电商订单履约"]
    D --> CORE
    D --> SUP
    D --> GEN
    subgraph CORE["核心域：自研，最高投入"]
        C1["库存：可售、锁定与防超卖"]

    end

        G3["数据字典"]

库存与履约被判为核心域，前提是这家公司的差异化落在”大促不超卖”与”次日达”上；换一家以流量和低价立身的平台，核心域可能就是交易与促销。图是判定的结果，不是划分的起点。

案例推演

陌生业务的初始划分，只要求达到”能分派团队与预算”的粒度，不要求一次精确到可落库的模型。信息最少的时候定死边界，等于把猜测固化成架构。

第一步，先写一句业务边界，不画模块。 为下单用户，在承诺时效内把已支付的订单准确发出，且不超卖。这句话同时圈定范围和两个不可退让的指标，后面所有分档都要回溯到它。

第二步，列业务事实而不是名词。 沿流程把动作与结果写全：提交订单 → 订单已创建 → 库存已锁定 → 支付已完成 → 发货单已生成 → 订单已完成。命令与领域事件比”用户/商品/订单”这类名词更能暴露边界，因为规则总是挂在动作上，而不是挂在名字上。

第三步，按流程边界与业务关联度聚成候选子域。 相邻且共享同一批规则的动作合并，跨流程的强制拆开，得到交易、库存、支付、履约、结算，以及认证、通知、字典这些横切能力。经验值是一次划分控制在 5–9 个；超出这个数，多半是把功能模块当成了子域，应再合并一轮。

第四步，用核心域判定条件逐项定级。 下面五问是可检验的，不靠感觉：

判定条件 问的是什么
去掉它，产品是否就不成立 是否直接决定客户选择与付费
行业里是否有可直接采购的等价实现 有，基本排除核心域
是否承载本公司独有的规则或算法 是，核心域的强信号
规则变更频率与出错代价是否最高 决定投入上限
出错是否致命、且换供应商也补不回来 决定是否必须自主掌控

逐项过一遍候选子域：

候选子域 采购可得 独有规则 出错代价 档位
库存（可售与锁定） 否 是：占用、释放、防超卖 高 核心域
履约（时效与发货） 否 是：时效承诺与路由 高 核心域
交易（订单状态机） 部分 一般 中 支撑域
支付（渠道路由与对账） 通道可购，对账需自研 部分 中 支撑域
结算、发票 部分 弱 中 支撑域
认证、权限、通知、字典 是 无 低 通用域

定级只是分类，真正落地的是投入差异。三类子域不该用同一套人力和标准：

档位 判定依据 团队与掌控 建设策略 测试与质量投入 演进方式 失败代价
核心域 去掉即不成立、有独有规则、采购不可得 最强团队，完全自主掌控，拒绝外包 全自研，领域模型持续投入 最高：规则级单测、并发与压测 高频演进，边界可重构 丢壁垒，致命
支撑域 必需、带企业特性、非竞争力来源 内部团队定制开发 自研或基于开源二次开发，够用即可 中：主流程覆盖 随业务调整 影响交付，可补救
通用域 无个性化、被多子域共用、可采购 无需专职团队 外购 + 适配层，最小化定制 低：验收与集成即可 尽量不动，版本跟随供应商 低，可替换

第五步，给模糊地带留活口。 交易与促销边界不清、支付与结算时有重叠，都标成”暂不判定”，先按一个团队、一个代码库推进，流程跑顺再拆。这里有个策略取舍：全新系统用自顶向下，先按战略分解再建模型；遗留系统改造用自底向上，先盘点既有模型再归并共性。陌生业务从零起步，选自顶向下，但只做一层，不逐级分解到底——对二三级子域的判断，此时大概率是错的。

    B --> C["按流程边界聚成候选子域"]
    C --> D["五问判定条件定级"]
    D --> E["产出投入决策与仓库结构"]

代码与目录

分档要能在仓库结构上被读出来，否则很快退化成口头共识。核心域独立成模块、独占最强人力；通用域只留一层薄适配，隔离采购产品的 SDK。

核心域的代码密度明显不同，它值得把规则建成对象，而不是写成 SQL：

SkuRepository 是接口，锁定态、占用记录与并发控制都落在库存聚合根内；通用域恰好相反，除了一层适配层几乎不写业务代码。同样是”一个子域一个人”，两处代码量可以差一个数量级，这正是分档要买到的东西。

反模式与适用边界

  1. 按名词平均切分。 把字典、通知与订单平级排期，等于放弃判断；十四个模块平均用力，最该深挖的那块最容易被草草带过。
  2. 按部门划子域。 组织边界是历史结果，不是业务边界；照组织架构切，会把一条流程规则劈给两个团队。
  3. 把核心域外包或外购。 省下的是一次性成本，丢掉的是规则演进权；核心域必须自主掌控。
  4. 一次到位、追求终态划分。 陌生业务信息最少，此时定死的二三级边界多半是猜测；划分要能撤回。
  5. 用同一套标准要求所有子域。 给通用域做充血模型和事件风暴，或给核心域套 CRUD 模板，都是投入错配。

以下情形建议不做三类分级，或只做粗分：

情形 建议
以 CRUD、报表、数据搬运为主，规则少且稳定 直接按模块分层，不做分档
一次性交付、后续不再演进 划分只到”能分工”即可，不建领域模型
领域专家缺席，需求只有文档 先补沟通机制，暂缓核心域认定
商业模式尚在试水、战略未稳 不急于定核心域，用可迁移的薄边界兜底
团队不足两个小组 分级带来的协调成本大于收益，保持单模块

分级的前提是资源确实稀缺、各子域的重要性又能拉开差距；两者只要有一个不成立，平铺反而是最省事的选择。

要点速查

概念 关注点 判定 / 动作 常见误区
领域 业务范围 一句话写清边界与不可退让指标 一上来就列模块
子域 问题空间切分 按流程边界与关联度聚类，5–9 个 当成服务或代码目录
核心域 竞争力来源 五问判定，最强团队自研、拒绝外购 按”重不重要”拍脑袋
支撑域 必需但非壁垒 定制开发，够用即演进 与通用域混为一谈
通用域 可采购、被共用 外购 + 适配层，最小化定制 重复造轮子
初始划分 分派团队与预算 只做一层，模糊处标”暂不判定” 逐级分解到终态
投入决策 资源稀缺 按档位拉开人力、测试与自研深度 十四个模块平均用力

一条主线：业务事实 → 候选子域 → 判定条件定级 → 投入决策 → 仓库结构。分档不是给图染色，是决定谁来做、做多深、能不能买。

小结与参考

陌生业务的第一版架构，最贵的错误不是少画一个框，而是把核心规则放进了通用档位。子域划分的产物不是一张分类图，而是一份能直接分派人力与预算的决策：核心域自主掌控，支撑域定制开发，通用域能买就买。判定依赖公司战略，会随商业模式变化，所以初始划分只做一层、留活口，比一次画到终态更耐用。
