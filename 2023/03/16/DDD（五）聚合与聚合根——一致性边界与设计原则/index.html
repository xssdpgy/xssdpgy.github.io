DDD（五）聚合与聚合根——一致性边界与设计原则

发表于 2023-03-16 分类于 架构设计
本文字数： 6.8k 阅读时长 ≈ 6 分钟

引言

事务边界画大一圈，大促时就会变成死锁和超卖。本篇讲聚合与聚合根的划法：按不变条件而不是按名词圈边界，四条设计原则怎么用，跨聚合的状态变化为什么只能交给领域事件。

大促开始第 11 分钟，订单库开始大面积报死锁与锁等待超时，下单接口 P99 从 80 毫秒飙到 4 秒；几乎同时冒出超卖工单，却没人能说清库存究竟是在哪一步被扣穿的。排查下来，两类异常指向同一段代码——一个被团队称作 Order 的类，把订单项、SKU 库存、支付流水、发货单全装进同一个聚合，任何一次下单都在一个本地事务里锁住四张表的十几行记录。

Order 名义上是聚合根，实际上成了一段跨表事务的入口。真正致命的不是 @Transactional 标得太大，而是没人说得清哪些对象必须在同一瞬间保持一致。于是库存行被下单、支付回调、发货批处理三类流量争抢；订单项金额与可售库存本不需要同生共死，却被绑进同一把锁；deduct 与 create 散落在应用服务里，超卖时无法判定哪一处是权威。

事务边界画错，调隔离级别、加索引、拆库都只是缓解。要收敛的是边界本身：把「必须同时成功」的东西圈在一起，把其余的请出去。

概念界定

聚合是一组生命周期与业务规则紧密绑定的对象的集合，也是数据修改的最小一致性单元：聚合内的不变条件由一次事务守住，聚合之外不保证强一致。聚合根是聚合内唯一对外的实体，拥有全局唯一标识，外部只能通过它访问聚合内对象；聚合与聚合之间只通过聚合根的标识互相引用，不做对象引用。一个聚合对应一个资源库，持久化以聚合为单位整体读写。

这里的不变条件，指任何时刻都必须成立的业务断言，例如「订单实付金额等于各订单项小计之和」「SKU 可用数量不小于零」。判断两个对象该不该进同一个聚合，只问一句：它们之间是否存在必须在同一事务内成立的不变条件。有则同聚合，无则分开。按「看起来有关」聚类，是大聚合最常见的起点。

拆分前后，事务边界的差别一目了然：

左边一个事务持有四组行锁，任意一处慢都会拖住整条链路；右边四个事务各管一组数据，彼此通过事件衔接，锁的粒度与持有时间都降了一个量级。聚合是限界上下文内部的逻辑边界，事务则是聚合的运行时投影——边界画对了，代码里的 @Transactional 才有处可放。

案例推演

把订单履约链路按不变条件重新切一遍。

  • 订单聚合：订单、订单项、收货地址。不变条件是总额等于各订单项小计之和、订单项非空、已支付订单不可修改地址。收货地址无独立标识、依附订单存在，作为值对象并入。
  • 库存聚合：SKU 可售库存。不变条件是可用量等于总量减占用量且不小于零，单 SKU 的扣减必须串行。
  • 支付单聚合：支付单与支付流水。不变条件是支付金额与订单应付一致、同一渠道流水号只入账一次。
  • 发货单聚合：发货单与明细。不变条件是发货数量不超过已支付数量。

这四组不变条件彼此并不要求在同一瞬间成立：用户下单成功时，库存可以晚几百毫秒锁定；支付完成后，发货单可以稍后生成。它们因此分属四个聚合、四个本地事务。落到设计上，是四条原则：

  1. 在一致性边界内建模真正的不变条件。 聚合不是把相关的类装在一起，而是把必须同时成立的断言圈起来。订单与订单项有总额断言，同聚合；SKU 库存与订单之间只有「数量够不够」的校验关系，不构成同时成立的不变条件，必须拆出。
  2. 设计小聚合。 聚合越大，一次事务持有的行锁越多、持锁时间越长，并发冲突概率随聚合内实体数近似线性上升。把库存拆出后，下单事务只锁订单与订单项两三行，大促的锁等待从秒级回到毫秒级。
  3. 通过唯一标识引用其它聚合。 订单里保存 skuId、paymentId，而不是持有 Inventory、Payment 对象；跨聚合加载由应用服务按标识分别调用各自资源库。对象引用会让边界在代码里消失，重构时无从拆起。
  4. 边界之外使用最终一致性。 一次事务最多改一个聚合；涉及多个聚合就用领域事件异步串联，发布方提交后即返回，不等待订阅方。

原则四落到履约链路：OrderCreated 触发库存锁定，PaymentCompleted 触发发货单创建。代价是下单接口返回时库存尚未锁定，存在「订单已建、库存未锁」的中间态。处理办法不是退回分布式事务，而是把中间态显式建模：库存不足时发布 StockRejected，交易上下文据此把订单置为「已取消」并触发退款。换来的是库存上下文可以独立发布、独立扩缩，不被下单流量直接拖垮。

四个事务彼此独立，事件是唯一的连接。这里有一条判断线值得记住：不变条件必须在同一事务内守住，流程状态可以跨事务最终一致。把流程状态误当成不变条件，是大聚合最顽固的成因。

反模式与适用边界

  1. 把聚合当关系图画。 用外键或对象引用把「看起来有关」的实体全连起来，边界靠直觉而非不变条件，几轮迭代后退回大聚合。
  2. 一个事务改多个聚合。 图省事用 @Transactional 包住整条链路，锁竞争与耦合一起回来，还把超卖责任稀释到多处。
  3. 聚合根贫血。 聚合根只剩 getter/setter，不变条件散落在应用服务，totalAmount 这类断言无人把守，模型与实现重新分成两套语言。
  4. 聚合间对象引用。 订单直接持有 Payment 并级联保存，边界在代码里消失，将来无法按聚合拆服务。
  5. 把聚合当成微服务的固定粒度。 一个聚合一个服务，服务数暴涨；聚合是逻辑边界，是否升格为物理边界取决于演进需要，不是建模时一次定死。

以下情形建议不严格追求小聚合与全面最终一致：

情形 建议
账务、清算类强一致记账，借贷必须同时入账 用单库本地事务守住同一聚合，不引入事件异步
低频、单团队维护的内部系统 适度放宽粒度，别为小概率并发付出建模成本
团队尚无补偿与对账能力 先保留同步校验，不急于全面最终一致
一次操作本质是同一事实的多个视图（订单与订单快照） 同事务写入，不拆成事件
外部渠道承诺「下单即锁库存」 对渠道侧同步，内部异步，但须先定义中间态契约

判断标准可以压成一句：最终一致性是用可用性与可演进性换来的，代价是必须显式处理中间态与补偿；没有补偿能力，就不要先拆边界。

要点速查

项 判定或做法 落地位置
聚合 一组必须同事务成立的不变条件 领域层，一个聚合一个资源库
聚合根 唯一对外实体，全局 ID，把守不变条件 聚合内唯一入口
聚合间引用 只持对方聚合根 ID，不做对象引用 字段为 skuId / paymentId
事务边界 一次事务最多改一个聚合 @Transactional 落在单个应用服务方法
跨聚合协作 领域事件 + 最终一致 应用层提交后发布，订阅方独立事务
真正不变条件 必须同瞬间成立 划入同一聚合
流程状态 可跨事务最终一致 拆成不同聚合

一条主线：不变条件定边界，标识引用代替对象引用，事件承接边界之外的协作。

小结与参考

事务边界不是由 @Transactional 标在哪决定的，而是由不变条件决定的。大聚合的病根，是把流程状态误当成必须同瞬间成立的业务断言；把它拆回四个各守其职的聚合，锁竞争与耦合一起消失，代价是要为「订单已建、库存未锁」这类中间态写好补偿。聚合设计到最后，回答的是一个很朴素的问题：这两件事，必须同时成功吗。
