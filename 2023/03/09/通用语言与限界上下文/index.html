通用语言与限界上下文

发表于 2023-03-09 分类于 架构设计
本文字数： 5.3k 阅读时长 ≈ 5 分钟

引言

一张金额表被两个团队按各自的口径共写，对账差额往往从这里开始。本篇讲通用语言与限界上下文：怎样把术语冲突收敛成模型边界，以及边界确定后团队、代码库与数据库该怎么对应。

财务对账连续三天出现差额，量不大，但每天都有。追到最后，问题不在渠道，在一张表：order.amount 一个字段被两个团队写。交易侧把它当应付金额，支付侧把它当渠道实收金额（已扣手续费），两边各按各的口径累加，谁也没觉得有问题——因为在各自的代码里，它都叫”订单金额”。

更早的信号其实已经出现过，只是没人当回事。这个 Order 类被四个团队轮流加字段：

字段越加越宽，是因为没人给”订单”划定它在哪里生效。四个部门开会统一过命名，结论是”都叫订单”，然后各回各家继续往同一个类里塞字段。共享一个模型，把口头的歧义变成了数据库里一行谁都解释不清的数据。

结论先行：跨部门术语歧义不能靠开会统一，只能靠限定每个词生效的范围来收敛。统一语言的产物不是一份词汇表，而是一条条模型边界；边界之内，一个词只有一个含义，边界之外，同名可以不同义。

概念界定

通用语言是团队在限界上下文内共同使用、能准确描述业务含义与规则的语言：名词给领域对象命名，动词对应命令与领域事件，并且直接落到代码里。它不是会议纪要里的术语表，判断它是否成立只有一个标准——代码里的类名、方法名、事件名，业务方能否不看文档就读懂。

限界上下文是这份语言的适用边界：封装通用语言与领域对象，保证边界内的术语没有二义性，并明确什么该在模型里实现、什么不该。同一个”订单”在四个部门指四样东西，正确的处理不是统一命名，而是拆成四个各自成立、独立演化的模型。

四个上下文里都有”订单”这个概念，但各自的类名、字段、状态、通用语言都不同；它们之间不共享模型，只通过显式契约协作。边界定下来之后，团队、代码库、数据库才有对齐的依据。

案例推演

先把歧义摊开。 下表把订单履约里最容易打架的词摆在一起：

术语 交易上下文 支付上下文 库存上下文 履约上下文 冲突后果
订单 待支付的单据，含明细与应付 收款请求，标识为商户订单号 库存占用凭证 待发货的包裹清单 同一 ID 被四处改写，状态互相覆盖
商品 含售价与促销的 SKU 计价项 可售数量载体 含重量体积的货物 字段越加越宽
库存 可售数量 — 货位、批次、可用量 待拣货量 “扣库存”动作语义不同
金额 应付金额 实收 / 结算金额（含手续费） — — 财务对账差额
已支付 可进入发货 渠道回调成功 占用转实扣 生成发货单 时序不一致，重复发货或漏发

再收敛成边界。 交易上下文的聚合根叫 Order；支付上下文叫 PaymentInstruction（收款指令），它关心的商户订单号只是一个关联标识；库存上下文叫 StockReservation（占用记录）；履约上下文叫 ShipmentOrder（发货单）。四个类各自演化，谁也不用迁就谁。跨上下文协作靠领域事件与显式接口，不靠把一个类改得更宽。

第三步，定义上下文之间怎么协作。 边界划清之后，关系也要写明白，否则集成时又会退回成互相直接调对方领域对象。上下文映射给出几种常见关系：

flowchart LR
    T["交易上下文"] -->|"合作关系：共同保障不超卖"| I["库存上下文"]
    I -->|"合作关系"| T
    T -->|"客户-供应方：请求收款"| P["支付上下文"]
    P -->|"防腐层：隔离渠道报文"| G["外部支付渠道"]
    P -.->|"开放主机服务 / 发布语言：支付已完成"| T
    T -.->|"遵奉者：消费事件契约"| F["履约上下文"]
    I -.->|"共享内核：SkuId、Money"| T
  • 合作关系：交易与库存共同背负”不超卖”，任一侧改规则都要同步，一损俱损。
  • 客户-供应方：交易是下游客户，支付是上游供应方，收款能力由支付提供，交付节奏可协商。
  • 防腐层：支付上下文把外部渠道的报文、SDK、状态码挡在边界外，翻译成内部的收款指令；换一家渠道，改的只有这一层。
  • 开放主机服务 / 发布语言：支付对外发布统一的「支付已完成」领域事件，任何上下文按同一契约消费，不暴露内部模型。
  • 遵奉者：履约直接沿用交易发布的事件契约，不做二次翻译，代价是失去议价能力，换来的是简单。
  • 共享内核：四个上下文共用 SkuId、Money 两个极小值对象，共享范围越小越好，改它必须四方同意。

第四步，把边界落实到团队与物理资源。 语义边界不落到组织与存储上，很快会被一次”顺手复用”冲垮：

限界上下文 团队 代码库 / 模块 数据库 对外契约
交易 交易组 trading-context（独立仓库） trade_db 「订单已创建」「支付已完成」领域事件
支付 支付组 payment-context payment_db + 对账表 收款指令接口、领域事件
库存 库存组 inventory-context inventory_db 锁定 / 释放接口
履约 履约组 fulfillment-context fulfillment_db 发货单创建事件

一个上下文对应一个团队、一个代码库、一个独立库，是最常见的对齐方式，但不是铁律。早期两个上下文可以同库不同 schema，只要不共享表、不共享领域模型。真正不可退让的是模型与表的隔离，团队和库的拆分只是它的结果，不是前提。

代码与目录

边界要能在目录里一眼看出来：模型各归各家，外部依赖只有唯一出入口。

反模式与适用边界

  1. 靠开会统一命名。 强推一份全局词汇表，把四个部门的”订单”合成一个，结果造出谁都不满意的巨型模型。
  2. 共享一个领域模型或一张宽表。 把歧义压进 order 表，字段越加越多，改动互相踩踏。
  3. 直接调用对方领域对象。 交易里 new PaymentInstruction().setAmount(...)，或者跨上下文直接查表，边界名存实亡。
  4. 防腐层写成透传。 把外部 DTO 一路传到业务代码，等于没有隔离，渠道一改，全链路跟着改。
  5. 边界没稳就先拆库拆团队。 上下文与微服务强行一一对应、一上来就物理隔离，协作成本先于收益到来。

以下情形建议不划多个限界上下文，或只做术语澄清：

情形 建议
业务规则单一、几乎没有歧义术语 单一模型即可，不必分上下文
团队不足两个、无跨部门协作 划分带来的沟通成本大于收益
外部依赖稳定、报文长期不变 防腐层退化为薄适配，不必独立成模块
一次性交付、无后续演进 用术语对照表澄清口径，不落模型边界
报表与查询类系统 按消费方口径出统一数据视图，不追求模型唯一

判断可以收成一问：同一个词在不同团队是否指向不同东西，且各自会独立变化？ 是，才值得划上下文；否则统一模型更省事。

要点速查

概念 关注点 产出 / 动作 常见误区
通用语言 边界内无歧义 类名、方法名、事件名落到代码 做成会议术语表
限界上下文 语义适用范围 模型、团队、代码库、数据库边界 当成纯逻辑分组
领域事件 跨上下文协作 「支付已完成」等显式契约 事件里塞对方模型
合作关系 共同成败 交易 ↔ 库存同步演进 一方独改规则
客户-供应方 上下游协商 交易 → 支付 下游反向定义上游
防腐层 隔离外部模型 适配器翻译渠道报文 写成透传
开放主机服务 / 发布语言 统一对外契约 发布领域事件 暴露内部模型
遵奉者 直接沿用契约 履约消费交易事件 误用于核心模型
共享内核 极小共享 SkuId、Money 共享范围过大

一条主线：术语冲突 → 限定适用范围 → 上下文映射 → 团队 / 代码库 / 数据库对齐。

小结与参考

术语歧义不是沟通问题，是模型边界问题。统一语言的价值不在词汇表，而在划出每个词生效的范围；范围一定，团队、代码库、数据库与集成契约才有对齐依据。跨上下文不共享模型，只共享显式契约——那条对账差额，本质上是把一个词塞进了同一个字段。
