高并发（六）缓存高可用、穿透防护与静态加速

发表于 2023-06-07 分类于 架构设计 ， 高并发
本文字数： 5.9k 阅读时长 ≈ 5 分钟

引言

穿透、击穿、雪崩不是一回事，判定条件不同，手段也不同，混着讲就会用错药。比如活动页被人刷一个已经下架的 SKU：缓存里没有、库里也没有，请求一次次落到数据库；换个场景，5000 库存那个热点 key 整点过期，几万请求同时回源，这是另一种故障。两种都叫「缓存没挡住」，一个靠空值挡，一个靠只放一个请求回源。

概念界定

命中率是缓存的命门。核心缓存盯 99% 以上，非核心也别低于 90%。把大促的账算一下：峰值 2 万 QPS，读放大 3 倍，命中率掉 1% 就是每秒多 600 次回源；单个关系库节点的读峰值大约 1500 次 / 秒，这 600 次足以把 P99 从 60ms 抬起来，逼近错误率 0.1% 的验收红线。所以缓存节点故障不是慢一点的问题，是整条链路跟着塌。

三种故障的判定条件必须分开写：

异常 判定条件 影响范围 手段
穿透 要查的数据在库里就不存在，缓存永远不命中 单个不存在的 key，持续 空值缓存、布隆过滤
击穿 单个热点 key 到期或被删，并发一起回源 一个 key，瞬时高峰 互斥锁、后台加载
雪崩 一批 key 同时失效，或缓存分片整体不可用 整片缓存，全局 过期时间打散、副本、降级 
flowchart TB
    Q["缓存未命中"] --> C1{"库里这条数据存在吗"}
    C1 -->|不存在| T["穿透：空值缓存 / 布隆过滤"]
    C1 -->|存在| C2{"失效的是单个热点 key 还是一批"}
    C2 -->|单个热点| B["击穿：互斥锁 / 后台加载"]
    C2 -->|一批或整片| A["雪崩：TTL 抖动 + 副本 + 降级"]

高可用靠分片加副本。分片用 Hash 取余实现最简单，但节点数一变，大部分 key 重新映射，命中率塌一片；一致性 Hash 把节点和 key 放到同一个环上，增减节点只让少量 key 漂移，加虚拟节点还能避免故障节点的流量全压到环上下一个节点、引发连锁压垮。分片数不是越多越好，节点一多，批量读取的可用性由最慢那个节点决定，4 到 6 个比较合适。副本分担读，主节点挂了不至于让请求全穿透到库。

把这套逻辑放在哪一层，代价不同：客户端方案把分片与路由写进应用，没有额外网络损耗，但逻辑重、换语言就得重写一遍；代理层方案在应用和缓存之间加一层无状态代理统一路由，多语言能复用，代价是多一跳网络和一层要运维的组件；服务端方案由缓存侧自动做主从切换，应用改动最小，运维复杂度上移。三种没有绝对优劣，看团队在哪一边有积累。

CDN 是另一种缓存。用 CNAME 把厂商节点藏在自有域名后面，域名解析时由 GSLB 按地理位置返回最近的节点，图片、视频、脚本这类体积大又几乎不变的内容才适合就近分发。要盯的是命中率和回源带宽：回源一多，源站带宽和延迟一起上去。CDN 只接静态和允许延迟的准静态内容，这条边界不能松。

案例推演

固定设定：单 SKU、库存 5000 件、预约 30 万人、整点开抢，日常下单 200 QPS、P99 60ms，峰值 2 万 QPS，验收目标 2 万 QPS 下 P99 < 200ms、P999 < 1s、错误率 < 0.1%，链路下单 → 锁库存 → 支付 → 发货，分层结论是网关 6 台、应用 20 台、缓存 3 分片、数据库同步写入不成立。

2 万 QPS 按 3 倍读放大落到缓存是每秒 6 万次，3 分片各担约 2 万次。这个量级下，命中率掉 1% 带来的 600 次 / 秒回源会直接吃掉 P99 余量，所以三种异常要按触发点分开处理。

先说穿透。下架的 SKU、爬虫刷随机 id、前端参数被改，查的都是库里根本没有的数据。Cache Aside 在这种请求上不会回种，来一次打一次库。回种一个短过期时间的空值就能挡住重复查询，代价是内存；如果被刷的是海量各不相同的随机 id，空值会把空间占满、挤掉真实热点，这时该换布隆过滤，判断「不在」一定不在，误判只会出现在判断「在」的时候，对挡穿透正好够用。

再说击穿。5000 库存那个 key 是全场最热的，整点一旦过期，几万请求同时发现未命中、同时回源，关系库瞬时被打满。做法是只放一个请求拿互斥锁去加载，其余请求轮询缓存等结果；或者由后台线程在过期前续期，访问根本不穿透。给一批活动 key 配同一个固定过期时间，等于亲手安排它们一起失效，过期时间要加随机抖动。

雪崩是整片层面的事。3 分片里挂掉一片，若分片算法没有虚拟节点，故障片的流量会集中压到环上下一个节点，很可能连锁把它也压垮；副本接住读流量、降级兜住非核心读，才能把冲击摊开。这一层靠加锁挡不住。

flowchart TB
    U["用户请求"] --> CDN["CDN：活动页静态资源、预约人数(短 TTL)"]
    CDN --> GW["网关 6 台：限流 / 资格预判"]
    GW --> APP["应用 20 台"]
    APP --> C["缓存 3 分片 + 副本：商品详情、库存单键"]
    C --> DB["关系库：订单写入"]
    CDN -.-> NOTE["库存 5000、资格、下单结果：强一致，不进 CDN"]
    APP -.-> NOTE

活动页的分层要按一致性要求划，不按数据类型划：

数据 一致性要求 落点 过期策略
活动页图片、脚本、样式 无 CDN 就近节点 长，靠版本化文件名更新
预约人数 30 万 准静态，可延迟几十秒 CDN / 缓存 短 TTL
商品详情 秒级延迟可接受 分布式缓存 3 分片 分钟级加抖动
库存 5000、资格、下单结果 强一致 缓存单键原子操作或关系库 不进 CDN

「预约人数」放上去没问题，它晚几十秒不影响谁抢到；库存放上去就是另一回事了，就近节点返回的是旧值，5000 件按旧值继续放单，超卖是确定结果。强一致数据不上 CDN，是这里最该写死的一条。

代码与目录

这段实现有明确边界：空值存活时间要比业务键短一个量级，取 10 秒量级，否则下架商品重新上架会长期读不到；空值本身占内存，被刷的是海量不同随机 id 时就该换布隆过滤，别硬堆空值。warmUp 的抖动只错开失效时刻，防不了分片整体故障，那要靠副本和降级。防击穿的互斥锁没写进这段，落地时只放一个请求回源、其余轮询缓存即可，塞进来会把这段代码撑成框架。

反模式与适用边界

  1. 三种故障一律加互斥锁。 穿透是数据根本不存在，加锁只会让请求排队等一个空结果；雪崩是整片不可用，锁也拦不住流量。判定条件不同，手段不能通用。
  2. 空值缓存不设过期，或过期时间跟业务键一样长。 空值挤掉真实热点，命中率反而下降，下架商品重新上架后也读不到，等于自己造了一份脏数据。
  3. 给一批活动 key 配同一个固定过期时间。 整点一起失效，热点回源叠加，击穿和雪崩一起到；过期时间加抖动是成本最低的一步。
  4. 用 Hash 取余分片还频繁扩缩容。 节点数一变，大部分 key 重新映射，命中率塌一片，换一致性 Hash 加虚拟节点才稳得住。
  5. 把库存、资格、下单结果放上 CDN。 就近节点返回几十秒前的旧值，5000 件按旧值继续放单，超卖是确定结果，不是概率问题。

下面这些情况，这套防护与高可用方案可以不做或只做一半：

情形 为什么不必套 建议做法
内部后台，峰值远低于单机拐点 缓存挂了库也扛得住，副本是净成本 单节点缓存即可
单语言、小规模应用 客户端分片逻辑自己维护得住 不上代理层，省一跳网络
数据全量装得进内存、没有热点变化 没有穿透与击穿的触发条件 本地缓存定期全量刷新
纯内网服务，用户集中在同一地域 就近分发没有收益 静态资源走 Web 服务器
静态资源量小、带宽不紧张 按带宽计费，收益覆盖不了成本 源站直出加浏览器缓存

要点速查

故障 / 手段 判定条件 主要手段 代价
穿透 数据在库里不存在 空值缓存、布隆过滤 空值占内存，布隆有误判
击穿 单个热点 key 失效 互斥锁、后台加载 部分请求短暂等待
雪崩 一批 key 同时失效或整片不可用 TTL 抖动、副本、降级 副本吃内存，降级损功能
客户端方案 分片路由写在应用里 一致性 Hash 加虚拟节点 逻辑重，跨语言不能复用
代理层方案 多语言共用一套缓存 独立代理统一路由 多一跳网络，多一层运维
CDN 静态与准静态内容 CNAME、就近节点、短 TTL 强一致数据不能放

小结与参考

三种故障的判定条件不一样：库里根本没有的数据，用空值或布隆过滤挡住；单个热点 key 失效，只放一个请求回源，其余等缓存；整片失效要靠副本、过期时间抖动和降级把冲击摊开，加锁没用。缓存高可用落到分片加副本，客户端、代理层、服务端三处只是把路由逻辑放在不同位置，代价分别是逻辑重、多一跳、运维上移。CDN 是就近分发，只该接静态和允许延迟的准静态内容；库存和资格这类强一致数据放上去，换来的不是加速，是超卖。
