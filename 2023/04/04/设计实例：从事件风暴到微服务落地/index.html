设计实例：从事件风暴到微服务落地

发表于 2023-04-04 分类于 架构设计
本文字数： 8.5k 阅读时长 ≈ 8 分钟

引言

服务清单靠拍脑袋定，异步链路里迟早会出现没人认领的状态。本篇把电商订单履约从头走一遍：从事件风暴贴出的命令、事件与聚合出发，收敛成带数据归属的服务清单，最后落到聚合根代码和目录。

大促当天出现一批「支付成功却未发货」的订单，客服只能手工补单。根因不是消息丢了，而是没人定义过「支付已完成」这个事件。

当时团队拿到 PRD 就按名词拆了四个服务：订单、库存、支付、发货。交易侧认为「支付成功即订单完成」，履约侧认为「仓库出库才算完成」，库存侧把「锁定成功」记作占用。三个状态机各说各话，异步链路里缺一个明确的事件契约，发货单永远等不到触发条件。最后靠一个定时任务扫库兜底：

状态用字符串硬编码、跨服务直接读对方的表、重试没有幂等键，任何一处都能单独引发故障。但这些都是症状。真正的缺口在更早的一步：动手拆分之前，没有把「业务里究竟发生了哪些事、由谁触发、谁该响应」一次性摆到台面上对齐。

服务清单不是架构师拍出来的，是业务事实收敛出来的。下面把电商订单履约——下单、锁库存、支付、发货——从头走一遍，一直走到代码目录。

概念界定

事件风暴是一次建模工作坊：把懂业务的人和写代码的人聚在一起，按时间轴把业务事实铺开，再收敛成模型。它只产出四类东西，够用即可，不必先背概念。

  • 命令：触发动作的请求，由角色或外部系统发起，如「提交订单」「回调支付结果」。
  • 领域事件：已经发生、业务关心、用过去式命名的事实，如「订单已创建」「库存已锁定」。
  • 实体与聚合：命令作用于实体，事件由聚合根产生；聚合根是一致性边界。
  • 限界上下文：语义一致的边界，把模型按语义分组，是服务边界的候选。

四者的关系是一条可回环的链，这也是工作坊里便利贴的摆放顺序：

flowchart LR
    ACTOR["角色 / 外部系统"] -->|"发起"| CMD["命令"]
    CMD -->|"作用于"| AGG["聚合根 / 实体"]
    AGG -->|"产生"| EVT["领域事件"]
    EVT -->|"触发策略"| CMD
    AGG -->|"归入"| CTX["限界上下文"]

案例推演

第一步，贴事件，只发散不设计。 沿主链路按时间顺序铺开：订单已创建 → 库存已锁定 → 支付已完成 → 发货单已生成 → 商品已出库 → 订单已完成。再补异常分支：库存不足 → 库存锁定失败 → 订单已取消；支付超时 → 订单已关闭 → 库存已释放。这一步只写过去式事实，不讨论谁来实现、用什么中间件。

第二步，给每个事件回推命令与发起者。 事件不会凭空出现，它要么由命令产生，要么由策略自动触发。

命令 发起者 产生的领域事件
提交订单 买家 订单已创建
锁定库存 策略（订单已创建触发） 库存已锁定 / 库存锁定失败
发起支付 买家 —
回调支付结果 支付网关 支付已完成
创建发货单 策略（支付已完成触发） 发货单已生成
确认出库 仓库 商品已出库、订单已完成
关闭超时订单 定时任务 订单已关闭、库存已释放

「锁定库存」「创建发货单」这两行是自动命令，由上游事件触发。把它们明确标成策略，而不是埋在代码里，是后面状态机不再错位的起点。

第三步，从名词里识别实体与聚合。 判断标准只有一个：哪些对象必须同生共死、由同一事务守住不变量。

  • 订单与订单项必须同生共死，收货地址依附订单且无独立标识 → 订单聚合，订单为聚合根，地址是值对象。
  • SKU 的可用量与锁定记录必须一致，超卖与否在此判定 → 库存聚合，SKU 库存为聚合根。
  • 支付单与支付流水同属一次渠道请求，要一起对账 → 支付单聚合。
  • 发货单与发货项同属一次出库指令 → 发货单聚合。

「已支付订单不可修改收货地址」「可用库存不得为负」这类规则，分别由订单聚合根与库存聚合根把守，不落在编排层。

第四步，按语义冲突划限界上下文。 同一个词在不同语境里的模型不同，就该切开：交易语境里「订单」是带金额与状态的聚合；履约语境里它只是「待发货指令」，关心的是收货地址与 SKU 清单；库存语境里「库存」是可售数量，仓库作业语境里是货位与批次。据此得到四个上下文：交易、支付、库存、履约。跨上下文一律通过领域事件协作，不共享表、不直接调对方库。

flowchart LR
    subgraph T["限界上下文：交易"]
        O["订单（聚合根）"]
    end
    subgraph I["限界上下文：库存"]
        S["SKU 库存（聚合根）"]
    end
    subgraph P["限界上下文：支付"]
        M["支付单（聚合根）"]
    end
    subgraph F["限界上下文：履约"]
        H["发货单（聚合根）"]
    end
    O -->|"订单已创建"| S
    O -->|"订单已创建"| M
    S -->|"库存已锁定"| O
    M -->|"支付已完成"| O
    M -->|"支付已完成"| H
    H -->|"商品已出库"| O

第五步，收敛成服务清单与数据归属。 每个上下文一个服务，独占自己的库，数据归属写死，不给「顺手查一下对方表」留口子。

限界上下文 服务 聚合根 独占数据 发布的事件 订阅的事件
交易 order-service 订单 t_order、t_order_item 订单已创建、订单已关闭 库存已锁定、支付已完成、商品已出库
库存 inventory-service SKU 库存 t_sku_stock、t_stock_lock 库存已锁定、库存锁定失败、库存已释放 订单已创建、订单已关闭
支付 payment-service 支付单 t_payment、t_payment_txn 支付已完成 订单已创建
履约 fulfillment-service 发货单 t_shipment、t_shipment_item 发货单已生成、商品已出库 支付已完成

完整链路的消息流如下，虚线回流处都是领域事件，而不是同步 RPC：

sequenceDiagram
    participant U as 买家
    participant O as 交易
    participant I as 库存
    participant P as 支付
    participant F as 履约
    U->>O: 提交订单
    O->>O: 订单已创建（聚合根）
    O-->>I: 订单已创建
    O-->>P: 订单已创建
    I-->>O: 库存已锁定
    U->>P: 发起支付
    P-->>O: 支付已完成
    P-->>F: 支付已完成
    F->>F: 发货单已生成
    F-->>O: 商品已出库

三个决策各自有代价，值得写清楚。

库存锁定放在支付之前。 依据是钱货一致性：先占库存再收钱，避免付了款发不出货。代价是「锁了不付」必须补偿，于是要有超时关闭订单与库存释放事件，这是额外的状态与定时任务，不能省。

支付完成后用领域事件触发发货，不用交易服务同步调用履约服务。 同步调用会把两个服务的可用性绑死，还逼着交易服务了解发货接口的入参，边界随即被穿透。改用事件后，履约侧自行决定何时建单、缺货时如何排队。代价是引入最终一致性，发货状态会短暂落后于支付状态，需要前端与客服查询能接受这点延迟。

限界上下文不等于服务数量。 早期业务量小，交易与库存可以合在一个进程部署，但数据归属仍要按上表提前划清；一旦两张表被同一事务写惯，再拆就要动血。

代码与目录

先落聚合根。订单聚合根把状态机、不变量与领域事件登记收在一个类里，不依赖任何框架：

DomainEvent 是领域层定义的接口，OrderCreated、OrderPaid 是不可变事件对象。应用服务在事务提交后取走 drainEvents() 的结果，经资源库写入 Outbox 表再投递，聚合根本身不知道 MQ 的存在。状态枚举 CREATED → STOCK_LOCKED → PAID → SHIPPED → COMPLETED，异常分支落到 CANCELLED，与前面贴的事件一一对应。

再把模型元素映射到目录，确保便利贴上的每个产出都有代码落点：

事件风暴产出 代码落点
限界上下文（交易、支付、库存、履约） 顶层模块 *-context
命令：提交订单 application/command/PlaceOrderCommand.java
聚合根：订单 domain/model/aggregate/Order.java
值对象：金额、地址、订单号 domain/model/valueobject/
领域事件：订单已创建、订单已支付 domain/event/、shared-kernel/event/
资源库接口 domain/repository/OrderRepository.java
事件发布与订阅 infrastructure/messaging/

反模式与适用边界

  1. 跳过发散直接画服务框图。 按 PRD 名词拆服务，状态机各自为政，最后靠扫表补偿兜底，正是开篇那起故障。
  2. 把领域事件当技术消息。 事件是过去式的业务事实，带明确的业务语义与字段契约；写成 OrderMsg 这种技术信封，下游只能猜字段，契约等于没有。
  3. 聚合按表聚类或画得过大。 把订单、库存、支付塞进一个聚合，锁竞争和分布式事务随之而来；一致性边界应按不变量划，不按表数量划。
  4. 上下文之间共享数据库表。 数据归属没写死，边界只是目录名，一次「顺手 join 一下」就让拆分失效。
  5. 风暴开成一次性会议。 便利贴拍照归档、模型不落到代码目录，半年后无人能对上实现。

以下情形不必走完整流程：

情形 建议
业务规则稳定、以 CRUD 与报表为主 不做完整事件风暴，按子域直接划分
单体内部模块、无跨服务协作 领域事件退化为进程内事件，不引入 MQ
召集不到领域专家，需求只靠文档传递 先补沟通机制，否则风暴会变成开发自嗨
验证性原型、短期活动页 直接实现，保留重构空间
资金核心、强一致且不接受最终一致 优先收紧事务边界，限制事件解耦的范围

判断标准是一问：这次拆分的难点在业务语义对齐，还是在技术实现？ 前者值得开风暴、把模型一路落到目录；后者开再多的会也解决不了工程问题。

要点速查

阶段 动作 产出 常见错误
一 发散 按时间轴贴过去式事件 主链路 + 异常分支 边贴边讨论实现
二 回推 补命令、角色与策略 命令清单、自动触发点 漏掉策略，状态机断裂
三 聚类 按不变量识别聚合 聚合根、实体、值对象 按表聚类、聚合过大
四 划界 按语义冲突分上下文 限界上下文与映射 同名词强行共用模型
五 收敛 定服务清单与数据归属 服务、独占库、事件契约 共享表、边界等于目录名
六 落地 模型映射到代码目录 聚合根骨架、模块结构 便利贴归档即结束

一条主线：事件 → 命令 → 聚合 → 限界上下文 → 服务与数据归属 → 代码目录。中间任何一环跳过，下游都会以补偿任务的形式把代价还回来。

小结与参考

「支付成功未发货」这类故障，补一个定时任务只能止血。把下单到发货的事件、命令、聚合、上下文依次铺开并收敛，得到的是一份有数据归属的服务清单，以及一个能守住状态机的聚合根骨架。微服务的边界因此不是拍脑袋的结果，而是业务事实一步步推导出来的产物；模型能否落到目录，决定这次建模是留下了资产，还是只留下了一叠照片。
