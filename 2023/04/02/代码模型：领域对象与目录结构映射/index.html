代码模型：领域对象与目录结构映射

发表于 2023-04-02 分类于 架构设计
本文字数： 10k 阅读时长 ≈ 9 分钟

引言

一个类同时当实体、接口出参和业务计算载体，迟早会在某个 getter 上出事。本篇讲领域模型到代码目录的映射：DO、DTO、PO 与 Entity 各管什么，转换放在哪一层，以及怎样让领域层不依赖框架。

财务对账发现某日全部订单金额缩小了一百倍，最后定位到一行 getter。

某电商订单服务里只有一个 Order 类，它同时被三处使用：作为 JPA 实体映射 t_order 表，作为下单接口的出参由 Jackson 序列化，又在下单流程里承担金额计算。为了让前端直接显示「元」，有人在 getAmount() 里加了句除法。而库里 amount 存的是「分」。

Jackson 序列化出参时调它，Hibernate 脏检查与持久化也调它，内部运算还调它。一个 getter 服务三种用途，任何改法都会波及另外两种。

根因不是这行除法，而是这个类没有确定的身份：它既是数据库表的镜像，又是网络传输的载体，还是业务规则的宿主。三者对「金额」的语义本就不同——库里是分、接口是元、领域里是带币种的值对象——却被压进同一个字段。类似的事故还有另一种形态：领域对象上打满 @Entity、@Table、@JsonProperty，换 ORM、加缓存、发消息时，每动一处都要改业务类。

代码模型要解决的正是这件事：让领域对象拥有独立的类与独立的目录，并规定谁、在哪一层、把它翻译成别的对象。边界不落到目录上，分层就只是一句口号。

概念界定

先把容易混用的名词钉死。它们不是四种建模流派，而是同一份业务数据在不同边界上的四种形态。

名称 全称 所在层 职责 框架注解
DTO Data Transfer Object 接口层、应用层 跨网络传输、参数校验、字段裁剪与脱敏 可有 @NotNull、Jackson 注解
DO / 领域实体 Domain Object / Entity 领域层 承载状态与业务规则，聚合根把守不变量 零注解
PO Persistent Object 基础设施层 与表结构对齐，供 ORM 读写 @Entity、@Table（javax.persistence）
值对象 Value Object 领域层 不可变、无标识、描述属性（金额、地址） 零注解

有个坑必须点明：Entity 被两个体系占用了。领域驱动设计里的领域实体，是有唯一标识、有行为的领域对象；而 @Entity 是持久化注解，标记的是 PO。看到 Order 上挂着 @Entity，它就已经不是领域实体了。工程上的处理很直接：领域层里叫 Order，基础设施层里叫 OrderPO，用命名把两者切开，不靠注释提醒。

由此得到一条依赖规则：领域层不认识 DTO、PO 和任何框架；其余各层认识领域层。 转换是数据进入或离开领域模型时付出的代价，只能由外层承担。

flowchart LR
    JSON["请求 JSON"] --> DTO["DTO / Command<br/>接口层、应用层"]
    DTO -->|"接口层 Assembler"| DOM["Order 聚合根<br/>领域实体 + 值对象"]
    DOM -->|"基础设施层 Converter"| PO["OrderPO<br/>javax.persistence 注解"]
    PO --> DB["t_order 表"]
    DOM -.->|"定义"| REPO["资源库接口 OrderRepository"]
    REPO -.->|"实现"| IMPL["OrderRepositoryImpl"]

依赖方向同样要落到代码上，而不是画在文档里。

flowchart TB
    I["interfaces<br/>DTO / Assembler"] --> A["application<br/>用例编排"]
    A --> D["domain<br/>聚合根 / 值对象 / 资源库接口"]
    I --> INF["infrastructure<br/>PO / Converter / 资源库实现"]
    A --> INF
    INF -->|"编译期依赖指向领域层，实现其接口"| D

所有编译期箭头最终指向 domain，domain 不指向任何层、不 import 任何框架包。基础设施层实现领域层声明的资源库接口，由 Spring 在运行时注入——这才是「领域层不依赖框架」的实际含义。

案例推演

以交易限界上下文中的「提交订单」为例，把一次请求从接口走到库里，看四类对象各自在哪一刻出现。

第一步，接口层收口。 OrderController 接收 PlaceOrderRequest（DTO），用 javax.validation.constraints 做非空与格式校验。接口层的 Assembler 把它转成应用层的 PlaceOrderCommand，顺手完成单位归一：前端传「元」，命令里落成「分」。单位换算属于边界职责，不进领域对象。

第二步，应用层编排。 PlaceOrderAppService 开启事务，通过资源库拿到或构造 Order 聚合根，把命令交给 Order.place(...)。应用服务只负责「先做什么、后做什么」，不写「金额如何累加」「哪种状态允许改地址」这类规则。

第三步，领域层执行规则。 聚合根内部用 Money 值对象计算总额、校验订单项非空、把状态置为 CREATED、登记 OrderCreated 领域事件。此时的 Order 上没有 @Entity、没有 @JsonProperty、没有 HttpServletRequest，它是一个纯 JDK 对象。

第四步，基础设施层持久化。 OrderRepositoryImpl.save(Order) 调用显式 Converter 把 Order 翻成 OrderPO：值对象 Money 打散为 amount、currency 两列，状态枚举落成 status_code，订单项列表拆成 OrderItemPO 集合。领域事件写入 Outbox 表，再由消息适配层投递到 MQ。

第五步，接口层组装出参。 应用服务把结果交回 Assembler 生成 OrderResponse，金额由分转元、手机号掩码。领域对象从头到尾不知道「前端要元」。

三个取舍值得单独说清。

其一，转换放在外层，不放在领域层。领域层一旦 import DTO 或 PO，换 ORM、换 MQ、接口加字段都要改领域层，领域模型随即退化成数据表镜像。资源库接口定义在领域层、实现在基础设施层，是隔离的关键支点。

其二，用显式 Converter，不用反射拷贝工具。BeanUtils.copyProperties 在字段名相同、语义不同时会静默出错：status 一边是枚举一边是字符串，address 一边是值对象一边是五个平铺列，反射工具要么报类型不匹配，要么干脆漏拷。显式转换把「语义差异」集中在唯一一处，可单测、可评审。

其三，「领域层不依赖框架」要拆成可执行的具体做法：领域包内不出现 javax.persistence.*、org.springframework.*、com.fasterxml.jackson.*；资源库方法签名返回领域对象而非 PO；领域事件是普通对象；@Transactional 打在应用服务而非聚合根；领域对象由构造器创建，不交给 Spring 容器管理。少了这几条，分层就只剩目录名。

反模式与适用边界

  1. 一个类走天下。 实体、DTO、领域对象三合一，框架注解穿透所有层，改一处展示逻辑引发资损，就是开篇那起事故。
  2. 用反射工具无脑拷贝。 字段名相同、语义不同时静默出错；金额单位、枚举与字符串、值对象与平铺列，都是重灾区。
  3. 在领域层做转换。 领域对象 import 了 DTO 或 PO，或干脆打上 @Entity，领域模型随即被存储格式与传输格式绑架。
  4. 转换逻辑四处散落。 每个 Controller、每个 Service 各写一遍拷贝，同一字段出现多种口径，排查时无从对齐。
  5. 目录按技术名词一刀切。 全部平铺成 controller / service / dao，聚合根、值对象、领域事件无处安放，代码很快退回事务脚本。

以下情形不必引入这套四类对象与显式转换：

情形 建议
以 CRUD、报表、管理后台为主，几乎没有业务规则 PO 直通即可，DTO 可省，不建领域层
纯查询接口、读写比极高 走读模型直接投影，不经过聚合根与 Converter
一次性数据迁移、离线脚本 不分层，脚本内闭环
迭代以字段增删为主、团队规模很小 显式 Assembler 的维护成本可能高于收益
转换成为明确性能热点 评估同构映射或零拷贝方案，主动牺牲部分隔离

判断标准可以压缩成一问：这个模块的价值来自业务规则，还是来自数据搬运？ 前者值得为领域对象单独建层与目录，后者分层只会增加拷贝。

要点速查

判断项 结论
DTO 放哪 接口层，可延伸到应用层命令对象
PO 放哪 基础设施层，带 @Entity、@Table
领域对象能否带框架注解 不能，领域层零框架依赖
值对象怎么落库 打散成列，由 Converter 显式拆装
谁负责 DTO 与领域对象互转 接口层 Assembler、应用层边界
谁负责领域对象与 PO 互转 基础设施层 Converter
跨层拷贝用什么 显式转换，不用反射拷贝工具
单位换算、脱敏放哪 边界层，不进领域对象
资源库接口与实现 接口在领域层，实现在基础设施层
编译期依赖方向 一律指向领域层

一条主线：接口层收 DTO → 应用层编排 → 领域层执行规则 → 基础设施层转 PO 落库，转换只发生在进出领域层的那道门上。

小结与参考

那起金额缩小百倍的事故，修复只改了一行 getter，但真正让它不再复发的是把 Order 拆成三个各司其职的类，并把转换收拢到唯一一层。目录结构不是审美问题：它决定了框架依赖能否被挡在领域模型之外，也决定了换存储、换接口时改动会扩散到哪里。业务复杂度高的模块，值得为这条边界付出几个转换类的代价；数据搬运型的模块，则不必。
