实践总结：边界、演进策略与分布式设计

发表于 2023-04-11 分类于 架构设计
本文字数： 6.3k 阅读时长 ≈ 6 分钟

引言

把单体的事务写法原样搬进分布式环境，库存被扣穿只是时间问题。本篇汇总生产落地里最容易失守的几处判断，从一次超卖事故出发，给出服务化改造的固定顺序，以及分布式事务、幂等与对账的收敛手段。

一次服务化上线后的大促，库存被扣穿了。原因不是流量超预估，而是一段沿用自单体的写法被原样搬进了分布式环境：

网络抖动时这条链路分裂成两种不一致：订单写成功、扣减请求超时后重试，库存被扣两次；或者扣减成功、订单事务随后回滚，库存被永久占用。事后团队想用分布式事务框架兜底，把全局事务套在这条长链路上，大促时全局锁又把数据库拖垮。

这类事故的根因不在选了哪个事务框架，而在三件事从未被定清楚：哪些数据必须同生共死，也就是边界；老代码按什么路径退出，也就是演进策略；跨边界失败后如何收敛，也就是分布式设计。三者缺一，补偿任务、对账脚本和半夜告警就会变成常态。

分布式系统里的一致性，不是靠一个框架兜底，而是先把边界划对，再为跨边界的失败设计一条确定的收敛路径。

概念界定

把三个词压到工程语境里。

边界判定：区分两种一致性范围。同一限界上下文内、由同一个本地事务守住的一致性，是强一致；跨上下文、跨进程的一致性，只能按最终一致设计。聚合根是前者的粒度，限界上下文是后者的起点。

演进策略：遗留系统退出方式。绞杀者在外围加路由门面，让新流量走新服务，旧系统逐步退为只读直至下线；修缮者不动外部入口，在旧系统内部按模块抽接口、换实现，逐个替换后再搬出去。

分布式设计三件套：分布式事务决定跨边界写入如何原子化，幂等决定重试是否安全，数据一致性决定不一致窗口内如何发现与收敛。

边界内一次本地事务把业务写入与事件登记一起提交；跨边界只投递事件，由消费端用幂等与补偿收敛。这条分界线是整个分布式设计的地基。

案例推演

以订单履约的服务化改造为例，把三件事依次走过。

先判边界。 订单与订单项必须同事务，金额不变量由订单聚合根把守；SKU 可售量与锁定记录必须同事务，超卖与否在此判定。这两组数据各自收进一个限界上下文，独占一个库。订单与库存之间不共享表，用「订单已创建」「库存已锁定」两个领域事件衔接。判断时问三句就够了：规则失效时业务能否容忍短暂不一致？这些数据是否总被同一事务修改？语义差异能否用一次事件通知替代共享表？三句都指向「能容忍、不同生命周期、可事件替代」，就该跨边界；反之收进同一边界。

由此得到一份拆分原则清单，顺序不能颠倒：

  1. 先按不变量定边界，再定部署单元；同一不变量的数据不跨库。
  2. 一个服务独占一份数据，跨服务只走接口与领域事件，不共享表、不跨库 join。
  3. 边界内用本地事务守住强一致；跨边界只接受最终一致，并显式写下不一致窗口。
  4. 聚合根保持小，跨聚合只持有对方标识，不持有对象引用，避免大事务与锁竞争。
  5. 能合并部署就先合并：两个上下文若始终同团队、同发布节奏、同生命周期，不急着拆成进程。
  6. 切流量之前先具备幂等、对账、链路追踪与回退开关，否则不动。
  7. 每次只切一个维度，保留旧路径可回退，双写期必须开对账。

再定演进路径。 这个单体跑了几年，库里十几张表、若干存储过程与定时任务。网关层还能加路由，新上的履约能力希望快速上线；但支付模块被十几个内部系统调用，入口契约动不了。因此整体以绞杀者为主、支付局部用修缮者：新流量经门面进新服务，存量订单继续走旧库，两边通过事件同步，双写期靠对账兜底。

两种策略的适用条件差别很具体，选错比不选更贵：

维度 绞杀者 修缮者
切入方式 外围加路由门面，按流量或业务维度灰度 内部按模块抽接口、替换实现
外部入口 可变，允许加一层代理 不可变，契约被众多调用方锁定
旧系统处置 逐步退为只读，最终下线 持续运行，模块被逐个替换
适用条件 能按维度切流、允许双跑与双写过渡、有新业务要抢时间 无法加代理、耦合集中在内部、切换成本高于重构
数据迁移 需同步或双写，并配长期对账 库内先分离表，条件成熟再拆库
主要风险 双写期不一致、路由回退复杂 周期长、收益滞后、容易半途而废
典型信号 旧系统不敢动，但新需求等不起 入口动不了，调用方一大堆

    F -->|"新业务与灰度流量"| N["新服务：库存、履约"]
    F -->|"存量流量"| O["订单单体"]
    N --> S["事件同步 / 双写"]

代价要提前认：绞杀者会引入一段双写期，新旧两份数据在窗口内必然不一致，对账与回退开关不是可选项；修缮者则要接受很长一段时间看不到架构收益，最容易在半途被叫停。两条路都要求先把可观测性补齐。

最后收敛跨边界失败。 本案例不把全局事务套在「下单 → 锁库存 → 支付 → 发货」这条长链路上：XA 或长事务型 TCC 会把锁持有时间拉到整条链路，大促时首先压垮库。做法是边界内本地事务 + Outbox 保证「业务写入」与「事件登记」原子提交，跨服务用事件驱动与补偿。库存扣减、支付回调、发货单创建一律带幂等键；一致性靠最终一致 + 对账 + 兜底补偿 + 告警，并明确定义「支付成功到发货单可见」允许延迟多久。超过窗口未收敛的，走人工或自动补偿，而不是让状态悬着。

代码与目录

Outbox 把事件登记塞进同一个本地事务，这是不引入分布式事务也能拿到原子性的关键：

orderRepository 是领域层声明的资源库接口，实现落在基础设施层；事件不在此处直接发 MQ，避免「库写了、消息没发」或「消息发了、库回滚」的裂缝。

消费端的幂等靠一张带唯一索引的表，而不是靠「消息应该不会重复」的假设：

idempotency_record 对 key 建唯一索引，tryInsert 用一次插入是否成功判定首处理；重复消息在唯一约束处失败后直接返回。幂等键由「业务单号 + 操作类型」拼成，不用消息中间件自带的 ID——后者在重投或人工重放时会变。两段代码合起来，退役期的双写、事件重投与超时重试都落在同一套收敛机制里。

反模式与适用边界

  1. 边界按表或按团队人数划。 跨服务共享表、跨库 join，边界只剩目录名，一次「顺手查一下」就让拆分失效。
  2. 长链路套强一致事务。 把全局事务盖在下单到发货的全流程上，锁持有时间随链路线性增长，大促时先拖垮数据库。
  3. 双写不停、对账不上。 绞杀者迁移期新旧两套数据长期分叉，既没有对账也没有回退开关，出问题只能停机。
  4. 消费端不做幂等。 默认消息不重复，超时重试即重复扣减、重复发货，开篇的库存被扣穿正是这么来的。
  5. 把最终一致当成不用管一致。 没有不一致窗口定义、没有补偿、没有告警，状态悬着无人知晓。

以下情形不宜照这套做法推进：

情形 建议
资金记账核心，强一致且不接受任何不一致窗口 收进同一边界用本地事务，不拆、不做最终一致
遗留系统入口无法改、也找不到灰度维度 用修缮者，不硬上加门面的绞杀者
调用链极短、QPS 低、两模块同生命周期同团队 合并部署更经济，不引入分布式复杂度
尚无幂等、对账、链路追踪与回退能力 先补底座，再谈切流量
一次性交付、后续不再演进 不投入演进式改造的成本

判断标准始终是一问：这次不一致的代价，是否高于为消除它引入的分布式复杂度？ 答案是否，就别拆。

要点速查

主题 要点 推荐做法 代价 / 反例
分布式事务 跨边界原子写入 边界内本地事务 + Outbox；跨服务用事件与补偿 长链路套 XA / 长事务 TCC，锁竞争压垮库
幂等 重试与重投安全 业务单号 + 操作类型作键，唯一索引去重 依赖消息 ID，重放时失效
数据一致性 不一致窗口收敛 最终一致 + 对账 + 兜底补偿 + 告警 无窗口定义、无监控，状态悬空
边界判定 强一致与最终一致的分界 不变量同库、同事务；跨库只走事件 共享表、跨库 join
演进选型 遗留系统退出 能切流用绞杀者，入口锁死用修缮者 双写无对账、修缮半途而废
拆分前提 切流量前的底座 幂等、对账、追踪、回退开关齐备 底座未建先切流

再压成三条可执行的结论：能不拆就不拆；必须拆就先把边界内的事务守住；出了边界，只允许带幂等与对账的最终一致。

小结与参考

库存被扣穿这类事故，补一个分布式事务框架往往越补越糟。可收敛的做法有固定顺序：按不变量划对边界，让强一致留在边界内；为遗留系统选一条与入口约束匹配的退出路径，并认下双写期与对账的代价；跨边界的每一次失败，都用幂等、补偿与监控给出确定的归宿。架构演进不是把单体改成多少进程，而是每引入一处分布式复杂度，都清楚它换来了什么、又必须配哪套收敛机制。
