高并发（二）架构分层与高可用、易扩展设计

发表于 2023-04-28 分类于 架构设计 ， 高并发
本文字数： 6.3k 阅读时长 ≈ 6 分钟

引言

分层的目的是隔离变更和故障，不是照着模板搭三层目录。高可用要靠冗余、故障发现、切换三件事凑齐，光堆副本不产生可用性；易扩展靠无状态和可水平拆分，有状态那部分才是难点。比如整点开抢的下单链路，网关、应用、缓存都按峰值扩了机器，某台应用进程崩了仍有请求被打过去，错误率抬起来，缺的不是机器数，是摘除和切换的判断。

概念界定

分层是把系统按职责切成若干层，相邻层之间才允许依赖和数据流转，跨层直接访问会让边界失效。一个常见误区是把分层等同于目录规范：建了 web、service、dao 三个包就算分层了。真正的边界在于改动是否只落在一层——数据库地址变了只该改数据访问层，如果表现层也能直接读写库，这个改动就得散到多处，层数再多也挡不住变化扩散。业务复杂到一定量级，表现层容易顺手把「查用户、没有就创建」这类编排逻辑揽过去，边界就此糊掉；把通用能力下沉成单独一层，提供原子接口，由业务层负责编排，边界才拉得回来。

分层有代价。每层独立部署后，一次请求要多走几次网络，也就是多一跳；多一个中间层，调试时就要多追一段调用链，改一个小需求也可能要动好几层的透传代码。收益要能覆盖这两份成本才值得做：要么改动被隔离在单层，要么某一层能单独扩容。只做数据透传、不带任何判断的层，留着就是负担，不如删掉。

高可用不等于机器多。可用性用 MTBF 和 MTTR 度量，写成比例是 MTBF /（MTBF + MTTR），几个九描述的就是这个比例。三个九的年故障时间约 8 小时，四个九压到 1 小时以内，到这一步靠人盯报警已经做不到，得让机器自己完成发现和切换。冗余只是备好了候选节点，故障发现决定什么时候知道坏了，切换决定流量去哪儿，缺任何一件，副本都只是闲置成本。对等节点之间切换最简单，任意一个都能顶上；带主备之分的节点要先检测、再选主，结果还得在多个备节点之间达成一致，复杂度高一个量级。

易扩展的分界线同样落在状态上。无状态服务加机器就能线性分担流量，存储这类有状态的部分加减节点要搬数据、要重分布，才是扩展真正的瓶颈。所以判断一套结构能不能扩，不是问加了几台机器，是问加完之后流量有没有被线性接走，以及有状态那层有没有跟着一起成为新瓶颈。

案例推演

把已经定下的容量配置摆进分层结构：网关 6 台、应用 20 台、缓存 3 分片，数据库同步写入不成立。设定仍是单 SKU、库存 5000 件、预约 30 万人、整点开抢，峰值 2 万 QPS 是日常下单 200 QPS 的 100 倍，验收目标「2 万 QPS 下 P99 < 200ms、P999 < 1s、错误率 < 0.1%」，链路为下单 → 锁库存 → 支付 → 发货。

按层看谁能扩。网关做的是鉴权和限流，本身不存请求状态，6 台完全对等，任何一台挂了，负载均衡把流量分给其余 5 台即可，扩容就是加机器。应用 20 台同理，前提是会话、库存预检结果这些状态全部外置到缓存，别落在进程内存里；一旦有人把「已抢到的标记」写进本地 Map，这台机器立刻变成有状态节点，扩容和切换同时失效。缓存 3 分片是有状态的，分片规则和热点 key 的分布绑在一起，加分片要迁数据、重算路由，不能像应用那样随手加。数据库那一层同步写入扛不住 2 万 TPS，写入得丢进消息队列按库能承受的速率排队，这层既不能简单水平扩，也是整条链路的瓶颈落点。

层 有无状态 扩展方式 单机故障切换路径 代价
网关 无状态 加机器 + 负载均衡 摘除节点，流量分给其余对等节点 近乎为零
应用 无状态（状态外置） 加机器 摘除节点，会话由缓存续上 必须保证本地不存状态
缓存 有状态（分片） 加分片 + 数据迁移 主备切换 / 分片重定向 迁移成本、热点重分布
数据库 有状态 先垂直后水平拆分 主备切换、选主 复制延迟、跨片聚合

扩展方式落到每一层都不一样，这张表比一句「都做成无状态」有用：前三行里只有网关和应用能靠加机器解决，后两行都要先处理数据和一致性。

flowchart LR
    HB["心跳 / 健康检查"] -->|超时未响应| DET["判定节点故障"]
    DET --> RM["从可用列表摘除"]
    RM --> R1{"节点是否对等"}
    R1 -->|对等：网关 / 应用| RR["负载均衡把流量分给其余节点"]
    R1 -->|主备：缓存 / 数据库| EL["备节点选主并达成一致"]
    EL --> SW["切主 + 更新路由"]

切换路径要能自动跑完才算高可用。心跳或健康检查发现超时，先把节点从可用列表摘掉；对等节点直接把流量分给其余机器，带主备的层要先选主、达成一致，再更新路由。四个九的目标下这一串必须由机器完成，等人登录服务器处理，十分钟早就超出预算。超时控制也得跟上：下游一次慢调用若按几十秒的超时等待，调用方线程被长期占住，一个慢点就拖垮整片应用；把超时压到 P99 量级、留出重试，才能把损失限制在少量请求。这是取舍，不是无损：被超时砍掉的那部分请求对用户是有损的，换的是整体不雪崩。

这份路由有明确边界：它只覆盖对等节点，主备层的选主和一致性不在这里，那段逻辑要单独做。摘除靠连续失败计数，阈值和探测间隔得按 P99 调，太敏感会把一次网络抖动误判成故障、来回切，太迟钝又起不到隔离作用；恢复窗口到了先放少量流量试探，别一上来全量切回。故障发现、摘除、恢复三件事凑齐，冗余才算转成可用性。

反模式与适用边界

  1. 把分层做成目录模板。 包建齐了，表现层仍旧直接读写库，或者把业务编排散在多个层里，边界形同虚设，改动一来照样到处改。
  2. 只堆冗余不做故障发现和切换。 副本平时不承载判断，故障时没人切、没人知道坏了，多出来的机器只是成本，不是可用性。
  3. 把有状态服务当无状态扩。 缓存分片随手加机器却不迁数据，热点没重分布、路由没更新，扩容后读不到旧数据，比不扩还糟。
  4. 把状态写进应用进程。 会话或库存标记落在本地内存，节点变成有状态，扩容的新机器接不住老请求，故障切换也会丢状态。
  5. 跨层调用不设超时或一律给几十秒。 慢请求占住调用方线程不放，一处变慢拖垮整片，超时该按 P99 定并留出重试。

下面这张表回答什么情况不必这么做，这些情形下分层、冗余与切换可以不做或只做一半：

情形 为什么不必套 建议做法
内部后台、报表系统，峰值远低于单机拐点 故障影响面小，分层与自动切换的收益抵不过复杂度 单库单应用 + 基础监控
一次性静态活动页 请求在 CDN 被挡完，没有分层扩容的对象 静态化加 CDN
MVP 验证期，业务边界一周一变 层边界还没稳定，先分层等于反复重构 按模块分文件，不独立部署
低流量的资金类强事务操作 首要目标是一致性与可追溯，不是可用性的几个九 优先正确性，副本只做备份不做自动切换
只读配置下发类系统 性能几乎不重要，可用却不能断 多副本 + 客户端缓存兜底，别按流量模型扩展

小结与参考

把这三件事拆开看容易走偏：分层解决的是改动落在哪一层，冗余只是备好可替换的节点，真正决定可用性的是故障能不能被机器发现并自动切走。无状态让替换成本趋近于零，有状态部分则要迁数据、选主、达成一致，扩展的难点全压在这里。判断一套结构是否成立，问三句就够：改动是否收敛在单层、故障是否无需人工介入就能切、加机器是否真能线性分担流量。答不上来，层数堆得再多也只是把目录分得整齐些。
