MySQL（三）索引——结构与设计取舍

发表于 2024-01-10 分类于 数据库
本文字数： 5.9k 阅读时长 ≈ 5 分钟

引言

查询慢了加个索引，是常见的第一反应。索引为什么能加快查询，加错了又会带来什么代价，很多说法停在口头经验上。这篇沿着 InnoDB 的索引结构往下走：先看清 B+ 树里主键索引和二级索引各存了什么，为什么有的查询要回表、有的不用；再看联合索引怎么靠最左前缀复用，字符串字段怎么取舍前缀长度；最后落到普通索引和唯一索引在更新路径上的差别。索引设计没有通用答案，但每个选择背后的代价是固定的，看清代价再权衡。

B+ 树与聚簇索引

索引是表的目录。能当目录的数据结构不少：哈希表适合等值查询，范围查询要全扫；有序数组查询快，插一条就得挪动后面所有记录，只适合不再修改的数据；搜索树查询和更新的复杂度都是对数级，但要落到磁盘上，二叉的高度就成了问题。一百万个节点的平衡二叉树高约 20，查一行可能访问 20 个数据块，机械盘每次随机读约 10ms，这个延迟扛不住。

数据库用的是 N 叉树，N 由数据页大小决定。以一个整数字段索引为例，一个节点大约能放 1200 个键值，树高 4 时已能存 17 亿个值。根节点常驻内存，十亿行的表查一个值最多访问三次磁盘，第二层也大概率在内存里，平均次数更少。B+ 树被选中，靠的是贴合磁盘的读写粒度，用很少的磁盘访问次数定位记录。

InnoDB 是索引组织表，数据按主键顺序存放在 B+ 树里，每个索引对应一棵树。两棵树的叶子节点内容不同：

    subgraph PK["主键索引树（聚簇索引）"]
    direction TB
    P1["根节点 100 / 300 / 500"] --> P2["叶节点<br/>100 → 整行 R1"]
    P1 --> P3["叶节点<br/>200 → 整行 R2"]
    P1 --> P4["叶节点<br/>500 → 整行 R5"]
    end
    subgraph SK["k 索引树（二级索引）"]
    direction TB
    S1["根节点 1 / 3 / 5"] --> S2["叶节点<br/>k=1 → 主键 100"]
    S1 --> S3["叶节点<br/>k=3 → 主键 300"]
    S1 --> S4["叶节点<br/>k=5 → 主键 500"]
    end
    S4 -. "拿主键再查一次" .-> P4

主键索引的叶子节点存整行数据，叫聚簇索引；二级索引的叶子节点存主键的值，叫二级索引。select * from T where ID=500 搜一棵树就够，select * from T where k=5 要先在 k 树上取到主键 500，再到主键树查整行，这第二步叫回表。所以基于二级索引的查询要多扫一棵树，能用主键查就尽量用主键。

B+ 树为了维持有序，插入新值时要做维护。按主键 100、200、300、500、600 的顺序，插 700 直接在末尾追加；插 400 就得挪动后面的数据腾位置。如果目标数据页已经满了，还要申请新页、搬一部分数据过去，这就是页分裂，性能受影响，页的利用率也掉到大约一半。删数据后相邻两页利用率太低，又会触发页合并。

自增主键的价值就在这里。新记录的主键值递增，每次插入都是追加，不挪动其他记录，也不触发叶子节点分裂。用业务字段做主键，往往保证不了有序插入，写入成本更高。空间上也有差别：二级索引的叶子节点都带一份主键值，用身份证号当主键，每个叶子节点约占 20 字节；用整型只要 4 字节，长整型 8 字节。主键越长，所有二级索引跟着膨胀。

也有用业务字段直接做主键的场景。表只有一个索引，而且这个索引必须唯一——典型的 KV 结构，没有其他二级索引要照顾，直接把这个唯一字段设为主键，查询一次树搜索就能拿到整行，省掉回表。

回表与覆盖索引

用一张带主键 ID、字段 k 和字符串 s 的表看回表的成本：

执行过程是：在 k 树找到 k=3，取出主键 300，回主键树查整行；在 k 树取下一条 k=5，取出主键 500，再回主键树一次；再取下一条 k=6，不满足条件结束。k 树读了 3 条记录，回表 2 次。回表的次数，就是需要整行数据的次数。

如果查询改成 select ID from T where k between 3 and 5，要的 ID 已经在 k 树的叶子节点上，直接返回，一次回表都不用。这时称索引 k 覆盖了查询需求，叫覆盖索引。覆盖索引减少树搜索次数，是常用的优化手段。要注意引擎内部在 k 树上读了三条记录，Server 层拿到的是两条结果，所以 rows_examined 记的是 2。

flowchart LR
    Q["where k between 3 and 5"] --> K["在 k 索引树定位<br/>读到 3 条记录"]
    K --> B{"要返回的字段<br/>都在 k 树上?"}
    B -->|"否：select *"| R["按主键回表 2 次<br/>取整行数据"]
    B -->|"是：select ID"| C["直接返回结果<br/>回表 0 次"]

覆盖索引还能省掉建索引的纠结。市民表上已经有身份证号索引，如果”按身份证号查姓名”是高频请求，可以建一个（身份证号，姓名）联合索引，让这个请求走覆盖索引，不再回表读整行。冗余一个索引字段换来高频请求的提速，值不值要看请求频率和字段维护成本。索引越多，写入时的维护负担越重，这一步需要业务侧权衡。

最左前缀与前缀索引

为每种查询各建一个索引，索引会多到难以维护。B+ 树可以利用联合索引的最左前缀来定位记录。以（name，age）联合索引为例，索引项按定义里的字段顺序排序：先按 name 排，name 相同再按 age 排。查 name='张三' 能快速定位到第一条满足的记录再向后遍历；查 name like '张%' 也可以用上这个索引。最左前缀可以是最左 N 个字段，也可以是字符串索引的最左 M 个字符。

由此得到安排联合索引字段顺序的原则：看复用能力。有了 (a,b)，一般就不用单独在 a 上建索引，a 是最左前缀。只有 b 条件的查询用不上 (a,b)，得另建 (b) 索引，这时按空间决定——name 字段比 age 大，就建（name，age）加（age），把大的字段放前面能省索引空间。

最左前缀只负责定位，索引里靠后的字段还能帮忙过滤。查名字第一个字是张、年龄 10 岁的男孩，条件落在（name，age）上，name 用 ‘张%’ 定位，age 在索引里就有值。引擎在遍历索引时先判断 age 是否等于 10，把不满足的记录直接跳过，只让符合的回表。这就是索引下推，效果是回表次数从 4 次降到 2 次：

flowchart LR
    subgraph OLD["没有下推"]
    direction TB
    O1["name like '张%'<br/>取出 4 条索引记录"] --> O2["逐条回表<br/>回表 4 次"]
    O2 --> O3["Server 层再判断<br/>age 和 ismale"]
    end
    subgraph NEW["有下推"]
    direction TB
    N1["name like '张%'<br/>遍历时判断 age"] --> N2["过滤掉 age 不符的<br/>只对 2 条回表"]
    N2 --> N3["回表 2 次"]
    end

字符串字段上，完整索引占空间，可以只取前缀建索引。email 上建 index(email) 包含整个字符串，index(email(6)) 每个值只存前 6 个字节，省空间，代价是可能多条记录共享同一个前缀。select id,name,email from SUser where email='zhangssxyz@xxx.com' 用 email(6) 时，前 6 字节 ‘zhangs’ 可能命中多条，每条都要回表拿完整 email 再比对，扫描行数从 1 变成 4；把前缀改成 email(7)，命中的只剩一条，又回到扫描一行。

前缀多长合适，看区分度。先 select count(distinct email) as L from SUser 算出全列不同值的数量，再用 count(distinct left(email,4)) 到 count(distinct left(email,7)) 逐段比较，设定一个可接受的损失比例，比如 5%，取第一个不低于 L×95% 的长度。前缀索引还有个容易被忽略的代价：即使 select id,email from SUser where email='...' 只要求返回索引里已有的字段，InnoDB 仍然要回表，因为系统不确定前缀是否截断了完整信息，覆盖索引在这里用不上。

身份证号这类字段前几位是地址码，同县的人前缀相同，前缀索引的区分度很差。等值查询场景下可以换两种做法。一是倒序存储，把身份证号倒过来存、建前缀索引，查询时用 reverse() 处理输入，末 6 位没有地址码，区分度够用。二是加一个整数字段存 crc32() 校验码，在校验码上建索引，查询时 where id_card_crc=crc32('...') and id_card='...'，用精确比对兜住哈希冲突，索引长度降到 4 字节。两者都不支持范围查询；倒序存储不额外占字段空间、CPU 消耗略小，哈希字段的查询性能更稳定，平均扫描行数接近 1。

普通索引与唯一索引

字段值唯一时，建唯一索引还是普通索引？查询能力上没有差别。普通索引找到第一条满足的记录后，还要看下一有没有相同值；唯一索引找到一条就停。这个差别落在数据页内部，一次指针寻找加一次判断，而页早就在内存里，成本相对 CPU 可以忽略。

更新路径上的差别更值得看。InnoDB 更新一个数据页时，如果目标页不在内存，普通索引可以把这次改动缓存在 change buffer 里，记一笔就结束，不必从磁盘读入数据页；唯一索引必须先判断值是否重复，这要求把数据页读进内存，既然页已经在内存，直接更新更快，change buffer 就用不上了。change buffer 里的记录会在访问这个页、后台线程定时触发或正常关闭时 merge 回原数据页，它本身也会持久化，内存里存着的只是它的一份拷贝。

flowchart TD
    U["插入一条记录<br/>普通索引"] --> M{"目标数据页<br/>在内存?"}
    M -->|在| D["直接更新内存页"]
    M -->|不在| C["改动记入 change buffer<br/>不必读磁盘"]
    C --> W["写入 redo log 后<br/>语句即可返回"]
    W --> G["后续读到该页时<br/>merge 回数据页"]

change buffer 对写多读少的业务收益最大，账单类、日志类系统页面写完很少马上被读，merge 之前攒的改动越多越划算。反过来，写入后立刻查询的业务会马上触发 merge，随机 IO 一次没省，还多了维护 change buffer 的代价。redolog 和 change buffer 都在减少随机 IO，分工不同：前者把随机写转成顺序写，后者省掉随机读。

所以业务能保证字段不重复时，从性能出发优先普通索引，机械盘上的历史数据表尤其如此。唯一索引没法借 change buffer 缓存改动，把普通索引改成唯一索引，可能直接把更新性能拖垮：大量插入的业务，内存命中率会从九成多掉到七成多，更新语句排队堵住。反过来，业务无法保证唯一，或者本来就要求数据库强约束，就必须用唯一索引，这时它带来的写入代价是买约束的票价。好友关系这类场景还专门靠唯一索引做并发控制：两张表的唯一约束加上固定顺序的写入，让”互相关注”的双方必然有一方撞上行锁冲突，避免并发下漏建好友关系。

索引设计速查

现象或需求 背后的机制 处理方向
二级索引查询多扫一棵树 叶子节点只存主键，要回表 高频查询用覆盖索引或走主键
写入时页分裂、空间利用率下降 主键无序插入 用自增主键，除非是单索引 KV 表
联合索引只用得上第一个字段 B+ 树按最左前缀排序 按复用能力和字段大小安排顺序
like 前缀查询回表多 下推前不判断索引内其他字段 靠索引下推提前过滤；前缀长度看区分度
身份证前几位区分度低 地址码重复 倒序存储或 hash 字段，只支持等值查询
普通索引改唯一索引后写入变慢 唯一索引没法缓存改动到 change buffer 业务能保证唯一就用普通索引
写完马上查询，change buffer 没收益 访问页立即触发 merge 关闭 change buffer

小结与参考

索引的取舍都落在结构上：聚簇索引存整行、二级索引存主键，决定了回表；B+ 树按最左前缀排序，决定了联合索引能复用多少；change buffer 只对普通索引开放，决定了查询和更新两条路径的分岔。设计索引时，先算清查询能省几次树搜索、写入要付多少维护成本，再决定建哪些、建多长、建不建唯一。
