MySQL（四）锁机制——表锁、行锁与间隙锁

发表于 2024-01-21 分类于 数据库
本文字数： 5k 阅读时长 ≈ 5 分钟

引言

一条语句卡住，屏幕上只显示 Waiting for lock，具体在等谁、锁的范围有多大，往往要靠猜。MySQL 的锁分散在几个层次：备份时要锁整个实例，改表结构会碰到元数据锁，更新同一行是行锁，范围查询还会带上间隙锁。这些锁各有触发场景，也各有代价。这篇按锁的粒度从大到小走一遍，把每种锁解决什么问题、什么时候会互相挡路讲清楚，最后落到 next-key lock 的加锁规则，让一条语句该锁多大范围能推算出来。

全局锁与元数据锁

全局锁锁的是整个数据库实例。MySQL 提供的命令是 flush tables with read lock（FTWRL），执行之后整个库进入只读：增删改、建表改表、更新类事务的提交都会被阻塞。它的典型用途是全库逻辑备份——把每张表都查出来存成文本，如果备份期间有写入，各表备份的时点就不一致。举个常见的例子：先备份账户余额表，用户买课扣了余额并写入课程表，再备份课程表，备份结果就成了钱没扣、课多了，拿这份数据恢复，账就对不上。

备份真正需要的是一致性视图，禁止写入只是拿到它的手段之一。可重复读隔离级别下开启一个事务就能拿到这个视图，所以 mysqldump --single-transaction 在导数据前先启动事务，靠 MVCC 保证备份过程中数据照常更新。这个办法只适用于所有表都用事务引擎的库；一旦有 MyISAM 这类不支持事务的表，备份时读到的总是最新数据，一致性被破坏，这时还得退回 FTWRL。也有 set global readonly=true 能让全库只读，一般不推荐：readonly 的值常被用来判断主备角色，影响面更大；客户端异常断开时，FTWRL 会自动释放锁，readonly 却会一直留着，把库卡在不可写状态。

表级锁有两种。一种是显式表锁 lock tables ... read/write，除了限制别的线程，也限定本线程接下来能访问哪些表，所以在支持行锁的 InnoDB 上基本不用它。另一种是元数据锁（MDL），访问表时自动加上，用来防止查询遍历到一半表结构被改。增删改查加 MDL 读锁，改表结构加 MDL 写锁；读锁之间不互斥，读写锁之间和写锁之间互斥。

MDL 有个常见的坑：给小表加字段，整个库挂住。事务拿到 MDL 读锁后，要等事务提交才释放，语句结束并不释放。如果一个长事务占着表 t 的读锁，另一个会话要加字段申请写锁，就会被阻塞；更要命的是，写锁排在最前面之后，后续所有针对 t 的增删改查申请读锁，也都会被这个等写锁的会话挡住，这张表彻底不可读写。查询一频繁、客户端一重试，连接很快被打满。

处理方式分两种。表上有长事务时，先查 information_schema.innodb_trx，暂停 DDL 或 kill 掉长事务。表是热点、请求不断、kill 完马上又有新请求进来时，用带超时的方式加字段，拿不到锁就先放弃，之后再重试：

两阶段锁与死锁

行锁是引擎层实现的，InnoDB 支持，MyISAM 不支持——后者同一张表任何时刻只能有一个更新在执行，并发度上不去。InnoDB 的行锁遵守两阶段锁协议：锁在需要的时候才加上，但不会用完立刻释放，一直持有到事务提交或回滚。

这条规则直接影响事务里语句的顺序。设想一个买票交易：扣顾客余额、给影院账户加钱、写一条交易日志。多个顾客同时在同一家影院买票，冲突点在影院账户那一行。按两阶段锁协议，三个操作的锁都要等到提交才释放，所以把更新影院余额的语句放到最后，这一行的锁持有时间最短，事务之间的等待也最少。原则是：事务里要锁多行时，把最可能造成冲突的锁往后放。

即使调整了顺序，死锁仍然可能发生。两个事务互相拿着对方要的行锁，就进入循环等待：

    B -->|"等待 id=1"| A

死锁有两种处理方式。等超时由 innodb_lock_wait_timeout 控制，默认 50 秒，在线服务等不起；把它调成 1 秒又会让普通的锁等待被误伤。另一种是主动死锁检测，innodb_deadlock_detect 默认开启，发现循环等待后挑一个事务回滚，让其他事务继续。

检测本身有代价。每个被堵住的线程都要判断它加入后会不会形成环，这是个 O(n) 的操作。一千个线程同时更新同一行，检测要跑到百万量级，虽然最后判定没有死锁，CPU 已经被吃掉——表现就是 CPU 接近满载，每秒却提交不了几个事务。缓解方向是减少访问同一资源的并发量：在服务端对相同行的更新排队，或者把一个热点账户拆成多条记录，总额取各条之和，每次随机选一条更新，冲突概率降到几分之一。拆行要考虑余额减少时的边界，某条记录扣到零之后代码得绕开它。

从 show engine innodb status 的 LAST DETECTED DEADLOCK 一段能读出现场：哪个事务在等哪把锁，哪个事务持有哪些锁。lock_mode X waiting 是 next-key lock，locks rec but not gap 是纯行锁，locks gap before rec 是纯间隙锁。两条语句锁同一组资源却顺序相反，就容易死锁；回滚时 InnoDB 挑持有资源少、成本低的那个事务。

next-key lock 规则

gap lock 锁的是记录之间的间隙，防止往间隙里插入新行。行锁和间隙锁合起来是 next-key lock，前开后闭。加锁规则可以压成两条原则、两条优化和一个特例：

类别 内容
原则一 加锁的基本单位是 next-key lock，前开后闭区间
原则二 查找过程中访问到的对象才会加锁
优化一 等值查询命中唯一索引时，next-key lock 退化为行锁
优化二 等值查询向右遍历，最后一个值不满足条件时，退化为间隙锁
特例 唯一索引上的范围查询，会访问到第一个不满足条件的记录为止

这套规则在可重复读隔离级别下讨论，间隙锁也只有这个级别才生效。用下面这张表走几个案例：

先等值查一个不存在的 id=7：本该加 next-key lock (5,10]，向右遍历时发现 id=10 不满足等值条件，按优化二退化成间隙锁 (5,10)。于是别人往这个间隙插 id=8 会被挡住，改 id=10 这行却可以。

唯一索引上的等值查询命中记录时用优化一。主键上 where id=10 for update 只加 id=10 的行锁；而 where id>=10 and id<11 for update 逻辑上等价，加锁却分成两段：定位 id=10 时按等值查询退化为行锁，向右扫描到 id=15 停下，加 next-key lock (10,15]。非唯一索引没有优化一，where c=10 for update 会在 c 索引上加 (5,10] 和 (10,15) 两段，因为 c 值可能重复，必须向右扫到 c=15 才能确认没有更多 c=10。

一个容易忽略的点：锁是加在索引上的，而且是一条一条加上去的。select c from t where c=5 lock in share mode 用覆盖索引，只访问 c 索引，主键索引上不加锁，此时别的会话仍能更新这一行；换成 select *，或者查询里带上 c 索引没有的字段，就得回主键树，主键上也加了锁。order by 的方向还会改变加锁顺序，c in (5,20,10) 正序是先锁 c=5 再锁 c=20，倒序反过来，两个会话并发执行时就可能互相卡住。

加锁案例推演

再看几个把规则用得更深的场景，重点是理解”间隙由谁定义”。间隙锁锁住的是两个记录之间的空隙，而空隙是由它右边那条记录决定的。删掉 id=10 之后，原本的 (5,10) 和 (10,15) 合并成 (5,15)——右边那条记录变成了 id=15。所以删除记录会让别的会话持有的加锁范围”变大”，虽然它什么都没做。更新索引字段也是同理：把 c=5 改成 c=1，在索引上相当于删除 (c=5,id=5) 再插入 (c=1,id=5)，间隙的边界随之移动，之后再想把这行改回 c=5，插入动作会撞进别人已经锁住的间隙，被堵住。

范围查询加 order by desc 时，优化器要先找”第一个小于目标值”的记录。找的过程其实是拿目标值做一次等值定位：where id>9 and id<12 order by id desc for update 先定位 id=12，没找到，落在 (10,15) 这个间隙，加间隙锁 (10,15)；再向左遍历，扫到 id=5 停下，加 next-key lock (0,5] 和 (5,10]。写法上是不等号，定位阶段用的却是等值查询的规则。

删除数据时加 limit 能缩小加锁范围。表里有两条 c=10 的记录，delete from t where c=10 会一直向右扫到 c=15，锁住 (5,10] 和 (10,15)；加上 limit 2 后，凑够两条就停，锁只到 (c=10,id=30)，后面的间隙不锁，别的会话往 c=12 插记录就能成功。limit 一方面控制删除条数，一方面减少锁住的范围，删除操作值得加上它。

    direction TB
    F1["扫描到 c=15 才停"] --> F2["锁 (5,10] 与 (10,15)"]
    F2 --> F3["c=12 的插入被挡住"]
    end

    direction TB
    L1["凑够 2 条就停"] --> L2["锁只到 (c=10,id=30)"]
    L2 --> L3["c=12 的插入可以通过"]
    end

读提交隔离级别下没有间隙锁，只剩行锁；语句执行完，不满足条件的行上的锁会立刻释放，不必等到事务提交。锁的范围更小、时间更短，这是不少业务默认用读提交的原因。可重复读下要用 next-key lock 解决幻读，就得接受更大的锁范围，在写语句时按规则算清楚代价。

锁机制速查

现象或需求 背后的机制 处理方向
备份时各表数据对不上 备份时点不一致 事务引擎用 single-transaction，否则 FTWRL
加字段把库堵住 MDL 写锁排在读锁后面，挡住后续请求 查 innodb_trx 处理长事务，DDL 带超时
热点行更新 CPU 高、事务少 死锁检测在大量并发下开销陡增 服务端排队，或把一行拆成多行
事务锁等待时间长 两阶段锁，锁持有到提交 把最可能冲突的语句往后放
只改一行却挡住插入 next-key lock 覆盖记录与间隙 按加锁规则算范围，等值命中唯一索引退化为行锁
删除记录后锁范围变大 间隙由右边的记录定义 注意相邻间隙合并
删除想缩小加锁范围 扫描到不满足条件才停 delete 带 limit

小结与参考

锁的粒度决定了冲突的范围：全局锁停掉整个实例，MDL 保护表结构，行锁和间隙锁作用在索引上。两阶段锁协议让锁的释放时机被绑在事务边界上，死锁检测则把循环依赖转成一次回滚。next-key lock 的规则看着细，核心只有两点——按访问到的索引对象加锁，按查找方式判断区间是否退化。把这两点套进具体语句，锁的范围就能推算出来。
