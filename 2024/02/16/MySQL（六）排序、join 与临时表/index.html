MySQL（六）排序、join 与临时表

发表于 2024-02-16 分类于 数据库
本文字数： 5.7k 阅读时长 ≈ 5 分钟

引言

一条语句执行得慢，原因常常藏在中间过程里：排序时内存放不下要落磁盘，join 选错了算法反复扫表，group by 悄悄建了一张临时表，删掉一半数据后文件却一点没小。这些动作在 explain 里只留下几个 Extra 字段，看懂它们要把执行过程拆开。这篇按几条线走：表里的空洞怎么来、怎么收回去；count 为什么越数越慢；order by 有几种排法；join 的两套算法各自适合什么场景；内部临时表什么时候出现，又该怎么绕开。

表空间的空洞与重建

一个 InnoDB 表的数据可以放在共享表空间，也可以独立成一个 .ibd 文件，由 innodb_file_per_table 控制。独立成文件更好管理：不需要这张表时，drop table 会直接删掉文件；放在共享表空间里，表删了，空间仍留在那里。

删行删不掉文件大小，得从删除流程说起。InnoDB 的索引是 B+ 树，删掉一条记录时，引擎把这条记录标记为删除，位置留给之后落在同一范围的新记录复用，磁盘文件保持不变。整个数据页的记录都删光，这个页才标记为可复用，而且能复用到树上的任何位置。相邻两页利用率都很低时，数据会合并到其中一页，另一页空出来。所以 delete from t 执行完，所有数据页都变成可复用状态，文件一点没缩。这些占着位置又没被用的空间，就是空洞。

空洞不只来自删除。按索引递增插入时索引紧凑，随机插入会触发页分裂：页满了再插一条，就申请新页搬一部分数据过去，原页末尾留下空洞。更新索引字段的值，等于删旧值再插新值，同样留洞。

flowchart LR
    D[delete 删除记录] --> M[标记为可复用]
    I[随机插入] --> P[页分裂]
    P --> M
    U[更新索引字段] --> M
    M --> H[空洞累积 文件不缩]
    H --> R[重建表]
    R --> S[文件收缩]

收缩的办法是重建表：新建一张结构相同的表，按主键递增顺序把数据从旧表读出来再插进去，新表没有那些空洞，主键索引更紧凑，最后换名替换。alter table t engine=InnoDB 做的就是这件事。早期流程是 server 层建临时表转存数据，整个过程不允许对原表更新。后来改成 InnoDB 内部建临时文件、扫描原表主键生成新 B+ 树，期间把增删改记进 row log，临时文件建好后再重放日志，最后替换数据文件。复制数据那段时间允许写入，所以对业务来说近似在线。

启动时仍要拿 MDL 写锁，真正拷贝之前会退化成读锁：退化是为了让增删改继续，保留读锁是为了挡住别的线程同时做 DDL。Online 和 inplace 是两个容易混的概念。inplace 说的是数据挪动在引擎内部完成，server 层没建临时表；Online 说的是拷贝期间允许读写。Online 的 DDL 一定是 inplace，反过来不成立——给字段加全文索引就是 inplace 的，却会阻塞增删改。重建表要扫描全表并构建临时文件，很大的表会吃掉大量 IO 和 CPU，临时文件本身也占空间；磁盘只剩一点余量时，1TB 的表未必收得动。

另外两个命令容易和重建混在一起：analyze table 只重新统计索引信息，不碰数据；optimize table 相当于重建再加一次统计。

count 为什么越来越慢

MyISAM 把表的总行数存在磁盘上，count(*) 直接返回这个数字。InnoDB 没有这个快捷方式，它要把数据一行行读出来累加。原因在 MVCC：同一时刻的多个查询，因为各自的一致性视图不同，应该看到的行数也不同。每一行都得判断对当前会话是否可见，可见的才计入结果。三个会话并行，一个先开事务，一个开事务后插入一行，一个用单条语句插入一行，同一时刻发出 count(*)，拿到的数字可以各不相同。

优化器在这里能省一点：count(*) 遍历哪棵索引树结果都一样，于是挑最小的那棵——普通索引树的叶子节点只存主键值，比主键树小得多。show table status 返回的 TABLE_ROWS 来自采样估算，误差可能到四成五成，不能拿来当精确行数用。

页面要显示操作总数加最近 100 条记录，脱离了数据库自己存计数是常见做法。把计数放进缓存系统，插入时加一、删除时减一，读写都快，代价有两个。一是缓存重启可能丢更新，重启后得回数据库跑一次 count(*) 把值补回来。二是并发下逻辑不一致：先写数据表再改缓存，查询可能看到新记录却拿到旧计数；把顺序倒过来，又可能拿到新计数却查不到新记录。两套存储之间没有分布式事务，拿不到一致的视图。

把计数放进数据库里单独一张计数表，插入记录和更新计数放在同一个事务中，就借到了事务的隔离性。更新事务没提交时，计数值的加一对查询会话还不可见，它看到的总数和最近 100 条记录自然对得上。

sequenceDiagram
    participant W as 更新会话
    participant T as 计数表 C
    participant R as 查询会话
    W->>T: begin
    W->>W: 插入操作记录
    W->>T: 计数值加 1
    R->>T: 读计数值 看不到未提交的加 1
    R->>W: 读最近 100 条 看不到未提交记录
    W->>T: commit

几种 count 写法的效率有差别。count(字段) 要判断字段是否为 NULL，允许为 NULL 时还得把值取出来再判断；count(主键 id) 由引擎逐行取出 id 交给 server 层累加，涉及解析数据行和拷贝字段；count(1) 不取字段，server 层对每行放一个数字 1 累加；count(*) 专门优化过，不取值，直接按行累加。效率从低到高大致是 count(字段)、count(主键 id)、count(1) 约等于 count(*)。

order by 的排序路径

市民表按城市查名字，再按名字排序返回前 1000 条。city 上有索引，查询先通过它定位到满足条件的记录，再按主键回表取出需要的字段，放进每个线程独有的 sort_buffer，按 name 排序后取前 1000 行。这就是全字段排序。

flowchart LR
    A[city 索引定位主键] --> B[回表取 city name age]
    B --> C[存入 sort_buffer]
    C --> D{sort_buffer 装得下}
    D -->|是| E[内存快速排序]
    D -->|否| F[分块落临时文件 归并排序]
    E --> G[取前 1000 行返回]
    F --> G

排序要不要落磁盘，看数据量和 sort_buffer_size 的关系。内存放不下时用外部排序，把待排数据分成若干份，每份单独排序写进临时文件，再把这些有序文件归并成一个。打开 optimizer_trace 执行一遍语句，可以从 number_of_tmp_files 看到用了几个临时文件，examined_rows 记录参与排序的行数。

一行要返回的字段很多时，sort_buffer 里能放下的行数就少，临时文件变多，排序性能下滑。单行长度超过 max_length_for_sort_data 时，MySQL 改用 rowid 排序：sort_buffer 里只放排序字段 name 和主键 id，排完序再按 id 回表取 city、name、age 返回。它省了排序时的内存，却多读了一次主键索引——limit 1000 就多读 1000 行。

内存够用时优先全字段排序，排完直接从内存返回结果；只有担心单行太大拖慢排序，才切到 rowid。如果能让数据从索引里取出来时就已经按 name 有序，这两条路都可以省掉。

建 (city, name) 联合索引后，树搜索定位到第一个 city=’杭州’ 的记录，往后遍历时 name 天然递增，不需要临时表也不需要排序，扫够 1000 条就能停。再进一步，建 (city, name, age)，三个返回字段都在索引上，连回表也省了，explain 的 Extra 里出现 Using index。索引有维护代价，为每条查询都堆联合索引不划算。

join 算法与驱动表

两张表做 join，被驱动表的关联字段有索引时走 Index Nested-Loop Join：从驱动表读一行，取关联字段的值去被驱动表做树搜索，找到匹配的拼成结果，直到驱动表扫完。t1 有 100 行、t2 有 1000 行，这条语句扫 200 行就结束了。拆成应用层循环，先 select * from t1 再逐行 select * from t2 where a=$R.a，扫描行数一样，却要多执行 100 次语句，还要自己拼结果。有索引时直接用 join 更合适。

驱动表选谁也有讲究。驱动表 N 行全扫，被驱动表每行要查两次树（关联索引加主键索引），整体代价近似 N + N×2×log₂M。N 的影响是线性的，M 只出现在对数里，所以让小表做驱动表。

被驱动表没有索引时，MySQL 不会傻到逐行全扫被驱动表，而用 Block Nested-Loop Join：把驱动表的数据读进 join_buffer，再扫被驱动表，每行跟缓冲区里的数据比对。两表各扫一次，比较次数是两表行数的乘积，但比较在内存里完成，比反复读盘快。缓冲区放不下时会分段：装一段，扫一遍被驱动表，清空，再装下一段——被驱动表因此被扫多次。调大 join_buffer_size 能减少段数，这也是 join 慢时常见的调整项。

判断是否踩到 BNL，看 explain 的 Extra 里有没有 Block Nested Loop。这种 join 在大表上代价很高：多次扫被驱动表占磁盘 IO，M×N 次比较占 CPU，反复扫冷表还会把 Buffer Pool 里的热数据挤出去，而且查询结束后命中率不会立刻恢复。

优化方向是让 join 用上被驱动表的索引。NLJ 上可以叠加 Batched Key Access：先从驱动表批量取出若干行放进 join_buffer，一次传给被驱动表，配合 Multi-Range Read 把拿到的主键 id 在 read_rnd_buffer 里排序，再按递增顺序回表，把随机读变成接近顺序读。启用前要把相关优化开关打开。

不适合在业务大表上建索引的场合，可以用临时表中转：把被驱动表经条件过滤后的少量数据导进一张带索引的临时表，再让驱动表和它 join。过滤后只剩几千行时，建索引的成本落到临时表上，原本上亿次的内存比较变成几千次带索引查找。

flowchart LR
    J[join 语句] --> A{被驱动表有索引}
    A -->|有| N[NLJ 小表驱动]
    A -->|无| B{能加索引}
    B -->|能| K[BKA 批量传值加 MRR]
    B -->|不能| T[临时表中转并建索引]
    T --> K

内部临时表与 group by

union 要取两个查询结果的并集并去掉重复行，执行时会建一张内存临时表，把第一个子查询的 1000 写进去，第二个子查询取到 1000 时因为主键冲突插不进去，取到 999 才能插入，最后从临时表逐行返回。这里的唯一性约束直接承担了去重。把 union 换成 union all，没有去重语义，两个子查询的结果直接发给客户端，临时表就消失了。

group by 也会建临时表。select id%10 as m, count(*) from t1 group by m 建一张以 m 为主键、带计数列的内存临时表，扫描索引取出 id，算出 id%10，存在就给计数加一，不存在就插一行，扫完再按 m 排序输出。数据不要排序要求时加上 order by null，能省掉最后一步。内存临时表有大小上限，超过 tmp_table_size 会转成磁盘临时表，大表上的 group by 因此可能占用大量磁盘空间。

让分组字段有序，就能去掉临时表。给 id%100 建一个生成列并加索引，索引上的取值天然有序，group by 变成从左到右顺序扫描、遇到新值就输出上一组的计数。这个句型不需要临时表，也不需要额外排序。

不方便建索引时，用 SQL_BIG_RESULT 提示优化器数据量很大，它会放弃临时表，把分组字段直接放进 sort_buffer 排序，得到一个有序数组，再从左到右统计每个值的出现次数。排序占内存，但省掉了一张不断扩容的二维表。

小结与参考

delete 只标记空洞，收缩要靠重建表；count 逐行累加是 MVCC 的必然结果，自己计数要放进同一个事务里；排序优先全字段，单行过大才换 rowid，最省的路是让索引本身有序；join 能用被驱动表索引就用，用不上就转 BKA 或临时表，驱动表始终选过滤后数据量小的那个；临时表在需要二维结构和唯一约束时出现，group by 能靠有序索引绕开它。
