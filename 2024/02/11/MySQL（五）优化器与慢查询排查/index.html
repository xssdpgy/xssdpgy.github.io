MySQL（五）优化器与慢查询排查

发表于 2024-02-11 分类于 数据库
本文字数： 5.8k 阅读时长 ≈ 5 分钟

引言

语句该走哪个索引，由优化器说了算。多数时候它判断得准，偶尔一次估算偏差，就能让毫秒级的查询变成全表扫描。这类问题查起来费劲：SQL 语义没写错，索引也建了，执行计划偏偏和预期相反。这篇先看代价怎么估、扫描行数怎么算出来，偏差出现后有哪些矫正手段。再往后是另一类更常见的慢——字段上加了函数、类型对不上、两表字符集不同，索引在树搜索这一步就废了。最后落到排查顺序和高峰期的应急边界，哪些手段能止血，哪些会埋雷。

优化器的代价估算

一条语句可能有多个候选索引，用哪个由优化器决定。它挑的是代价最小的执行方案，扫描行数是主要输入：扫的行数越少，访问磁盘的次数和 CPU 消耗都越低。除行数之外，要不要临时表、要不要排序，也计入代价。

建一张测试表：id 是主键，a、b 各建一个普通索引，插入十万行 (i,i,i)。查询 select * from t where a between 10000 and 20000，范围条件落在 a 上，explain 显示用了索引 a，扫描 10001 行，符合预期。

接着做一组动作：会话 A 开启事务不提交，会话 B 把表里数据删空，再调用存储过程重新插入十万行。同样的查询再跑，explain 里已经看不到索引 a 了。把慢日志阈值设成 0 之后对比：原句扫了十万行、40 毫秒；加上 force index(a) 只扫 10001 行、21 毫秒。优化器选错，耗时翻了一倍。这对应的是不断删历史数据又新增数据的场景。

flowchart LR
    S[SQL 语句解析] --> C[列出候选索引]
    C --> E[估算每个索引的扫描行数]
    E --> X[计入回表 排序 临时表代价]
    X --> P[选代价最低的方案]
    P --> Q[执行]

优化器在开始执行之前并不知道满足条件的有多少行，只能估算。扫描行数估错，后面整套代价比较就跟着错，这正是上面例子的症结。

索引统计与扫描行数

估算的依据是索引的基数（cardinality），也就是这个索引上不同值的个数。基数越大，区分度越好，用它筛掉的行越多。基数来自采样：InnoDB 抽若干个数据页，数出这些页上不同值的个数求平均，再乘索引总页数。把整张表逐行统计能得精确值，代价太高，采样是折中。持久化统计时默认抽 20 个页、数据变更超过十分之一就重算；只放内存的模式下抽 8 个页、变更超过十六分之一重算。两种模式都会偏，采样本身就带偏差。

在这个表里，三列的取值逐行相同，show index 查出来的三个基数却各不相同，而且都不准。更直接看 explain 的 rows 字段：原句估成 104620，强制走 a 的版本估成 37116，而它实际只扫 10001 行。估出来差了几倍，优化器据此算代价，结论自然歪。

还有一层代价要算进去：走普通索引 a，每取一个值都要回主键树查整行，这个回表成本会被计入。直接扫主键树虽然行数多，却省掉回表。优化器权衡之后认为全扫更快——算法本身没问题，错在行数估得离谱。

统计信息偏了就重算，analyze table t 之后 explain 恢复成选索引 a。实践里发现 rows 的估计值和实际扫描量差得远，先做这一步。

选错索引的矫正

优化器多数时候选得对，碰上误判有几条路可走，代价各不相同。

最直接的是 force index。优化器先解析出候选索引列表，再逐个估代价；force index 指定的索引只要在这个列表里，就直接采用，不再比较其他方案。看另一个例子：where (a between 1 and 1000) and (b between 50000 and 100000) order by b limit 1，两个范围没有交集，结果为空。走 a 只扫 1000 行，走 b 要扫 50001 行，可优化器偏偏选了 b。原因在于 b 本身有序，用它能免掉排序，尽管扫得多，代价看起来反而低。实测原句 2.23 秒，强制走 a 之后 0.05 秒。

flowchart TD
    A[语句选错索引] --> B[force index 强行指定]
    A --> C[改写语句引导]
    A --> D[新增或删除索引]
    B --> B1[见效快 但写死索引名]
    C --> C1[不改语义时可用 依赖数据特征]
    D --> D1[改动大 需评估索引必要性]

force index 的麻烦在于运维节奏。开发阶段谁也不会预先写它，多半是线上出问题了才改 SQL，再走测试和发布，赶不上止血。索引改了名，语句也得跟着改；迁到别的数据库，语法还可能不兼容。

第二条路是改写语句。把 order by b limit 1 写成 order by b,a limit 1，limit 1 时返回的仍是 b 最小的那行，逻辑一致。这一改，两个索引都免不了排序，扫描行数重新成为决定性因素，优化器就转去选只扫 1000 行的 a。还可以套一层 select * from (... order by b limit 100) alias limit 1，让优化器看到一个更大的候选集，意识到走 b 的代价高。这两种写法都借了这条语句的数据特征，换条 SQL 未必成立。

第三条路从索引本身下手：建一个更合适的索引给优化器挑，或者删掉那个被误用的。有些库里”选错”的那个索引本来就没有业务在用，沟通确认后删掉，优化器自然回到正确的选择。

函数与隐式转换导致的索引失效

比选错索引更常见的，是语句写法让索引用不上。三类写法看着都合理，落到执行上都会废掉树搜索。

B+ 树能快速定位，靠的是同一层兄弟节点的有序性。对索引字段做函数运算之后，传进去的值在树的第一层就没法比较了，优化器只能放弃树搜索。它未必会丢掉这个索引——索引 t_modified 比主键树小，遍历它比遍历整张表划算，于是退化成全索引扫描。

flowchart LR
    T[字段直接比较] --> R1[按有序性逐层定位]
    F[字段套函数] --> R2[第一层无法比较]
    R2 --> R3[放弃树搜索]
    R3 --> R4[全索引扫描或全表扫描]

交易表 tradelog 存了交易流水号、交易员和交易时间，t_modified 上有索引。统计所有年份 7 月的交易数，很自然会写 where month(t_modified)=7，结果跑得很慢。改成按字段本身的范围查询，把涉及的年份列出来，快速定位就恢复了：where (t_modified >= '2016-7-1' and t_modified < '2016-8-1') or ...。优化器在这种地方不主动改写：where id+1=10000 加 1 并不破坏有序性，它也不会自动变成 where id=10000-1，得手动改。

隐式类型转换是第二类。tradeid 定义成 varchar，拿整型 110717 去比，MySQL 会把字符串转成数字——select "10" > 9 返回 1 就能验证这个方向。转换落在索引字段上，效果等同于套了一层 CAST，树搜索失效，整表扫描。反方向则没事：id 是 int，拿字符串 ‘83126’ 去比，字符串转成数字，索引照用。

flowchart LR
    A[varchar 字段 比 整型参数] --> B[字符串转数字]
    B --> C[函数落在索引字段上]
    C --> D[索引失效]
    E[int 字段 比 字符串参数] --> F[字符串转数字]
    F --> G[函数落在参数上]
    G --> H[索引可用]

第三类是隐式字符编码转换，出现在两表 join 上。交易明细表 trade_detail 的 tradeid 用 utf8，tradelog 的同名字段用 utf8mb4。utf8mb4 是 utf8 的超集，比较时 MySQL 把 utf8 那侧转成 utf8mb4，避免截断丢数据。关键看转换落在哪一侧：

以 tradelog 驱动 trade_detail 时，被驱动表的 tradeid 字段被 CONVERT，索引失效，退化为全表扫描。把驱动关系反过来，以 trade_detail 驱动 tradelog，CONVERT 加在传进去的参数上，被驱动表的索引有效。

flowchart TD
    J[两表按 tradeid 关联 编码不同] --> D1[tradelog 驱动 trade_detail]
    J --> D2[trade_detail 驱动 tradelog]
    D1 --> X1[转换落在被驱动表字段]
    X1 --> Y1[索引失效 全表扫描]
    D2 --> X2[转换落在输入参数]
    X2 --> Y2[被驱动表索引可用]

修法有两种。能改表结构就把 trade_detail 的 tradeid 改成 utf8mb4，从根上消掉转换。不能做大 DDL 时改写语句，主动把驱动表的字段转成 utf8，让被驱动表那侧保持不变：

慢查询排查与应急边界

慢查询的成因大体三类：索引没设计好、SQL 没写好、优化器选错。前两类完全可以提前拦住——上线前打开慢日志，把 long_query_time 设成 0，测试表灌入接近线量的数据跑一遍回归，盯住每类语句的 Rows_examined 是否和预期一致。这段时间花得值，能省掉后面的故障复盘。

有些语句只查一行却很慢，卡点在等待上：等元数据锁，DDL 在前面排队，后续的读写全被挡住；等 flush，一条长查询没结束，flush tables 堵住，再后面的查询跟着堵；等行锁，另一个事务占着这一行的锁不放。show processlist 的 State 字段能把这几种状态区分开，处理思路在锁机制那篇里说过。

高峰期的临时手段都有代价，按风险从低到高看：

短连接突增时先别急着调高连接上限。连接数要算上权限验证的成本，放更多人进来只会让 CPU 耗在验证上，SQL 反而拿不到资源。更稳的做法是清掉空闲连接，优先处理事务外的 sleep 线程，从 information_schema.innodb_trx 里能查出哪些线程还在事务中——踢掉事务内的会导致回滚。客户端不会立刻感知连接被断，要确认应用有重连逻辑，并提前通知业务方。

索引漏建导致语句打满库，支持在线加索引的版本可以直接 alter table；更稳妥的节奏是在备库先加、做主备切换、再在原主库补上。查询重写功能可以把写坏的语句改成正确形态，也能给语句加 force index，前提是改写规则经过验证。把压力最大的语句重写成 select 1 直接返回属于止血，其他功能如果共用这条语句模板就会被误伤，优先级放到最后。QPS 突增时从源头断流更干净——撤掉白名单或停用专用账号，前提是白名单和账号本来就是按功能分开管理的。

flowchart LR
    A[高峰期性能应急] --> B[优先 清理空闲连接 在线加索引]
    A --> C[谨慎 查询重写 需验证规则]
    A --> D[兜底 重写成 select 1]
    B --> E[代价可控]
    C --> F[可能误伤共用语句]
    D --> G[业务逻辑可能整体失败]

还有一类手段绕开规则换性能：跳过权限验证重启数据库。外网可达的实例绝对不能这么做，这种方案留下的口子比它救回的时间难收拾得多。

小结与参考

代价估算依赖扫描行数，行数来自采样统计，采样会偏——这是选错索引的源头。统计偏了用 analyze table 重算；优化器坚持误判时，force index 见效快但要改 SQL，改写语句和增删索引更温和却依赖具体场景。字段上的函数、隐式类型转换、隐式编码转换会让树搜索失效，写法上把它们挪到参数一侧，或者用范围条件替代函数。慢查询排查先把上限收紧在上线前的回归测试里，应急手段按代价排序，止血动作做完还得回头补根因。
