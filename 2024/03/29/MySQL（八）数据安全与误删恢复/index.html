MySQL（八）数据安全与误删恢复

发表于 2024-03-29 分类于 数据库
本文字数： 4.7k 阅读时长 ≈ 4 分钟

引言

数据安全这件事分两头。一头是写进去之后别丢：WAL 把随机写换成顺序写，代价是内存里攒下脏页，刷的时候可能让一条本来很快的语句突然变慢。另一头是删错了能找回来：delete 删的行、drop 掉的表、rm 掉的整个实例，恢复路径各不相同，能恢复到什么程度取决于备份和日志留了多久。再往前一步是运行时的边界——kill 不掉的语句卡在哪、全表扫描会不会把内存打爆。这篇把这几件事放一起，按「异常从哪来、能救回什么、代价多大」串一遍。

刷脏页与抖动

更新语句走 WAL：改内存、写 redo log 就返回，数据页晚点再写回磁盘。内存页和磁盘页内容不一致时叫脏页，写回之后变成干净页。一条平时很快的语句偶尔慢一下，多半就是撞上了刷脏页。

刷脏页有四个触发时机。redo log 写满了，系统要停掉所有更新、把 checkpoint 往前推，这期间更新数跌到 0，是最要避开的情形；内存不够用了，淘汰数据页时如果淘汰的是脏页，得先把它写回磁盘；系统空闲时后台见缝插针地刷；正常关闭时把所有脏页写回，下次启动才能直接读磁盘。前两种影响性能，后两种没人会在意。

flowchart TD
    U[更新语句 改内存写 redo log] --> D[产生脏页]
    D --> A{触发刷脏}
    A -->|redo log 写满| R[停更新 推进 checkpoint]
    A -->|内存不足淘汰| E[先写盘再复用]
    A -->|系统空闲| I[后台刷]
    A -->|正常关闭| C[全量刷回]
    R --> X[响应变慢]
    E --> X

刷多快由两个因素决定：脏页比例和 redo log 的写入进度。脏页比例 M 除以 innodb_max_dirty_pages_pct 算出一个 0 到 100 的值 F1，比例到了上限就是 100；当前写入序号与 checkpoint 序号的差 N 越大，F2 越大。取两者较大的 R，按 innodb_io_capacity 定义的能力乘以 R% 去刷。所以 innodb_io_capacity 必须设成磁盘真实的 IOPS——SSD 上还按默认值 300，刷脏速度会慢过脏页生成速度，脏页越积越多，TPS 就是上不去。可以用 fio 测出实际能力再设。

脏页比例用 Innodb_buffer_pool_pages_dirty 除以 Innodb_buffer_pool_pages_total 查，平时别让它长期贴近上限。还有个放大器：刷一个脏页时，innodb_flush_neighbors 为 1 会把旁边的脏页一起带走，还能继续蔓延。机械盘年代这能省下大量随机 IO；SSD 上 IOPS 已足够高，连坐反而拖长响应时间，该把它设为 0。

误删行与闪回

误删分四种：delete 删行、drop/truncate 删表、drop database 删库、rm 删实例。传统高可用挡不住误删——主库上一条 drop table 会顺着 binlog 传到所有从库，整个集群一起执行。所以恢复能力只能靠备份加日志，复制帮不上忙。

delete 删掉的行可以用 Flashback 闪回，前提是 binlog 用 row 格式且 binlog_row_image 为 FULL。原理是改写 binlog 里的 event：Write_rows 换成 Delete_rows，Delete_rows 换成 Write_rows，Update_rows 把改前改后的值对调。多个事务要倒序执行，把 (A)delete、(B)insert、(C)update 恢复成 reverse C、reverse B、reverse A。别在主库上直接跑，恢复出备份或找一台从库做临时库，确认过结果再导回主库——发现晚的时候，业务可能已经在误操作的基础上又改了别的数据，直接补几行会造成二次破坏。

误删库表与备份恢复

drop 和 truncate 没有这条路径。即使配了 row 格式，这三类命令在 binlog 里仍记成 statement，只有一个语句原文，恢复不出数据。只能走全量备份加增量日志：取最近一次全量备份恢复出临时库，把备份时点之后的 binlog 除误操作那条外全部应用上去。没有 GTID 时用 --stop-position 和 --start-position 把 12 点那条语句前后两段分开应用；有 GTID 就把误操作的 GTID 设进 gtid_next，提交一个空事务，后面顺序应用时会自动跳过。

mysqlbinlog 方案有两个短板：不能只解析一张表的日志，应用日志也只能单线程。加速办法是让临时库挂到线上备库下做从库，同步前用 change replication filter replicate_do_table=(tbl_name) 限定只同步那张表，就能用上并行复制。备库上缺的 binlog 可以从备份系统取回放回日志目录，改 master.index 后重启备库让它重新识别。恢复时间取决于备份周期和日志量，一周一备的实例在第六天误删，可能要按天恢复。核心业务可以搭延迟复制备库，change master to master_delay=N 让它落后主库 N 秒；一小时内发现误删，这条命令还没在延迟备库上执行，stop slave 后跳过它就能拿到数据，最多再追一小时。

预防比恢复值钱。sql_safe_updates 设为 on，delete 和 update 忘了写 where、或者 where 里没有索引字段就会报错；代码上线前过 SQL 审计。账号分离，业务只给 DML 权限，DDL 走管理系统；删表先把表名改成带 _to_be_deleted 后缀，观察一段时间无影响再通过管理系统删，系统只认这个后缀。rm 删单个节点有 HA 兜底，选新主库后把这个节点恢复回来再接入；批量下线把整个集群删光，就只能靠跨机房甚至跨城市的备份。

kill 的边界

kill query 终止线程正在执行的语句，kill connection 断开连接。两者都谈不上”立刻停”：处理 kill 的线程只是把目标状态改成 KILL_QUERY 或 KILL_CONNECTION，再发一个信号，目标线程执行到埋点才检查状态、进入终止逻辑。处于锁等待时信号能把它唤醒，所以 kill 很快见效；但如果线程在循环里每 10 毫秒判断一次能不能进 InnoDB，进不去就 nanosleep，这个循环里根本没检查线程状态，kill query 就不起作用——innodb_thread_concurrency 不够时看到的正是这种场景。此时 kill connection 关掉网络连接，客户端会收到断连提示，可是 show processlist 里 Command 列仍显示 Killed，因为服务端那条语句还在等。

flowchart LR
    K[执行 kill] --> S[设置线程状态并发信号]
    S --> W{线程是否走到埋点}
    W -->|是| P[进入终止逻辑]
    W -->|否 如等待进入 InnoDB| B[继续等待 Killed 状态]
    P --> T{终止逻辑耗时}
    T -->|大事务回滚 大查询删临时文件| L[仍需等待]
    T -->|普通语句| F[结束]

另一类是终止逻辑本身耗时长：超大事务回滚要回收所有新数据版本；大查询生成的临时文件在文件系统压力大时删得慢；DDL 最后一阶段被 kill 也要清理临时文件。这些都显示为 Killed，只能等，或者通过改善环境加速——临时调大 innodb_thread_concurrency、停掉别的线程让出位置、降低系统 IO 压力。客户端按 Ctrl+C 并不会直接杀服务端线程，MySQL 是停等协议，客户端另起一个连接发 kill query 而已。被 killed 的事务一直回滚时，重启也省不掉回滚动作，让它自己跑完更快；如果它占着锁或 IO 影响别人，先做主备切换把流量挪走，再等它结束。

全表扫描与内存

100G 内存扫 200G 表，不会把内存用光。逻辑备份本来就是整库扫描，真会吃光内存早就挂了。关键在于服务端不保存完整结果集：取一行写进 net_buffer，写满就发；发送函数返回 EAGAIN 或 WSAEWOULDBLOCK 说明本地网络栈写满，停下来等可写再继续。服务端为这个查询占用的内存最多是 net_buffer_length 那么大，socket send buffer 也不可能有 200G。

代价落在时间上。客户端接收慢，结果发不出去，事务执行时间就拉长；show processlist 里 State 一直是 Sending to client，说明网络栈写满了。结果集不大时用 mysql_store_result 一次拿到本地内存；结果真的很大改用 mysql_use_result 边读边处理。要快速减少这类线程，可以调大 net_buffer_length。另一个常被误会的状态是 Sending data——它只表示语句正在执行，可能是执行器里的任意阶段，等锁时也会显示这个，跟发送数据没关系。

引擎侧也不会让内存暴涨。Buffer Pool 既加速更新也加速查询，命中率在 show engine innodb status 的 Buffer pool hit rate 里看，稳定服务该在 99% 以上。全表扫描真正威胁的是命中率：朴素 LRU 下扫一张 200G 的历史表，会把业务热数据全淘汰出去，命中率骤降、磁盘压力上来。InnoDB 的改进是按 5:3 把链表分成 young 和 old 两段，新读入的页放进 old 区，只有在里面待够 innodb_old_blocks_time 之后再被访问，才移到头部。顺序扫描时同一页的多次访问间隔不到一秒，页始终留在 old 区、很快被淘汰，young 区不受影响。全表扫描仍耗 IO，业务高峰别在主库上跑。

flowchart LR
    S[扫描冷表读入数据页] --> O[放入 LRU 的 old 区]
    O --> C{一秒后是否被再次访问}
    C -->|否 顺序扫描的常见情况| E[留在 old 区并被淘汰]
    C -->|是| Y[移到 young 区]
    Y --> H[保护业务热数据命中率]

小结与参考

WAL 换来写性能，也带来脏页；刷脏速度由磁盘能力、脏页比例和 redo log 进度共同决定，SSD 上关掉邻居刷新。误删行靠 Flashback 改写 binlog，误删库表靠全量备份加日志，延迟备库能把恢复窗口压到分钟级，预防手段比恢复流程更值得投入。kill 只是设置状态，线程走到埋点才会停；全表扫描不会撑爆内存，却可能挤掉 Buffer Pool 里的热数据，改进 LRU 把冷扫描挡在 young 区之外。
