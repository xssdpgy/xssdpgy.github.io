MySQL（七）主备一致与高可用

发表于 2024-03-16 分类于 数据库
本文字数： 6.8k 阅读时长 ≈ 6 分钟

引言

主库写一份数据，备库怎么跟上；主库挂了谁来接；接完以后，读请求打到从库会不会读到旧值。三件事串起来就是高可用。MySQL 的绝大部分高可用方案都长在一主一备这棵树上，树根是 binlog。这篇从 binlog 的内容和同步链路讲起，看主备延迟从哪来、切换时拿可靠性还是可用性换；再看备库怎么并行追日志、GTID 怎么替代位点；最后落到读写分离的过期读和实例健康检测——这两处最容易在表面正常的系统里埋问题。

binlog 与主备同步

最基本的架构是一主一备：平时读写都在节点 A，B 作为备库把 A 的更新同步过来；切换时客户端改访问 B，A 反过来做备库。备库建议设成 readonly，挡住运营查询的误操作和切换逻辑的双写，也方便用这个状态判断节点角色。同步线程有超级权限，只读拦不住它。

一条更新从 A 到 B 要走完整条链路：备库用 change master 配好主库的地址和起始位点，start slave 启动 io_thread 和 sql_thread；io_thread 连上主库，主库按备库给的位置读 binlog 发过来；备库把收到的内容写成 relay log；sql_thread 读 relay log，解析出命令并执行。B 执行完同一份 binlog，状态就和 A 一致。

flowchart LR
    C[客户端写入 A] --> A[主库 A 执行事务写 binlog]
    A --> IO[A 的 binlog 发送线程]
    IO --> IT[备库 io_thread]
    IT --> R[relay log]
    R --> ST[sql_thread 解析并执行]
    ST --> B[备库 B 数据更新]

binlog 的格式决定备库拿到的是什么。statement 格式记录 SQL 原文，一条带 limit 的 delete 在主库走索引 a、在备库走索引 t_modified，删掉的是不同行，MySQL 会对这种语句报 unsafe 警告。row 格式不记原文，改记 Table_map 和 Delete_rows 两类 event，把被删行的主键和字段值写进去，备库拿到后直接删那一行。一条语句删十万行，statement 只记几十字节，row 要把十万行都写进日志，空间和 IO 都上去了。mixed 让优化器判断：可能引起不一致的用 row，否则用 statement。

row 格式还有个附带好处是数据恢复。delete 的 binlog 里存着整行旧值，改成 insert 就能插回去；insert 记着所有字段，反过来就是 delete；update 记着改前改后两行，对调一下再执行就能撤销。依赖上下文的语句则不能只拷 SQL 出来执行——比如 mixed 下带 now() 的 insert，binlog 里会在前面补一条 SET TIMESTAMP，把函数返回值钉住。恢复数据时要用工具把整段解析结果发给 MySQL，摘出 statement 单独跑会丢掉这些上下文。

双 M 结构互为主备，切换时不用改主备关系，代价是日志在两个节点间来回传。解决办法靠 server_id：两个实例的 server_id 必须不同；备库重放日志生成的 binlog 沿用原日志的 server_id；每个节点收到日志先看这个 id，跟自己相同就丢弃。三节点迁移时可能绕过这个机制，可用 IGNORE_SERVER_IDS 临时过滤某个 id，稳定后再去掉。

主备延迟与切换取舍

一个事务在主库写完 binlog 记 T1，备库收到记 T2，执行完成记 T3，延迟就是 T3-T1。show slave status 返回的 seconds_behind_master 取当前事务 binlog 里的时间戳和系统时间的差。备库连主库时会取一次主库的 Unix 时间校准，两边系统时间不一致也让这个值失准不了——但校准只在建连时发生，连上之后改系统时间就管不着了。网络正常时 T2-T1 很短，延迟主要出在备库消费 relay log 跟不上主库生产 binlog。

慢在消费端通常有三类原因。备库机器规格低或多台备库挤在一台机器上，更新的 IOPS 压力跟主库没区别，争抢就慢；备库被拿去跑运营分析和统计查询，CPU 被吃满；主库上有大事务，binlog 要等事务提交才写，一个十分钟的事务能让备库落后十分钟——一次性删大量历史数据、大表 DDL 都属于这类。前两类靠对称部署、一主多从、统计查询输出到外部系统疏解，第三类要把大事务拆小、DDL 走在线变更工具。

延迟存在，切换就有两种策略。可靠性优先的流程是：先看备库的 seconds_behind_master 小于阈值；把主库设为只读；等备库的延迟归零；把备库改成可读写；切流量。第 2 步之后到第 4 步之前两边都只读，系统有不可写窗口，等延迟归零那一步最耗时——第 1 步的预判省不掉。可用性优先把第 4、5 步提到最前面，几乎消除了不可用时间，代价是可能数据不一致：主备延迟 5 秒时切到备库，新写入的 c=5 先在备库插成 (4,5)，随后 relay log 里的 c=4 插成 (5,4)，主库那边又收到 c=5 插成 (5,5)，两边各多出一行。row 格式下这类冲突会报 duplicate key 并停下，问题容易暴露；statement 或 mixed 下可能悄悄错下去。

主库掉电属于被动切换，此时没有”等延迟变小”的机会。按可靠性优先就得等备库把 relay log 应用完，这期间整个服务不可用；直接切过去又会让客户端查不到已提交的事务，看起来像丢数据。保证可靠性的前提下，可用性取决于延迟——延迟越小，故障恢复越快。日志库这类可以事后用 binlog 补齐、短暂不一致不影响业务的场景，才值得选可用性优先，前提是写入逻辑能降级，别让日志写不进去挡住主流程。

flowchart TD
    A[发起主备切换] --> B{选择策略}
    B -->|可靠性优先| C[主库设只读]
    C --> D[等备库延迟归零]
    D --> E[备库可读写 切流量]
    E --> F[有不可用窗口 数据可靠]
    B -->|可用性优先| G[直接切流量并开放备库写入]
    G --> H[几乎无中断 可能数据不一致]

并行复制的演进

主库有行锁，除了热点行都能并发写；备库只靠一个 sql_thread 顺序执行 relay log，追不上是迟早的事。多线程复制把 sql_thread 改成 coordinator，只负责读日志和分发事务，真正更新数据的是一组 worker，数量由 slave_parallel_workers 控制。分发有两条硬约束：更新同一行的两个事务必须进同一个 worker，否则顺序颠倒会导致主备不一致；同一个事务的多条语句不能拆开，否则别的查询会看到”更新了一半”的事务。

按表分发用每个 worker 一张 hash 表，key 是库名加表名，value 是队列里修改这张表的事务数。新事务跟所有 worker 的队列比对：都不冲突就给最闲的 worker；跟多个冲突就等；只跟一个冲突就投给它。多表负载均匀时效果好，所有更新都砸在同一张热点表上就退化成单线程。按行分发把 key 换成库名、表名和唯一键值，冲突判断细到行，并行度更高，前提是 binlog 用 row 格式、表有主键且没有外键。唯一键也得算进去：两个事务改的主键不同，新值可能撞上对方的唯一索引，分到不同 worker 就会报错。大事务删一百万行要记一百万个 hash 项，超过阈值就暂时退回单线程。

按库分发最省事，hash 的 key 只是库名，也不挑 binlog 格式，但所有表都在一个库里时没有并行效果。基于组提交的思路换了角度：同一组提交的事务不会改同一行，主库能并行的备库也能并行。给同组事务打上相同的 commit_id 写进 binlog，备库把相同 commit_id 的事务分给多个 worker，这组做完再取下一组。问题是组里混进一个大事务，其他 worker 就闲着。

官方后来用 prepare 阶段替代 commit 阶段作并行边界——走到 prepare 就说明通过了锁冲突检验，prepare 与 commit 状态之间的事务也能一起并行。拉长 binlog 从 write 到 fsync 的间隔，能攒出更多同时处于 prepare 的事务，主库稍慢一点，备库并行度反而上去。再往后的策略基于 WRITESET：给改动的每一行按库名、表名、索引名和值算 hash 组成集合，两个集合没有交集就能并行。hash 集合在主库生成后直接写进 binlog，备库不用解析行数据。

flowchart LR
    R[coordinator 读 relay log] --> D{分发依据}
    D -->|按表| T[同表事务同一 worker]
    D -->|按行| K[同键值事务同一 worker 需 row 格式]
    D -->|按库| S[同库事务同一 worker]
    D -->|组提交| G[同 commit_id 或 prepare 组并行]
    D -->|WRITESET| W[无交集 writeset 可并行]
    T --> P[worker 线程组]
    K --> P
    S --> P
    G --> P
    W --> P

GTID 与过期读

一主多从切换时，从库得把自己指向新主库。基于位点的做法要在新主库上找一个”稍微往前”的位点，再用 mysqlbinlog 按故障时刻定位，这个值很难精确——已经同步过的事务会被重放，同步线程报 Duplicate entry 停住。处理办法是碰到错误就 set global sql_slave_skip_counter=1 跳过，或者设置 slave_skip_errors='1032,1062' 忽略两类已知无损的错误，稳定后置空，免得真出不一致也被跳过。

GTID 把这件事接了过去。每个提交的事务有一个 server_uuid:gno，gno 从 1 递增，实例维护一个已执行 GTID 的集合。切换时用 master_auto_position=1，从库把自己的集合发给新主库，新主库算出差集，确认有从库需要的全部 binlog，就从第一个不在从库集合里的事务开始发；日志已被清掉就直接报错，不像位点协议那样让备库随便指定位置。如果从库多出一个主库没有的 GTID，把它设进 gtid_next、提交一个空事务、再恢复 automatic，就精确表达了跳过。

读写分离绕不开过期读：刚提交完更新，紧接着的查询路由到从库，从库还没应用完日志，读到的是旧状态。用得最多的办法是按请求分类——发布商品后立刻回看走主库，逛商铺页面晚几秒无所谓。如果所有查询都不能读旧值，读写分离就失去意义。sleep 一下或前端先回显来”等一等”并不精确：本来 0.5 秒能读到正确结果也要等 1 秒，延迟真超过 1 秒还是过期。

更准一点的思路是等条件满足再查。判断 seconds_behind_master=0，或比对 Master_Log_File 与 Relay_Master_Log_File、Read_Master_Log_Pos 与 Exec_Master_Log_Pos 两组位点，或比对 Retrieved_Gtid_Set 与 Executed_Gtid_Set——后两种比秒级判断精确。它们判断的都是”收到的日志都执行完了”，但还有一种状态：事务在主库已提交并回复客户端，日志还没发到从库。这时从库认为无延迟，依然查不到那个事务。semi-sync 要求主库收到从库的 ack 才回复客户端，配合位点判断能堵上这个口子；一主多从下它只保证收到 ack 的那一个从库是最新的，其他从库照旧可能过期。

再进一步是只等自己关心的那个事务。更新提交后取主库当前的 File 和 Position，在选中的从库上执行 select master_pos_wait(File, Position, 1)，返回非负整数说明这个位置之前的日志都应用完了，可以查从库；超时退回主库。GTID 模式下用 wait_for_executed_gtid_set(gtid, 1)，事务的 GTID 能从返回包直接拿，省掉一次 show master status。两种方案都要处理所有从库都延迟的情况：查询全涌到主库，限流得提前想好。大表 DDL 是反例——主库上十分钟的大事务，备库要过十分钟才执行到后续事务的 GTID，等待查询全线超时，这种预期内的操作该先把读流量切回主库再变更。

健康检测

select 1 只能说明进程还在。把 innodb_thread_concurrency 设成一个小值，几个 select sleep(100) from t 占满并发额度之后，select 1 照样秒回，查业务表却全部堵住。并发连接和并发查询是两回事：processlist 里几千个连接只是多占内存，真正吃 CPU 的是正在执行的语句，这个上限卡的是后者。等行锁的线程不计入并发额度，这点很关键——否则一个持锁事务加上 128 个等锁线程就能把额度占满，持锁事务反而提交不了，整个系统卡死。

要覆盖并发打满，得访问 InnoDB。在系统库建一张 health_check 表，定期 select * from mysql.health_check。它能查出并发过高，却查不出磁盘写满：binlog 所在磁盘 100% 时更新和提交都堵住，读仍正常。把检测改成更新时间戳就能覆盖。主备都检测时，双 M 结构会把备库的检测更新传回主库，两边用同一行会冲突，所以按 server_id 存多行，用 on duplicate key update 各更新各的。

外部检测有个绕不过去的短板：轮询有间隔，系统出问题后要等下一次探测才可能发现；探测语句本身消耗很小，日志盘 IO 已经 100%、业务 SQL 慢得不能接受时，它仍可能抢到一点 IO 资源在超时前返回，检测系统据此判断”正常”。把判断搬进数据库内部更可靠。performance_schema 的 file_summary_by_event_name 记录了每次 IO 请求的时间，按 event_name 分别统计 redo log 和 binlog 的 COUNT_STAR、SUM、MIN、AVG、MAX。打开需要的统计项，设一个单次 IO 超过 200 毫秒的阈值去查 MAX_TIMER_WAIT，发现异常后 truncate 这张表，让下一轮统计从头累积。全开统计会有大约一成的性能损耗，只开需要的项就便宜得多。

小结与参考

binlog 的格式决定备库重放得失真，row 记行、statement 记语句，同步链路靠 io_thread 落 relay log、sql_thread 执行。延迟出在备库消费慢和大事务，切换在可靠性与可用性之间取舍，多数场景该选可靠性优先。并行复制按表、按行、按组、按 writeset 逐级细化冲突判断；GTID 让一主多从切换不再手工找位点。读写分离的过期读按请求分类，必要时等位点或等 GTID，超时退回主库并限流；健康检测从 select 1 走到查表、更新系统表，再补上内部 IO 统计，逐层逼近真实状态。
