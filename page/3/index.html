DDD（三）通用语言与限界上下文

发表于 2023-03-09 分类于 架构设计
本文字数： 5.3k 阅读时长 ≈ 5 分钟

引言

一张金额表被两个团队按各自的口径共写，对账差额往往从这里开始。本篇讲通用语言与限界上下文：怎样把术语冲突收敛成模型边界，以及边界确定后团队、代码库与数据库该怎么对应。

财务对账连续三天出现差额，量不大，但每天都有。追到最后，问题不在渠道，在一张表：order.amount 一个字段被两个团队写。交易侧把它当应付金额，支付侧把它当渠道实收金额（已扣手续费），两边各按各的口径累加，谁也没觉得有问题——因为在各自的代码里，它都叫”订单金额”。

更早的信号其实已经出现过，只是没人当回事。这个 Order 类被四个团队轮流加字段：

字段越加越宽，是因为没人给”订单”划定它在哪里生效。四个部门开会统一过命名，结论是”都叫订单”，然后各回各家继续往同一个类里塞字段。共享一个模型，把口头的歧义变成了数据库里一行谁都解释不清的数据。

结论先行：跨部门术语歧义不能靠开会统一，只能靠限定每个词生效的范围来收敛。统一语言的产物不是一份词汇表，而是一条条模型边界；边界之内，一个词只有一个含义，边界之外，同名可以不同义。

DDD（二）领域与子域——核心域、通用域与支撑域

发表于 2023-03-06 分类于 架构设计
本文字数： 5.4k 阅读时长 ≈ 5 分钟

引言

面对没做过的业务，第一版架构最容易把名词平铺成模块，再把资源平均分掉。本篇讲初始子域划分：先判核心域、支撑域与通用域，按档位决定人力和自研深度，也给出这套分级不成立的条件。

一个团队接手从未做过的电商履约业务，评审会上给出的第一版架构，是把能想到的名词平铺成十四个一级模块：用户、商品、订单、库存、支付、促销、发票、物流、通知、字典、权限、报表、评价、售后。每个模块分一个小组、一个库、一套 CRUD，两周搭完骨架，排期表整齐漂亮。

大促当天出了问题：同一 SKU 被超卖。追查下来，库存扣减散在两处——下单时在订单服务里执行一次 update stock set available = available - n，发货前又在履约服务里扣一次，中间没有锁定态，也没有占用记录。规则没有归属，更没有人把它当成需要认真设计的东西。

坏味道通常长这样，库存被当成与字典、通知同构的通用能力：

没有并发控制，没有”谁占用了这批货”的记录。这不是写得差，而是被放错了投入档位：最强的三个人派去做权限和消息中心，库存交给一个新人按 CRUD 实现。十四个模块被平均对待，等于没有判断。

面对陌生业务，资源永远不够。初始划分要解决的不是”分得全不全”，而是先分出轻重：哪一块值得最强的人自研，哪一块能买，哪一块够用就行。分错档位，比少画一个框代价大得多。

本篇从一次按数据表拆服务的改造说起，说明 DDD 在拆分决策里的位置，以及哪些情况下不值得用它。

某电商系统原本是一个单体应用，一张库里躺着 order、order_item、stock、coupon、payment、shipment 等十余张表。团队决定「上微服务」，按数据表拆成八个服务，两周内完成了部署拆分。

上线三个月后出现三个典型症状：

  • 一次下单要串行调用库存、优惠、订单、支付、履约五个服务，链路长、故障点分散；
  • 「优惠券能否与满减叠加」这条业务规则，一半写在 order-service 的应用服务里，一半写在 promotion-service 的 Controller 里，改一次规则需要两个团队联调；
  • 库存扣减逻辑同时存在于 stock-service 与 order-service，超卖时无法判定哪一处是权威。

于是代码往往长成这样——服务拆开了，业务逻辑却仍散落在调用方：

这里真正出问题的不是注册中心、网关或 RPC 框架，而是没人能说清业务的边界在哪里。按表拆、按技术层拆、按团队人数拆，都是用技术或组织维度去替代业务维度。服务数量成了目标，边界反而成了事后补的解释。

微服务架构本身并不提供边界的判定方法。这正是 DDD 被引入微服务设计的原因。
