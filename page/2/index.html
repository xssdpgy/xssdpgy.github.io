高并发（一）系统设计目标与容量度量

先看一个常见的秒杀需求：单 SKU，库存 5000 件，预约三十万人，整点开抢。运营给的口径往往就这一句，剩下的要技术侧自己补——峰值多少 QPS、每一层能扛多少、瓶颈在哪一层。常见的讨论是从「加多少台机器」开始的：网关加几台、应用加几台，数据库不动。问题不在加少了，在于跳过了度量：峰值没算过，数据库那一层扛不扛得住就无从判断。这类活动里先出问题的通常不是网关，是被同步写入压住的订单库，响应时间从几十毫秒抬到几秒，支付回调跟着一起变慢。

这组文章按十二篇来排，从度量写起，一直写到大促链路落地。案例统一用大促秒杀下的下单与履约：整点开抢、单 SKU、峰值是日常的几十到上百倍，链路还是下单、锁库存、支付、发货那一条。站点前面有十篇 DDD，那组文章关心业务边界的划分；这里只关心流量和容量，同一个业务域，名词不用重新认。

顺序是从下往上排的：先量清楚再谈优化，接着是数据层、消息与服务、稳定性，最后落到两个读模型实战。面试技巧、组件源码、学习方法这些不讲。每篇给判断依据和要付的代价，配重画的图和能跑的原创代码。十二篇目录：

  • 高并发（五）NoSQL 与缓存读写策略
  • 高并发（六）缓存高可用、穿透防护与静态加速

DDD（十）实践总结——边界、演进策略与分布式设计

发表于 2023-04-11 分类于 架构设计
本文字数： 6.3k 阅读时长 ≈ 6 分钟

引言

把单体的事务写法原样搬进分布式环境，库存被扣穿只是时间问题。本篇汇总生产落地里最容易失守的几处判断，从一次超卖事故出发，给出服务化改造的固定顺序，以及分布式事务、幂等与对账的收敛手段。

一次服务化上线后的大促，库存被扣穿了。原因不是流量超预估，而是一段沿用自单体的写法被原样搬进了分布式环境：

网络抖动时这条链路分裂成两种不一致：订单写成功、扣减请求超时后重试，库存被扣两次；或者扣减成功、订单事务随后回滚，库存被永久占用。事后团队想用分布式事务框架兜底，把全局事务套在这条长链路上，大促时全局锁又把数据库拖垮。

这类事故的根因不在选了哪个事务框架，而在三件事从未被定清楚：哪些数据必须同生共死，也就是边界；老代码按什么路径退出，也就是演进策略；跨边界失败后如何收敛，也就是分布式设计。三者缺一，补偿任务、对账脚本和半夜告警就会变成常态。

分布式系统里的一致性，不是靠一个框架兜底，而是先把边界划对，再为跨边界的失败设计一条确定的收敛路径。

DDD（八）代码模型——领域对象与目录结构映射

发表于 2023-04-02 分类于 架构设计
本文字数： 10k 阅读时长 ≈ 9 分钟

引言

一个类同时当实体、接口出参和业务计算载体，迟早会在某个 getter 上出事。本篇讲领域模型到代码目录的映射：DO、DTO、PO 与 Entity 各管什么，转换放在哪一层，以及怎样让领域层不依赖框架。

财务对账发现某日全部订单金额缩小了一百倍，最后定位到一行 getter。

某电商订单服务里只有一个 Order 类，它同时被三处使用：作为 JPA 实体映射 t_order 表，作为下单接口的出参由 Jackson 序列化，又在下单流程里承担金额计算。为了让前端直接显示「元」，有人在 getAmount() 里加了句除法。而库里 amount 存的是「分」。

Jackson 序列化出参时调它，Hibernate 脏检查与持久化也调它，内部运算还调它。一个 getter 服务三种用途，任何改法都会波及另外两种。

根因不是这行除法，而是这个类没有确定的身份：它既是数据库表的镜像，又是网络传输的载体，还是业务规则的宿主。三者对「金额」的语义本就不同——库里是分、接口是元、领域里是带币种的值对象——却被压进同一个字段。类似的事故还有另一种形态：领域对象上打满 @Entity、@Table、@JsonProperty，换 ORM、加缓存、发消息时，每动一处都要改业务类。

代码模型要解决的正是这件事：让领域对象拥有独立的类与独立的目录，并规定谁、在哪一层、把它翻译成别的对象。边界不落到目录上，分层就只是一句口号。

DDD（六）领域事件——微服务解耦与最终一致性

引言

本地事务提交成功、消息却没发出去，是跨服务链路里最隐蔽的一类故障。本篇讲领域事件：进程内事件与跨服务事件的差别，Outbox 怎样把业务提交和事件发布收进同一个事务，以及幂等与乱序的收敛办法。

支付回调服务在灰度发布当晚被重启了一次。重启前那几秒里，有 37 笔订单的本地事务已经提交、状态改成「已支付」，进程却在把「支付已完成」写进消息队列之前被 kill 掉。结果：支付上下文显示收款成功，履约上下文始终没收到发货指令，次日客服按「已付款未发货」逐单手工补发，其中两笔因重复补发又触发了退款。

出问题的代码只有一行位置不对：

消息发在事务内，事务一旦回滚，下游会为未成立的支付发货；发在事务外，提交后崩溃就永久丢消息。业务数据在数据库、消息在中间件，两个资源没有共同的事务边界，这类「双写」不可能靠重试补干净——因为重放时无法区分「没发过」和「发过但没记录」。

根因不是消息队列不可靠，而是把一次业务事实拆成了两次没有原子性的写。

DDD（五）聚合与聚合根——一致性边界与设计原则

发表于 2023-03-16 分类于 架构设计
本文字数： 6.8k 阅读时长 ≈ 6 分钟

引言

事务边界画大一圈，大促时就会变成死锁和超卖。本篇讲聚合与聚合根的划法：按不变条件而不是按名词圈边界，四条设计原则怎么用，跨聚合的状态变化为什么只能交给领域事件。

大促开始第 11 分钟，订单库开始大面积报死锁与锁等待超时，下单接口 P99 从 80 毫秒飙到 4 秒；几乎同时冒出超卖工单，却没人能说清库存究竟是在哪一步被扣穿的。排查下来，两类异常指向同一段代码——一个被团队称作 Order 的类，把订单项、SKU 库存、支付流水、发货单全装进同一个聚合，任何一次下单都在一个本地事务里锁住四张表的十几行记录。

Order 名义上是聚合根，实际上成了一段跨表事务的入口。真正致命的不是 @Transactional 标得太大，而是没人说得清哪些对象必须在同一瞬间保持一致。于是库存行被下单、支付回调、发货批处理三类流量争抢；订单项金额与可售库存本不需要同生共死，却被绑进同一把锁；deduct 与 create 散落在应用服务里，超卖时无法判定哪一处是权威。

事务边界画错，调隔离级别、加索引、拆库都只是缓解。要收敛的是边界本身：把「必须同时成功」的东西圈在一起，把其余的请出去。

DDD（四）实体与值对象——领域模型的基础单元

发表于 2023-03-11 分类于 架构设计
本文字数： 5.9k 阅读时长 ≈ 5 分钟

引言

一个地址字段选型错了，发货单、售后单和历史快照会一起跟着变。本篇讲实体与值对象的分界：什么时候该用唯一标识，什么时候用不可变的值，以及值对象在关系库里怎么存。

客服对不上账：用户三天前下的订单，详情页里的收货地址变成了他昨天新改的地址。发货单、售后单、当时的快照全跟着变了。排查下来，地址被建成一张带主键的表，订单只存了一个 address_id，指向那一行可随时 update 的记录。

代码没有 bug，事务也正常。问题在建模：地址在这里没有独立生命周期，它只是”这一单送到哪里”的描述，却被赋予了标识和可变状态。任何一次改动都会沿着 address_id 回溯到全部历史，而历史本不该被改写。

结论先行：判断一个概念靠标识区分、还是靠值区分，决定了它会不会被别处的修改牵连。需要追踪”是不是同一个”、且会独立变化，用实体；只描述”是什么样的”、没有独立生命周期，用值对象。 值对象一旦不可变、只做整体替换，历史就自然被固定在下单那一刻。

DDD（三）通用语言与限界上下文

发表于 2023-03-09 分类于 架构设计
本文字数： 5.3k 阅读时长 ≈ 5 分钟

引言

一张金额表被两个团队按各自的口径共写，对账差额往往从这里开始。本篇讲通用语言与限界上下文：怎样把术语冲突收敛成模型边界，以及边界确定后团队、代码库与数据库该怎么对应。

财务对账连续三天出现差额，量不大，但每天都有。追到最后，问题不在渠道，在一张表：order.amount 一个字段被两个团队写。交易侧把它当应付金额，支付侧把它当渠道实收金额（已扣手续费），两边各按各的口径累加，谁也没觉得有问题——因为在各自的代码里，它都叫”订单金额”。

更早的信号其实已经出现过，只是没人当回事。这个 Order 类被四个团队轮流加字段：

字段越加越宽，是因为没人给”订单”划定它在哪里生效。四个部门开会统一过命名，结论是”都叫订单”，然后各回各家继续往同一个类里塞字段。共享一个模型，把口头的歧义变成了数据库里一行谁都解释不清的数据。

结论先行：跨部门术语歧义不能靠开会统一，只能靠限定每个词生效的范围来收敛。统一语言的产物不是一份词汇表，而是一条条模型边界；边界之内，一个词只有一个含义，边界之外，同名可以不同义。
